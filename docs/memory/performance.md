# Performance — what keeps an instrument light on a phone

Read before adding an instrument, a stage, a transport, an inspector panel, a thumbnail grid, or anything that reads a shared index (the town gazetteer, the coastline, a library's pool). Atelier is JS on ONE main thread, used on his phone and iPad as much as on his Mac; a defect of this family passes every spec in node and only shows as «toute l'interface lag». The rules below are what the 2026-11-10 pass (his report on Recap's Trip card, then «refaire une passe sur les autres instruments») measured and fixed.

## The gate: `scripts/check-perf.mjs` (2026-11-10)

**Decision**: performance is MEASURED by a headless run, never argued from the code. `node scripts/check-perf.mjs [scenario…]` against `npm run dev` (Playwright: the project's, else the machine's global one — `NODE_PATH` does not reach an ES module, the script resolves it itself). Each scenario seeds a synthetic document through the dev server's own modules (a twelve-place West Australian trip, 28 generated pictures with their prints kept — nothing of his, the repo is public), opens the editor and measures: while PLAYING the frame times, long tasks, script ms per second, React commits per second and **`rootRendersPerS`** (how often the editor's ROOT component re-rendered — read through React's DevTools hook: the root's fiber found once, a new hooks list = a render); while EDITING the latency of a click to the next painted frame; the heap after a GC. **Budgets are written for `THROTTLE=4`** (CPU ×4 ≈ a phone): the root ≤ 2 renders/s while playing, frame p95 ≤ 70 ms, ≤ 400 ms of long tasks in 4 s, a click painted in ≤ 400 ms; unthrottled, a quarter of the times. Over budget exits 1. **How to apply**: a new instrument with a transport or a heavy panel gets a scenario here in the commit that adds it; a change to a stage, a clock or a panel runs the gate at `THROTTLE=4` before and after and quotes both in the PR. The harness's noise at ×4 is real (a run of a quiet editor can show one 50–100 ms long task): read three runs before believing a regression under ~150 ms.

## Rule 1 — the playhead lives OUTSIDE React state (2026-11-10)

**Decision**: an instrument's transport time is a `PlayClock` (`shared/media/play-clock.ts`), never a `useState` set from a `requestAnimationFrame` loop. The STAGE repaints from it outside React (`useClockPaint(clock, paint)`, `shared/media/use-play-clock.ts`); the scrubber and the time readout are a small leaf that reads it (`useClockSelect(clock, c => c.t)`); anything else that depends on time reads a DERIVED value that changes rarely (`useClockSelect(clock, c => pageAt(film, c.t))`, «inside the opener») or sets state only when that value turns. **Why**: `setT(now)` per frame re-renders the whole editor sixty times a second — every inspector tab, every thumbnail, every inline prop rebuilt, every effect keyed on one of them re-armed. Measured on Recap's film (month, 28 pictures): 434 ms of script per second unthrottled, 740 at CPU ×4 with frames p95 83 ms; after the clock, **46 ms/s** and the editor's root 0 renders/s while playing (the scrubber leaf still commits 60/s, at a fraction of a millisecond each). Storytelling and Flight Atlas were built this way first — their stages are the model (`StoryStage.tsx`, `AtlasStage.tsx`). **How to apply**: a new instrument with a transport starts from a `PlayClock`; `check-perf.mjs` fails it if its root renders more than twice a second while playing. Seeking is `clock.seek(t)`; keep `setTotal` in a `useLayoutEffect` so a seek is never clamped to a stale length. **A clip's TELEMETRY is a clock too** (2026-11-11): a DJI SRT has a cue per frame, so the active cue lives in a `CueStore` (`shared/telemetry/cue-store.ts`, fed by `useCueStore`), the map's marker and the composite subscribe to it, a readout is a leaf (`useActiveCue` = the store through `useSyncExternalStore`); and a video transport whose host must not re-render ~4×/s passes `useVideoTransport`'s `trackTime: false` with a `VideoSeek` leaf (`shared/media/VideoSeek.tsx`). Composer 20 → 0 and Flight Map 21 → 0 root renders/s while playing (`check-perf` composer-play, map-play). **Where the editor's own logic reads the time** (Trips' piece editor: the needle that picks a motion card, the cut's I/O keys, the band, the badge's settle at rest — 2026-11-10, second pass): the editor keeps a SNAPSHOT at rest and the clock moves while playing — `use-deck-transport.ts`'s `clock` is the open slide's live moment (the still's loop and a clip's reported playhead write it; a layout effect puts it on the snapshot whenever the piece is at rest), the stop writes the clock's moment back into the snapshots IN THE SAME RENDER (`onStop`, a clip's `stopClip`), an event handler that needs the moment reads `clock.t`, and the stage takes a `live` view (`BadgeStage`'s `StageLive`: the badge's time, the framing and the collage at a moment) it reads itself while the piece plays; the band is wrapped in `ClockValue` (`shared/media/ClockValue.tsx`), the leaf that follows a clock. Measured at CPU ×4: Trips' Virée Reel, editor root 26 → 0 renders/s, frames p50 33 → 16.7 ms, script 383 → 178 ms/s; with the Look tab open p50 67 → 33 ms, p95 83 → 33 ms, frames over 50 ms 52 → 1. Two leaves subscribed to one clock commit twice a frame (~120 commits/s, cheap): batch them only if a measurement asks.

## Rule 2 — a shared index is read through a grid or a map, never scanned per question (2026-11-10)

**Decision**: the town gazetteer (135 233 towns), and any other index the suite ships or builds (the coastline, a library's pool), is read through a structure built ONCE per list and kept in a `WeakMap` keyed on the list (rebuilt only if it grew): `gazetteer.ts`'s `forEachCityNear` (one-degree cells; a full scan only near a pole) behind `nearestCity` and `stop-index.ts`'s `townsWithin`, and its names folded once (`namesOf`, behind `homonyms`). **Why**: a scan is cheap ONCE and ruinous in a loop, and the loops are everywhere — a Winnow's statistics name up to 20 000 rows, a deduction names every leg, an export names every picture, a card's six face thumbnails read every stop's state. Measured on the shipped index in node: `nearestCity` 1.28 → 0.012 ms a call, `homonyms` 22.5 → 0.002 ms; the Trip card's face pick 1.3–2.2 s → 150–270 ms at CPU ×4. **How to apply**: before calling a function over a shared index inside a loop, a render or a paint, check it is O(cells), not O(index); a new reader of the index goes through `forEachCityNear` or a folded map, with a spec that it answers exactly what a scan of the whole list answers (cell edges, the antimeridian, near a pole, ties in the list's order).

## Rule 3 — what a memoised child is handed is stable, and the child does not trust it (2026-11-10)

**Decision**: a heavy child (an opener's panel, a thumbnail grid, a canvas painted in an effect) is memoised on props that keep their identity while they mean the same: callbacks through a ref (`useCallback(fn, [])` reading `latest.current`), a value derived from the document memoised ON THE STORED VALUE (`useMemo(() => normaliseFraming(stored), [stored])`, `readPlateSpec(post.badge.camera)`), never an inline arrow, a `{...spread}` or a reader's fresh result. And a SHARED brick does not trust its host: `OpenerPanel` reads `onChange` and the host's asks through a ref itself (`panel-host.ts`), so a host that hands new functions each render cannot re-render a variant's panel. **Why**: the Trip card crawled because Recap handed `OpenerSection` an inline `change`, which broke `OpenerPanel`'s memo every frame (Trips had met the same trap 2026-10-09 and fixed only its own host); a click took 2.6–7 s at CPU ×4. Trips' motion cards and camera tiles repainted per render because a reader returned a new object; Recap's `pictures.still` was a new function per render, so the slide strip and the poster were redone after every click. **How to apply**: before passing a prop to a memoised child or an effect's deps, ask «is this the same object next render if nothing changed?»; a hook that returns a function returns a `useCallback` keyed on what it really reads (an object that is itself new per render — a `LutStack` — read through a ref). A shared brick mounted by several hosts protects itself.

## Rule 4 — a heavy engine rests, then goes; a cache has a byte ceiling (2026-11-10)

**Decision**: a wasm or GPU engine (ffmpeg, the subject model, a RAW/HEIF/JXL decoder, a grader's WebGL context) is let go once it rests and when the tab is hidden on a phone, through `shared/lib/idle-release.ts` (`busy()` / `settled()`; `restMs()` null keeps it on a roomy machine) — the RAW decoder's hand-written shape (`raw-decoder.ts`, `raw-budget.ts` `decoderIdleMs`) made a brick. Everything an engine was handed is freed on EVERY path, failure and cancel included (ffmpeg's in-memory files, its core's blob URLs). A cache that holds bytes (decoded pictures, converted clips, logs' text, map grounds) has a BYTE ceiling by device class (`sources/held-budget.ts`, `raw/decoded-cache.ts`), or a few entries of a known size by device class (Storytelling's map grounds: 2 on a phone, 6 elsewhere) — never an unbounded count — and its entries leave with what they were made from (a converted clip leaves with its Library asset). A GPU resource per item (a collage cell's grader) is disposed when the item is no longer DRAWN, not only when it is asked again. **Why**: wasm memory never shrinks, iOS reclaims a background tab by its memory, and past ~16 live WebGL contexts the browser takes back the OLDEST — often the stage's, which then draws ungraded. The audit of 2026-11-10 found ffmpeg kept for the whole session (one clip's size in its heap, ~32 MB more per cancel), converted clips never forgotten, the segmenter never unloaded, collage graders kept past their cell. **How to apply**: a new engine starts from `idleRelease`; a new cache states its key, its ceiling and what evicts it in its header comment. **A renderer that loses its context on `dispose()` OWNS its canvas, one per renderer** — a `<canvas>` React keeps hands back the same dead context, so the next renderer compiles nothing (`LookScene.tsx` measured it first; the LUT tool's preview drew black after every clip switch, and from the first clip under StrictMode, until 2026-11-10 — `use-lut-preview.ts` now appends its own).

## Rule 5 — a per-frame painter redoes only what moves (2026-11-10)

**Decision**: a stage's paint at time `t` draws from data prepared OUTSIDE the frame: what depends on the document and not on `t` (a ranking of the pool, a picture chosen, a layout, a blurred ground, a road's projection) is computed once per document — memoised on `(doc, resolved)` in a `WeakMap`, or drawn once into an `OffscreenCanvas` the frames draw — and a loop that composites draws only while something moves or after something changed (a dirty flag: Composer's loop, `use-overlay-stage.ts`, `AtlasStage.tsx`), never sixty times a second over a paused frame. A slider over a GPU parameter moves a UNIFORM (`setIntensity`, `setLut`, `setPasses`, `setFilm` on a grader), never a new grader. **Why**: Recap's blurred ground ranked the whole pool and ran a full-page canvas `blur` per frame (25 fps at CPU ×4; 48 after); Composer graded and composited a paused frame sixty times a second (125 ms of script per second for nothing; 1 after) and built a WebGL2 context per step of its strength slider. **How to apply**: in a painter, mark each line «per frame» or «per document»; a «per document» line inside the frame is a cache waiting to be written.

## Rule 6 — what an edit does not touch is not prepared again; a cache that holds a render belongs to ONE surface (2026-11-11)

**Decision**: a resolved opener is cached on what it is really made of, never on the document's identity (an edit makes a new trip and a new piece every time): the slide's own layers (the same array while that slide is untouched), the slide's timing, the aspect, the badge's words (by what they say, `JSON.stringify` of a few strings), the pictures (a new map only when one lands), and the trip's parts an opener reads (`hookCalendar`, `trip.stages`, vehicles, crossings, road, writing, theme, the loaded indexes). `hookStages` is ONE list per stored `stages` (a fresh list per call had made every downstream identity cache miss). The brick is `createHookCache()` (`hooks/hook-context.ts`): **a cache is OWNED by one surface** — the rail keeps its own (`use-rail-thumbs.ts`, through `slideRender`'s `cache`), the deck's lengths and `openerMoves` share `resolvedForTiming` (they read seconds, never paint) — because a `HookRender` carries mutable scratch (Virée's road, its paint caches) and two canvases painting one could corrupt each other; the stage and the exports still prepare their own. **Why**: an edit of ONE slide prepared every opener of the piece again, each Virée planning its whole road: in node, deck + rail after an edit of the first of four Virées 3.64 → 1.28 ms; at CPU ×4 a step of a Virée slider 176 → 135 ms (mean of 18 steps), a key typed in the piece's title 70–130 → 31–82 ms (`check-perf` trips-opener-step, trips-edit). **How to apply**: a new surface that resolves openers in a loop takes its own `createHookCache()`; a new input an opener reads joins the cache's deps in the same commit, or the cache serves a stale opener.

## The checklist for a NEW instrument (2026-11-10)

1. A transport? A `PlayClock`; the stage paints through `useClockPaint`; only the scrubber leaf reads `t` (rule 1). 2. Its panels and grids memoised on stable props; a shared brick it mounts already protects itself (rule 3). 3. Any read of the gazetteer, the coastline or a pool inside a loop, a render or a paint goes through a grid or a folded map (rule 2). 4. A wasm engine, a decoder or a grader rests and goes (`idleRelease`); a cache states its key, ceiling and eviction; a canvas a renderer loses is the renderer's own (rule 4). 5. The painter prepares per document, draws per frame, and sleeps when nothing moves (rule 5). 6. A scenario in `scripts/check-perf.mjs`, green at `THROTTLE=4`, numbers quoted in the PR.

## Open after the pass (2026-11-10)

The full list of what the three audits found, with what was fixed and what was left, is `docs/audit-2026-11-10-performance.md`. Trips' piece editor moved to its clock in the second pass (rule 1), its openers to per-surface caches in the third (rule 6), Composer and Flight Map to the cue store in the fourth (rule 1).
