# Agent commands — the registry, the console, the MCP bridge

Read when you touch `src/shared/commands/`, `src/app/app-commands.ts`, a
`useRegisterCommands` call in a tool, `scripts/atelier-mcp.mjs`, or anything
that would let a script or an agent DRIVE the suite.

## Every agent-facing verb is a COMMAND, registered by the screen that can do it (2026-10-09)

**Decision.** The maintainer asked for LightCraft's command registry and MCP server (`storytold/lightcraft`, a Rust clone of Lightroom, read on 2026-10-08: every gesture there is a command with a stable id and JSON params, and the UI, CLI, a control channel and MCP dispatch through one entry). Atelier takes the REGISTRY half of that idea, not its "the UI is commands" half: `shared/commands/registry.ts` holds `{id, title, description, params, available, run}`, one `execute` door checks the params and runs; a screen registers its commands with `useRegisterCommands(owner, specs)` while it is MOUNTED, and `run` calls the very funnel its gestures call. **Why.** Rewriting every handler of a 200 k-line React app into commands would be a rewrite; registering from the screen means an agent's edit goes through the same updater, journal, undo stack and save as the author's (preview = export holds for free), and a command whose screen is not open is simply ABSENT — `app.waitFor` is how an agent waits for one after `app.navigate`. **How to apply.**
- Ids are dotted and stable (`app.status`, `develop.set`): scripts outlive labels. Two owners may register one id; the latest mounted wins, the earlier comes back when it leaves.
- Params are a small typed subset (`number` with bounds and `integer`, `string` with `enum`, `boolean`, `strings`, `numbers` — a non-empty list checked item by item with `maxItems`, Winnow's batch ids, kept identical in both registries —, `array`, `object`), turned into JSON Schema by `paramsJsonSchema` for MCP. Out of range is REFUSED, never clamped, and an unknown field is refused naming the known ones — a misspelt key that silently did nothing is the failure an agent cannot see.
- `available()` returns `true` or the REASON; `execute` answers `CommandError` with a code (`unknown` · `unavailable` · `invalid` · `failed`).
- `useRegisterCommands` reads the specs through a ref and re-registers only when the SET of ids changes — per-render registration would tell every subscriber the list changed on every slider step.
- A command answers JSON; a picture to LOOK at is an `ImageResult` (`kind: 'image'`, base64 JPEG/PNG), which the MCP bridge turns into an image content block.

## `window.atelier` is the console's door to the same registry (2026-10-09)

`installCommandConsole()` (`main.tsx`) puts `atelier.commands()` and `atelier.run(id, params)` on `window`. It grants nothing a script on the page could not already do; it gives a console, Playwright or a bookmarklet the same checked, undoable door an agent gets. **How to apply**: drive the app headless through `page.evaluate(() => atelier.run(...))` rather than clicking coordinates when the check is about a result, not about the gesture.

## Develop's commands, and an agent's write is MARKED (2026-10-09)

**Decision.** Develop registers its commands from the three screens that hold what they need: `DevelopTool` (`develop.rolls`, `develop.openRoll`, `develop.undo`/`redo` — the roll's own history, so an agent's write is one ⌘Z like the author's), `RollEditor` (`develop.pictures`, `develop.openPicture`, `develop.controls`, `develop.get`, `develop.set`, `develop.reset`), `PictureWorkbench` (`develop.snapshot`). The arithmetic is pure in `shared/develop/develop-commands.ts`: `withDevelopValues` writes ABSOLUTE slider values checked against `DEVELOP_RANGES` (refused outside, never clamped), keeps everything the sliders do not name (curves, mixer, grading, the RAW material) and answers null for "as shot"; `targetPicture` is the one rule "the named picture, else the open one". Every write goes through `handleDevelop` / `update` with `via: 'agent'` — a JournalVia added for this — so the making-of says *by an agent* and the training file carries `agent: true` (`develop-roll.md`). **Why the mark**: B2's pairs exist to learn HIS taste; an agent's develop in them would teach the model the agent. **How to apply**: any new command that writes a picture passes `'agent'`; a trainer filters on `agent`.

**The snapshot waits for the stage.** `develop.set` reaches the roll at once, the stage's cube a render later. `develop.snapshot` first waits until `picture.delivered` — whose IDENTITY tracks every input of the render — has not changed for 150 ms (`untilSteady`, capped at 3 s), then bakes the band cell's own recipe (`framedThumbnail`: graded, cropped, bordered) at `longEdge` (64–2048, default 1024), or the source AS SHOT with `before: true`. Measured headless: a snapshot asked right after a set shows the set. It is `unavailable` while the picture decodes — `app.waitFor('develop.snapshot')` after an open.

**The whole record is writable, by parts (2026-10-09, his «automatiser l'édition des media … vas-y à fond»).** `develop-record-commands.ts` (pure): `develop.curve` (points 0..1 as `[x,y]` or `{x,y}`, sorted here, refused off the square, on a shared x, under 2 or over 32), `develop.levels`, `develop.mixer` (band → value), `develop.bw` (on/off + mix, the colour mixer kept), `develop.grading` (wheels patched) — each writes through `handleDevelop` like `develop.set`; and four SECTION commands (`develop.perspective`, `.lens`, `.detail`, `.vignette`) over ONE rule, `patchRecord`: the patch is merged onto the current record and read back through the section's OWN reader (the one a stored roll goes through), and any named field the reader changed is refused with what it reads back as — so no range is written twice and a clamp is never silent. A clip refuses the sections (`sectionsFor`'s rule). `develop.applyTo` (the batch verb: the source's edited sections by default, `["all"]` = every other picture not ignored), `develop.deliver` (locked during a run like the band's verbs), `develop.words` — all journaled `via: 'agent'`.

**The crop is PLANNED, then restored whole** (`crop-commands.ts`, pure). Chaining the Crop tab's gestures in one tick is unsafe — `use-crop-zone`'s `write` updates `live.current` synchronously but not its zone — so `planCrop` replays the hook's own rules (quarter turns move the zone with the picture, a flip NEGATES the angle and mirrors the centre, a format alone is the largest zone of that shape about the centre, a straighten refits from the intent and never grows it) in the order reset · turn · flips · aspect · rect · straighten, and `crop.restore` writes the answer as an undo would. A rectangle is in fractions of the picture turned by its QUARTER turns only, (0,0) top-left; a locked format refuses a rectangle of another pixel shape (the answer says the h to use); a straighten that shrinks the zone says `adjusted`. `develop.getCrop` reads the same terms back.

**The automatic verbs are the Auto row's own switches** (`develop.auto`, `develop.cropToSubject`, registered in `PictureWorkbench` after `autoSteps`): a step already on is left on, each step's told line is answered back, and the draft write-throughs flush `via: 'agent'` through `asAgent` — a counter over `pendingVia` released three write delays after the last command, like the Auto-on-open path.

**Drive it headless** (`testing.md`'s Playwright recipe): `atelier.run('app.navigate', {path: '/develop/home'})`, `app.waitFor('develop.rolls')`, `develop.openRoll`, then drop files on the editor as the recipe says; every step after that is `atelier.run`.

## The MCP bridge: a relay to the TAB, three generic tools, loopback only (2026-10-09)

**Decision.** Atelier has no backend, so the commands live in the tab and the MCP server is a RELAY: `scripts/atelier-mcp.mjs` (Node, zero dependency) speaks MCP JSON-RPC on stdio to the client and Server-Sent Events + POST on `127.0.0.1:7981` to the tab (`bridge-client.ts`). Everything that decides is pure in `shared/commands/mcp-protocol.ts` (tested): `handleMcpMessage` (`initialize` echoing a known protocol revision, `ping`, `tools/list`, `tools/call`; notifications unanswered), three GENERIC tools — `atelier_status`, `atelier_commands`, `atelier_run` — rather than one tool per command (the tab's commands change with its screen and a client lists tools once; LightCraft does the same with `engine.execute`), `toolContent` turning an `ImageResult` into an MCP image block, a command's refusal answered as a TOOL error (`isError`, the coded message) and never a JSON-RPC error, so the model reads it. **Why the relay is shaped this way**: SSE + POST needs nothing but `node:http` and a browser's `EventSource` (a WebSocket server would have been the first dependency), and Node imports the protocol `.ts` directly through type stripping — which is why `mcp-protocol.ts` imports NOTHING (Node resolves only explicit file names) and restates the two types it shares with `registry.ts`. **How to apply**:
- Security is the `Origin` check (a browser cannot forge it, so no other site the person has open receives commands) plus loopback binding; a request without `Origin` (curl) is refused too. A newer tab REPLACES the older (`event: replaced`, the older stands down and says so). Pending calls fail with a sentence when the tab goes; a run times out at 150 s (above `app.waitFor`'s 120 s ceiling).
- The tab connects only on the person's click on `#/sources` (*Agents* row), per TAB in `sessionStorage`; `resumeBridge()` at boot reconnects only a tab that was connected before its reload. The masthead's `AgentPill` is drawn whenever it is on — a tab an agent can write to never looks like one it cannot.
- Requires Node ≥ 22.18 (type stripping on by default). CI runs Node 20 but never runs the script; its logic is covered by `mcp-protocol.test.ts`, and the whole chain was driven headless here: the real script on stdio, a tab connected through the UI, refusals, `develop.set`, a snapshot arriving as an image, undo, reload-reconnect, disconnect, a 403 for a foreign origin.
- Port taken by something that is NOT an Atelier bridge: the script keeps answering MCP and every tool says so (`McpDeps.problem`) rather than dying silently. Taken by another Atelier bridge: it FOLLOWS it (next section).
- Winnow and p5-templates were given the SAME conventions (dotted ids, refused-not-clamped params, `available()` with a reason, coded errors, image results, a `*_status`/`*_commands`/`*_run` trio) in their own sessions on 2026-10-09; Winnow, having a server, may serve MCP itself rather than relay.

## The look and the presets, for an agent (2026-10-09)

**Decision.** The look is written through the very `LutStack` the Look tab drives (`look-commands.ts`: `develop.looks` lists the built-in LUTs, the film stocks and the output transforms; `develop.look`, `.addLook` (builtin XOR film, intensity 0..3), `.setLook` (intensity, enabled, move), `.removeLook`, `.lookOutput`), so a look is baked, saved and undone like a click; each waits for `stack.busy` to fall before answering. The stack follows the OPEN picture, so a roll is dressed by one picture then `develop.applyTo` with `look`. Purchased pack looks and uploaded `.cube`s are NOT offered: they live in a vault the person owns. The stack's writes reach the roll through `useRollGrade`'s updater, which `RollEditor` now wraps with a `lookVia` ref set to `agent` while a look command runs (released 600 ms after, the stack writing an effect later) — the only way to mark a write the editor does not make itself. **Presets** (`preset-commands.ts`, pure): `develop.presets`, `develop.applyPreset` (by id or a unique name, onto named pictures or `["all"]`, ONE undo step, the preset's look worn when it carries one), `develop.savePreset`; `presetOnto` is `setDraft`'s rule (the picture's RAW material and base curve kept) and `presetsNow()` in `use-preset-book.ts` loads the book before reading it.

## A roll is made, filled and EXPORTED by an agent — the export through the bridge (2026-10-09)

**Decision.** `develop.newRoll` (`DevelopTool`: an empty roll kept in this browser, opened), `develop.addFromWinnow` (a day or span of the connected instance through `client.allAssets`, narrowed by Winnow's OWN culling — verdict, min stars — and kind by the pure `ingest-commands.ts`, added as refs through `rowMediaRef` + `addPictures` like *Add a day*; the bytes are fetched when a picture opens), `develop.addFromLibrary` (the Library's files by name or `["all"]`, hashed and split by `splitByRoll` so nothing lands twice), `develop.exportPlan` (each picture's run-plan line and whether it leaves) and `develop.export`. **Why the export goes through the bridge**: a folder picker must be asked AT THE CLICK (`frontend.md`) and an agent has no click to give; a download would land wherever the browser decides. So `DeliveryTarget` gained a third kind, `sink` (`deliver-files.ts`): `useRollExport.exportPictures(ids, to?)` takes it instead of picking, everything else — targets, sizes, EXIF stamping, the delivered marks, the note — is the roll's own run. `bridgeSink()` POSTs each file to the bridge's `/file` (name and sub-folder in URI-encoded headers), and the script streams it to `<--out>/<folder>/<name>.part` then renames — never outside the folder (`safeOutputPath`: no dot or empty segment, no separator or control character in a name), never over a file (`numberedName`, the suite's own `-1`, `-2`), at most `MAX_FILE_BYTES`. The person chose that folder by starting the bridge, which is what stands in for the click. **How to apply**: `develop.export` is `unavailable` without a connected bridge — it must never fall back to a picker or a download an agent cannot see; the answer lists the paths written on that computer (`atelier_status` says `exportsGoTo`). Driven headless: a roll made, two pictures dropped, an edit, one export, an all-export and a repeat writing `A.jpg`, `A-1.jpg`, `B.jpg`, `A-2.jpg` with the `Atelier` signature; a `..` folder or name refused 400. `addFromWinnow` was checked only for its refusal without an instance.

## The bridge is SERVED by the site as one file, built at every build (2026-10-10)

**Decision.** The maintainer asked for the MCP script to be hosted with the site (`public/`), so the bridge installs like a remote MCP — a download and `claude mcp add`, no clone. `agentBridgePlugin` in `vite.config.ts` bundles `scripts/atelier-mcp.mjs` + `mcp-protocol.ts` with esbuild (Vite's own dependency, imported lazily) into ONE plain-JS file emitted at `<base>atelier-mcp.mjs` at build and answered by the dev server; its version is `package.json`'s plus `+<GITHUB_SHA>` (`ATELIER_BRIDGE_VERSION`, a build `define` the script reads before falling back to `package.json`). `#/sources` shows the two install lines for the address the site was opened on. **Why generated and not committed into `public/`**: a committed copy drifts from the protocol the tab speaks; built from source it is served at the same URL a `public/` file would be and can never be stale. **Why the bridge stays at all**: a remote MCP (Gmail's kind) works because the data and the work live on a server; Atelier's live in the tab, which cannot be called from outside, so something local (this bridge), the browser's own agent (Claude in Chrome over `window.atelier`, later WebMCP's `document.modelContext`) or a relay on a server he owns (Winnow) must reach in — the last two discussed with him, not built. **How to apply**: change the bridge in `scripts/`, never the emitted file; driven end to end with the BUILT file copied out of `dist/` (a production preview, a tab connected, an export written). Tested on Node 22 only; the bundle targets Node 18.

## Setting it up is a PAGE, `#/agents`, and Claude Desktop installs it from a file (2026-10-10)

**Decision.** His ask: an elegant in-app guide that makes setup need as little typing as possible. `AgentsGuide.tsx` (a shell reading page like `#/sources`, linked from its Agents row) is three numbered steps over the LIVE bridge state (`BridgeControl.tsx`, shared with the Sources row so both say the same): (1) pick your app — **Claude Desktop** gets `atelier.mcpb`, an MCP bundle (a STORED ZIP of `manifest.json` + the bridge, `zip-store.ts` + `mcpbManifest` in `mcp-protocol.ts`, emitted beside `atelier-mcp.mjs` by `agentBridgePlugin`) that installs from a dialog with no terminal, Claude Desktop running it with its own Node; **Claude Code** gets the file plus one copyable line (or a curl one-liner); **Other** gets the `mcpServers` JSON filled live from the path typed; (2) Connect, ticked off when connected; (3) example prompts to copy; then a folded "Good to know" (exports, scope, privacy, the two waiting states, browsers, removal). **Why a page**: the how-to was a code line in the Sources row; a guide that checks itself off replaces reading with doing, and the row keeps one link. **How to apply**: the manifest is `manifest_version` 0.3 written from the MCPB spec as read on 2026-10-10 and NOT yet installed in a real Claude Desktop — the first thing to check on his Mac; the bundle's tools are listed from `MCP_TOOLS` so they cannot drift; a change to the bridge needs nothing here. Driven headless: both downloads served (dev and build), the zip read back by Python's `zipfile`, the bundled server answering `initialize` from the extracted archive, Connect ticking steps 1–2, no overflow at 390 px.

## Two MCP apps, one tab: the second bridge FOLLOWS the first (2026-10-10)

**Decision.** His first real run had Claude Desktop's extension holding 7981 with the tab connected while a Claude Code session started its own bridge, which could only answer «port taken» — and the advice it gave (restart the app, change the port) was a workaround, not a fix. Now the bridge that binds the port is the HUB; one that finds the port held probes the hub's `/peer/status` and, if it answers, FOLLOWS it: `atelier_status`, `atelier_commands` and `atelier_run` are relayed through `/peer/relay` (the hub's own `relay`, its 150 s timeout), the status is the hub's tab, exports land in the HUB's `--out` (it writes the files). When the hub's app quits, the follower's next call finds it gone and `takeOver()` binds the port; the tab's `EventSource` reconnects on its own, so no click is needed. **Security**: `/peer/*` is for programs on this computer — it refuses any request carrying an `Origin` (every browser request does, so neither a web page nor a DNS-rebinding one gets in) and asks for a 32-byte token the hub writes at `~/.atelier/bridge-<port>.token` (0600, dir 0700, removed on exit if still its own); compared in constant time (`peerAuthorized`, pure in `mcp-protocol.ts` with `parsePeerRequest`). A local process of the same user can therefore drive the tab — the same trust it already has over the files. **How to apply**: never tell a person to restart an app or change the port for two MCP clients; the guide's «Claude Desktop and Claude Code at the same time?» says it works. Driven headless: hub + follower on one port, the follower opening Develop and making a roll through the hub, a forged-Origin and a token-less `/peer/status` both 403, the hub quit, the follower taking the port and the tab reconnecting by itself.
