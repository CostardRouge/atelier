# Media pipeline — decode, grade, composite, encode

Read before touching video decode/encode, any export, the transcode fallback, LUT rendering, or canvas compositing (`src/shared/media/*`, `src/shared/lut/*`, `src/tools/lut/*`, `src/tools/overlay/*`, `src/tools/composer/*`).

## One shared WebCodecs pipeline, parameterised by a frame processor (2026-08-20)

**Decision.** `shared/media/webcodecs-export.ts` owns the whole demux → decode → transform → encode → mux machinery (mp4box.js → `VideoDecoder` → processor → `VideoEncoder` H.264 → mp4-muxer). Tools supply only a `FrameProcessor`. **Why**: the machinery is subtle and was being duplicated per export path. **How to apply**: a new export is a new processor, not a new pipeline. The processor **must not** close the frame it is given — the pipeline closes it after `draw` returns. Audio is **remuxed, never re-encoded**, so it stays bit-for-bit identical.

## The pipeline's other half: frames we PAINT, with no source clip (2026-09-09)

**Decision.** `shared/media/render-video.ts` (`encodeFrames`) encodes a sequence of painted canvases into an MP4 with no demux and no decoder: the caller supplies `draw(tSeconds)` and a duration, and gets H.264 back. **Why it had to exist**: `exportProcessedVideo` refuses a source with no samples (`No video frames found.`, then a codec description it cannot get), and the still path (`photo-frame.ts`) delivers a JPEG — so an animated badge over a *photograph* could not leave as a video from anywhere in the suite. It is not a second exporter: the codec pick, the bitrate, the queue back-pressure, the colour-tag guard and the frame plan are the same functions the decode pipeline uses, and the encoder lives in the same `try/finally` for the reason above.

**Two properties are structural, not omissions, and every caller must say them out loud**: a painted clip is **silent** (audio is copied and never re-encoded, and there is no demuxed track to copy), and it has **no source cadence to inherit** (`DEFAULT_PAINTED_FPS` is 30, a delivery choice). It refuses a zero-length clip rather than delivering an empty MP4.

**`framePlan` (`shared/media/frame-plan.ts`) is now shared** by this and by the outro tail — it was `tailFrames` in `export-tail.ts`, which kept only the `ExportTail` interface. Same arithmetic, two callers; a second copy is how two exports come to disagree about a duration.

**How to verify it, since no CI runner and no container Chromium has an H.264 encoder**: stub `VideoEncoder` / `VideoFrame` / `EncodedVideoChunk` and let the REAL mp4-muxer run (`render-video.test.ts`) — that proves the plan, contiguous timestamps, the keyframe cadence, every frame being closed and a real MP4 coming out. The stub chunks must be instances of the stubbed `EncodedVideoChunk`: mp4-muxer checks with `instanceof` and rejects a plain object. What no test can prove is that a real encoder accepts the config.

## Having a `VideoEncoder` is not being able to encode (2026-09-09)

**Measured, in this very container.** `isEncodeSupported()` answers "does the WebCodecs surface exist"; a Chromium build can carry all of it and refuse **every** H.264 config. `pickAvcCodec` then returns its baseline fallback (right for the decode pipeline, which may still get lucky), `configure()` throws asynchronously, and what reaches the author is the platform's own *"Encoder creation error"* — nothing they can act on.

**Two remedies, both kept**: `encodeFrames` re-probes `isConfigSupported` for the codec it picked and refuses with a sentence naming the size, so no run dies opaquely; and `useAvcEncodeSupport()` (`shared/media/use-encode-support.ts`) runs that probe ONCE per page at 1080p so a panel can say a clip is impossible **before** the author presses anything. It starts optimistic — a panel that says "no video" for a beat and then contradicts itself is worse than one that corrects itself once. **How to apply**: gate a BUTTON on `isEncodeSupported()` only for "is this API here"; gate what you PROMISE on the probe.

## How a source sits in an output frame is one shared transform (2026-09-07, rev. 2026-09-13)

**Decision.** `shared/media/framing.ts` owns pan, zoom, rotation and a mirror, over the cover-crop or a `contain` fit that letterboxes in black (`roadtrip.md` has why and the axis rules): `framingTransform` (pure, tested) and `drawFramed`, called by Road Trip's `renderBadge` and by `exportVariantVideo`. `VariantRenderOptions.framing` is optional and defaults to the centred cover, so every Studio export renders exactly as before. **Why one module**: the preview, the PNG deck and the burned-in clip are three renderers of the same picture, and a second copy of the transform is how they start disagreeing about where the picture is. **How to apply**: a new renderer that composites a source into a frame calls `drawFramed` rather than `fitRect(..., 'cover')` plus its own drawImage; the crop invariants (never below the fit's own scale 1, pan clamped to the slack, long-edge units) and the black bars live there and must not be re-derived at a call site — `drawFramed` fills the bars itself, so a caller reusing a canvas needs no clear of its own. The reasoning behind the value itself is in `roadtrip.md`.


## A failed export can silently break every export after it in the same tab (2026-08-22)

**Decision.** `exportProcessedVideo` now creates the `VideoEncoder` and `VideoDecoder`, and everything that can throw between their creation and the final `flush()`/`finalize()`, inside one `try/finally` that always calls `.close()` on both. `createLutRenderer`'s `dispose()` now also calls `gl.getExtension('WEBGL_lose_context')?.loseContext()`, not just `gl.delete*` on the individual objects.

**Why.** Both were leaking a browser-capped resource on the failure path only, which is exactly why they went unnoticed: `encoder.configure()`/`decoder.configure()` used to run *before* the pipeline's one `try { … } finally { close both }` block (added when the shared pipeline was built, see above), so a config the encoder actually rejects — e.g. a reframed variant (9:16 "TikTok" preset etc.) landing on an output resolution the hardware encoder won't take — threw straight out of `exportProcessedVideo` with the encoder never closed. Deleting a WebGL renderer's individual objects (`deleteTexture`/`deleteProgram`/…) frees their GPU memory but **not the context slot itself** — only GC (non-deterministic) or an explicit `loseContext()` does that, and `frame-grader.ts` allocates a fresh WebGL2 context per export run. Symptom reported by the maintainer: exporting two variants where one used a reframe preset failed on that variant, and *every export after it, including ones that had worked moments before, then failed too, in the same tab* — consistent with a leaked hardware encoder session or a WebGL context slot never being freed, both of which are page-lifetime caps, not per-call ones.

**How to apply.** Any future change to `exportProcessedVideo` must keep encoder/decoder creation, `configure()`, and the whole encode loop inside the same `try/finally` that closes them — do not hoist a `.configure()` call back out "because it can't normally fail there", that was exactly the previous shape. Any other `dispose()` on a WebGL renderer created per call (not the long-lived preview one, which is reused and only disposed on unmount) should lose its context too.

## Export frame rate is a resample, not a re-time (2026-08-21)

**Decision.** `shared/media/frame-rate.ts` (pure, 14 tests) holds the choice (`ExportFrameRate = 'source' | number`, `FRAME_RATE_CHOICES` 24/25/30/48/50/60/120) and the arithmetic; `ExportOptions.frameRate` carries it into the shared pipeline and a 10th positional argument into the seek fallback. **Why this shape**: the clip must keep its wall-clock duration, because audio is remuxed untouched and any re-time would desync it. So the output is a regular `1/fps` grid over the same timeline — frames dropped below the source rate, **duplicated** above it. No interpolation, ever: inventing intermediate frames would be the same lie as a fabricated telemetry value, which is why the export panel spells out "frames are duplicated, not interpolated" as soon as a variant asks for more than the clip has.

**How to apply.** `resolveFrameRate` maps a request equal to the measured (rounded) source rate back onto the source, and the pipeline then takes the **exact pass-through** — original timestamps, original per-frame durations. That branch is what keeps 29.97 footage exported "at 30" off a grid it would slowly drift against, and what makes the default path bit-identical to before the feature existed. A dropped frame skips `processor.draw` entirely, so a 60 → 24 export is *cheaper* than a plain one; a duplicated frame draws once and encodes the same surface twice. Progress stays keyed to decoded source frames (the real work), the GOP and the derived bitrate to the **output** rate.

**The trap that cost the first implementation.** Sample times and durations are each rounded to whole microseconds independently, so a span built as `timestamp + duration` overshoots its successor's start by a microsecond or two. Planning on the raw half-open span made 60 → 30 keep frames 0, 1, 3, 5 — the right *count* on the right grid, but a phase that stutters. `planFrameIndices` therefore shifts the comparison by `EDGE_TOLERANCE_MICROS` (500 µs — orders of magnitude above the jitter, far below the 8.3 ms of a 120 fps frame). Any future span arithmetic over decoded frames needs the same margin.

**Verified in headless Chromium** (2026-08-21), because vitest cannot run WebCodecs: a synthetic 2 s / 30 fps clip whose every frame carries its index in the red channel, pushed through the real pipeline and decoded back. source → 60 frames, original timestamps, each source frame once; 60 → 120 frames on a 16.67 ms grid, each source frame exactly twice, still 60 draws; 24 → 48 frames, the 5:4 pull-down 0,1,2,3,5,6,7,8,10…; 15 → 30 frames, 0,2,4,6…; duration preserved throughout. **Note for anyone redoing this**: Playwright's Chromium (`/opt/pw-browsers/chromium`) ships **no H.264 encoder or decoder at all** — `VideoEncoder.isConfigSupported` returns false for every `avc1.*`. The run used a copy of the pipeline with only its codec strings swapped to VP9 (`vp09.00.10.08`, muxer `codec: 'vp9'`, no `avc` config block); everything else, retiming included, was byte-identical. Also: WebCodecs is absent on `about:blank` — serve the page from `http://localhost` or the globals are simply undefined.

**That swap also unlocks driving the real app.** Applied to the working tree (four lines, reverted before committing), `npm run dev` + Playwright can take the Studio through a complete export and show the result on screen — how the export-feedback stats were checked, 2026-08-21. Two things that cost time: the Library's **Add files** button opens the File System Access picker, which Playwright cannot drive, so the way in is a synthetic `drop` event carrying a `DataTransfer` — dispatched on the drop-zone div itself, not an ancestor, and it falls through to `dataTransfer.files` because programmatic items return null from `webkitGetAsEntry`; and software VP9 under swiftshader runs at ~0.2× realtime, so a 3-second clip takes ~15 s per variant — poll for the finished state, don't guess a timeout.

## Exporting a trimmed range (2026-08-21)

**Decision.** `ExportOptions.trim` cuts inside the same pipeline rather than through a second one; `trimWindow` (pure, tested) resolves a range into sample indices. Three things it encodes, none of them optional: (1) decoding starts at the **sync sample before** the in point and the frames up to it are decoded then **dropped** — start at the in point itself and the first second is macroblock soup; (2) the last sample to decode is the highest-*indexed* one presented before the out point, because a frame can only reference frames earlier in decode order, so that bound is both sufficient and tight with B-frames; (3) the output is rebased on the **frame that covers** the in point (the one the preview shows under the handle) — the earliest PRESENTED of those, never the first in decode order, or a P-frame decoded ahead of its B-frames opens the cut and drops them — and **only the encoder's timestamp is shifted** — `processor.draw` keeps receiving SOURCE times, or the telemetry, the capture clock and the cues detach from the picture; (4) **2026-09-13 — every edge is measured on the AUTHOR'S clock, which starts at the first presented frame (`TrimWindow.leadMicros`, the smallest sample cts), not at the samples' zero.** A B-framed MP4 (ffmpeg writes two frames of composition delay and an edit list mp4box does not apply) has its first frame at cts 67 ms at 30 fps while the `<video>` element, and so the trim bar, calls it 0: read raw, every cut ended two frames short (a 3 s slide shipped 2.93 s) and the copied or mixed sound slid 67 ms against the picture. `baseMicros`/`endMicros` stay in sample time for the decoder's filter; audio (`copyAudio`, `decodeAacWindow`) and `processor.draw` get them minus the lead; an untrimmed export is rebased on the lead too (0 for a clip without reordering, byte-identical as before). The edges carry a 500 µs tolerance because µs rounding of a 1/60 s timescale let a 181st frame into a 3 s cut. Audio is filtered and rebased on the same origin by `copyAudio`, so a cut lands on an AAC frame boundary (~21 ms) — still no re-encode. The seek fallback applies the same range by seeking `start + i/fps` and looking cues up at the source time. An untrimmed export passes `null` and takes byte-for-byte the old path. Retiming composes with it: the output grid is anchored on the first **kept** frame and every timestamp is rebased by the trim's origin, so a 30 fps cut of a 60 fps clip starts at zero on its own grid.

**Verified in headless Chromium** (2026-08-21) with the VP9-swapped copy of the pipeline described above, on a synthetic 3 s / 30 fps clip: a 1.0 → 2.0 s trim produced exactly 30 frames, source frames 30–59 contiguous (so the keyframe-before-the-in-point decode and the drop of its lead-in frames are right), timestamps 0 → 966 667 µs, and `processor.draw` received source times 1.000 000 → 1.966 667 s — the overlays stay on the frames they belong to. The same trim at 15 fps gave 15 frames, source frames 30, 32, …, 58 on a 66 667 µs grid from zero; an untrimmed run gave all 90 frames unchanged. **Measured with real H.264 on 2026-09-13** (Chrome 152 in the desktop app's Browser pane, which HAS an H.264 encoder at 1080p and 4K, HEVC decode and AAC encode): after fix (4), B-framed 1080p30 with AAC, HEVC Main10 4K30 and a portrait 4K60 cut at 0–3, 1–4, 1.2–2.7 s and at 0.5×/2× all come out with the exact frame count, the in point on the right source frame (a luma-coded clip) and the click of the sound where it was. **Trap for anyone rebuilding this harness**: stamp the frame index as big black/white blocks, not as a level in one channel — a subtle red ramp drifted by up to 12 units through VP9 and made the readback lie.

## `bakeRotation` when anything is drawn at fixed coordinates (2026-08-20)

**Decision.** Exports that draw something positioned (overlays, compositions) set `bakeRotation`, rotating each decoded frame into display orientation in pixels and emitting `rotation: 0`, instead of relying on the container rotation flag. **Why**: with a rotation flag, burned-in elements land in coded coordinates and no longer match the on-screen preview — this was a real bug (`a989ce6`). Default is off because it is cheaper and fine for orientation-independent passes. **How to apply**: drawing anything at specific coordinates → bake. Using `outputSize` (compositions) forces muxer rotation to 0 and makes the processor responsible for orienting the frame itself.

## HEVC: transcode in-browser rather than refuse or upload (2026-08-20)

**Decision.** Clips the browser cannot decode get an opt-in "Transcode to H.264" action backed by ffmpeg.wasm (`shared/media/transcode.ts`), run entirely on the user's machine. **Why**: recent DJI drones record HEVC/H.265, which Chrome decodes inconsistently; the alternative would have been uploading or telling the user to leave the app. **How to apply**: constraints that shaped the module and must survive edits — the **single-threaded** core is used because GitHub Pages is not cross-origin isolated, so `SharedArrayBuffer` (multithreaded core) is unavailable; the core version is pinned so the runtime fetch cannot drift; runs are serialised through a promise chain (one wasm instance at a time) and the chain is kept alive on rejection so the queue never wedges; a hard cancel terminates the worker and resets, since that is the only way to stop ffmpeg mid-run; output is copied into a fresh `ArrayBuffer`-backed view because the wasm FS may hand back a `SharedArrayBuffer`-backed one, which is not a valid `BlobPart`.

## Transcode results are shared through a `File`-keyed store (2026-08-20)

**Decision.** `transcode-store.ts` dedupes by source `File` identity, tracks progress, caches the result and notifies subscribers; consumers read it through `useTranscode`. **Why**: the gallery works off raw `File`s while the studios work off library assets — they share no React state, so the `File` itself is the only natural key, and re-running a multi-minute ffmpeg pass per consumer is unacceptable. **How to apply**: the store is React-free with the transcode function injected, which is what makes it unit-testable in node — keep that shape.

## A codec-agnostic seek fallback exists for overlay export (2026-08-20)

**Decision.** `overlay/export-overlay-seek.ts` decodes via a `<video>` element (seek frame-by-frame, draw to canvas, feed the same encoder) when WebCodecs cannot decode the source; `export-overlay.ts` chooses the path and falls back on a late decode failure. **Why**: some browsers *play* HEVC in a `<video>` element while WebCodecs refuses it. **How to apply**: know the trade-offs before extending it — every seek decodes from the prior keyframe (far slower than realtime) and frame timing is approximate (`currentTime = i/fps` lands on the nearest decoded frame ≤ t). Composer export has **no** seek fallback yet: undecodable HEVC there surfaces a clear message instead.

## Grading happens in exactly one place (2026-08-20, rev. 2026-08-25)

**Decision.** `lut/lut-gl.ts` is a framework-free WebGL2 renderer (frame as 2D texture, `sampler3D` LUT with hardware trilinear interpolation); `frame-grader.ts` wraps it for the exporters so preview and export grade identically. **Why**: two grading implementations would diverge visibly. **How to apply**: LUT texel sampling is mapped onto texel centres (`scale = (N-1)/N`, `offset = 0.5/N`) so cube edges are not clipped — do not "simplify" that. Intensity above 1 extrapolates past the look and the 8-bit canvas clamps the overshoot. Without WebGL2 the grader degrades to pass-through so an export produces un-graded output rather than failing.

**WebGL trap, measured (2026-08-25): `UNPACK_FLIP_Y_WEBGL` is IGNORED for an `ImageBitmap`** — its orientation is fixed at creation, per spec — while every other `TexImageSource` (video, canvas) honours it. The renderer uploads flipped so its UVs line up, so when photo support handed it an `ImageBitmap` the graded still rendered upside down, on the stage AND in the JPEG export, with all four CI gates green. The fix is a `u_flipY` vertex-shader uniform set per draw by `source instanceof ImageBitmap` — compensate in UV space, never by pre-flipping the bitmap (the 2D path needs it upright). Any future texture upload path must ask which sources actually obey the flip flag. Note what that keying buys, since the stage now relies on it: hand the renderer a **canvas** holding the same picture and it comes out upright too, because a canvas obeys the flag and the uniform is then 0 — measured, both ways, in a browser.

**Every FILE decode says `imageOrientation: 'from-image'` (2026-09-20, the audit).** `decodePhoto` always did; `measurePicture`, `pictureThumbnail`, `loadImageMeta` and `loadBadgeSource` did not, and relied on the browser's default. The spec's default IS `from-image` today, so nothing changed on a current browser — the point is that the four readings that plan a delivery (the measured size), show it (the thumbnail, the library card) and cut it (the render) can no longer disagree on which way up a phone portrait is, whatever a browser decides its default means. Rule: a `createImageBitmap(file)` without the option is a defect, since a file can carry EXIF; a bitmap-to-bitmap resize needs none, its orientation is already fixed. Unverified: a RAW's EMBEDDED preview (`raw-probe.ts`) may carry no orientation tag of its own while the DNG's IFD0 does, so a portrait DNG could open sideways — needs a real file.

## The stage has a pixel budget; the deliverables do not (2026-09-09)

**Reported from an iPhone: picking a LUT on a JPEG killed the tab.** The stage drew at the media's own density, which is right for a clip — 4K is 8.3 megapixels — and ruinous for a photograph. Measured in Chromium on a 48-megapixel drone JPEG (8064×6048): the stage canvas was 48 771 072 pixels, 194 MB, and choosing a LUT put a texture and a drawing buffer of that same size on the GPU beside it. Three buffers of ~194 MB is not a leak, it is arithmetic, and it is more than an iPhone's tab is given. The photograph is also past `MAX_TEXTURE_SIZE` on older phone GPUs, so the upload could not have worked anyway.

**Decision.** `overlay/stage-size.ts` (pure, tested) gives the stage a budget — `MAX_STAGE_PIXELS`, one 4K frame — and `useOverlayStage` sizes its canvas through it: the media's own size while it fits, scaled down by area with the aspect kept once it does not. The same 48 MP still now works at 3326×2494, 33 MB. **It is a preview budget and nothing else**: the exports, the frame grab and the thumbnail all compose from the source bitmap at its own density, so no deliverable loses a pixel.

**How to apply.** Everything after the sizing reads the CANVAS's size, never the media's, so overlays, guides, the hit test and the selection outline follow for free. The two places that did not: the grader is handed the already-downscaled canvas instead of the frame once the frame is over budget (which keeps the texture at the stage's size — and stays upright, see the flip trap above), and the A/B wipe converts its cut from stage pixels to source pixels, or a capped still shows its left tenth blown across the divider. Any new code in `drawFrame` that reaches for `frame.w`/`frame.h` needs the same conversion.

**Still at source density, deliberately**: the still export and the frame grab (`photo-frame.ts`, `frame-grab.ts`) build a grader the size of the whole bitmap, because grading before the crop is a quality decision (a LUT is non-linear, so grading a downscaled picture is not the same picture). That is the next thing to measure on a phone — a 48 MP export has the same shape as the crash above — and it cannot be "fixed" by shrinking without deciding what the output owes the source.

## A preview grades once per picture, and draws a raster copy (2026-09-14)

**Reported: on the Trips editor, a picture with a LUT made every stage interaction lag.** Every repaint (block drag, pan, wheel zoom, selection) sent the whole picture through `grader.render` again. Measured in the desktop app's Chromium, 48 MP JPEG, wheel zoom one step per frame: **876 ms a frame, 6.6 s of long tasks over 60 frames**; after, **8.3 ms (display cap), zero long tasks**. Isolated per paint on a 1600 px canvas: regrade 31 ms (12 MP) / 103 ms (48 MP) against 6 ms ungraded.

**Decision.** `shared/lut/held-grader.ts` (`holdGrades`, node-tested) wraps a grader: it grades again only for a different source object or after `invalidate()`, and on the SECOND paint of an unchanged picture copies the result into a CPU-backed 2D surface (`willReadFrequently`) served from then on. `BadgeStage` and `DevelopSheet` use it; the stage also decodes its still through `boundSource` (`badge-render.ts`, the stage budget by area, never enlarging, still reporting the FILE's size to `onSourceLoaded` because the exports size variants from it).

**The trap that makes the copy necessary**: drawing a WebGL canvas into a 2D canvas costs a copy PER DRAW, proportional to its size (13 ms at a 4K frame, 38 ms at 48 MP, even held) — and so does a GPU-backed OffscreenCanvas 2D or `createImageBitmap(glCanvas)`. A raster surface is uploaded once and cached: ~6 ms at any size, for a ~3 ms copy at 4K. **How to apply**: a clip's element is the same object for every frame, so its owner must `invalidate()` on each new frame (`BadgeStage` keys it on `frameSeq`); never copy on the first paint after a change, or a strength slider and a playing clip pay a readback per step for a result they discard. Budget first, then hold: holding alone left 48 MP at 38 ms.

## The output transform: Rec.709 2.4 vs the sRGB canvas (2026-08-21)

**Decision.** `shared/lut/transfer.ts` (pure, tested) holds the transfer functions and the four named `OutputTransform`s; `composeLutStack(layers, output)` bakes the chosen one into the composed cube as a final, non-reorderable delivery stage. **Why**: every conversion LUT shipped here (D-Log→709, Apple Log→709, S-Log→709) emits values authored for a Rec.709 reference display (BT.1886, ~gamma 2.4), and we draw them onto a plain sRGB (~2.2) canvas with no conversion — so a look reads lighter and flatter than authored, strongly in the shadows (+59% at code 0.1, +15% at 0.5, 0% at both ends) and not at all at the ends, which is why the symptom is "milky, lifted blacks" rather than "brighter image". Rec.709 and sRGB share primaries and white point, so this is a **per-channel 1-D curve change, no 3×3 matrix** — the reason it is thirty lines of maths and not a colour-management subsystem. **How to apply**: it is **baked, never a shader stage** — the shader's `mix(src, looked, u_intensity)` means a stage placed after that mix would transform *ungraded log* at intensity 0; folded into the LUT's output values, intensity 0 correctly returns the untouched source, and all six consumers (preview, still grab, five export paths) get it free because they already take exactly one `CubeLut`. A transform bypasses both compose shortcuts (the single-full-strength-layer pass-through, and the `null` return for an empty stack) and imposes a lattice **floor of 33**, still rising to the largest input and capped at 64.

**The floor is a floor, not a target, and that distinction is load-bearing.** Forcing 64³ was the first attempt and it was wrong: **the bake is NOT a one-off.** `setIntensity` maps to a new `layers` array, so the `useMemo` in `use-lut-stack.ts` is invalidated on *every step of the strength slider* — which has no debounce and no local state — and `composeLutStack` runs synchronously during render. At 64³ that is ~180–230 ms per step and the UI freezes for seconds mid-drag; at the 33³ floor it is ~28 ms (≈36 fps) and the drag stays usable. Do not re-raise the floor without also deferring the bake. Measured worst error against an exact sample over a grey ramp, DJI D-Log M: **33³ = 0.77 code, 48³ = 1.34, 64³ = 0.35** — the first two are still under the 8-bit quantisation step, so eight times the lattice buys nothing visible. The order is **not monotonic**, because a 33³ composed lattice coincides node-for-node with a 33³ source; that alignment is luck, which is exactly why the rule keeps "largest input, capped at 64" rather than pinning 33.

**Second trap on the same hot path**: `applyTransfer` re-derives its (from, to) pair and allocates per call. Use `makeTransfer`, which resolves once, anywhere inside a loop — the bake calls it 3× per lattice point. Default is `'none'` (ProjectDoc v5): re-encoding a saved grade behind the user's back is not acceptable. Note sRGB's linear knee is derived as `0.04045/12.92`, not hard-coded to the published `0.0031308`: the standard's rounded constants make its two segments meet only to ~4.5e-8, and an exactly invertible pair matters when a bake composes them.

**Rejected.** Auto-selecting a transform from the DJI SRT's `color_md` (`telemetry-summary.colorProfile`, already parsed and displayed) — the studio's anti-fabrication convention forbids guessing a clip's colour handling and transforming silently. A hint may *suggest*; the user confirms. Equally, the display gamma a vendor baked into a "log → Rec.709" LUT is **not readable from the file** (most target ~2.4, not all), so this is a switch judged by eye, never a hardcoded constant. And gamma is **not sharpness**: it is tonal, not spatial — it only reads as "crisper" because perceived sharpness rises with local contrast.

## Tetrahedral LUT interpolation, and why it is the default (2026-08-21)

**Decision.** `shared/lut/interpolate.ts` (pure, tested) holds both lattice lookups; the shader in `lut-gl.ts` holds the same two, and `composeLutStack`'s third argument picks the one the CPU bake uses. Tetrahedral is the **default** everywhere — in `lut-gl.ts`'s module-level `defaultInterpolation` and in `useLutInterpolation`'s stored default, deliberately the same value so the app renders identically whichever tool is opened first. **Why**: trilinear averages all 8 corners of the enclosing cell, including the two on the far diagonal, so on a neutral (r=g=b) it mixes in corners where r≠g≠b and a channel-asymmetric look **tints greys that the LUT itself leaves neutral**. Measured on the shipped cubes, worst grey tint: **Apple Log→709 2.59 codes trilinear vs 0.01 tetrahedral; DJI D-Log M 0.67 vs 0.05**. Off the neutral axis the two methods diverge by up to **5 codes (DJI, Apple) and 29 codes (Sony S-Log3)** — this is not a subtle change in saturated colour. Sony's cube tints greys by 1.82 codes under *both*, because that tint is in the data, not the interpolation: tetrahedral guarantees not to **add** a cast, not to remove one.

**How to apply.** All six tetrahedra share the c000→c111 edge, so on the neutral axis every branch collapses to `c000 + (c111 - c000) * f` — that identity is the point and `interpolate.test.ts` pins it. The mode MUST be used by both the bake and the shader or preview and export diverge. `texelFetch` **ignores sampler filter state**, so both shader paths share one texture: the mode is a live uniform switch with no re-upload — do not "helpfully" switch the texture to `NEAREST`. (The cube texture is float, or half-float where the GPU cannot filter float; the 8-bit fallback is gone since 2026-09-20 — `render-core.md`.) The preference is `localStorage` (`atelier.lut.interpolation`), **not** `ProjectDoc`: it changes how faithfully an existing grade is read, not what the grade is, so it needs no document migration — this is a different question from the output transform, whose default is off precisely because it *does* change the look. Export paths build a throwaway renderer per job and read the module default rather than threading a mode through eight call sites (several already eight positional arguments deep); only long-lived preview renderers take it explicitly.

**Verified against real GL, not just unit tests.** The GLSL and the TypeScript are two implementations of one formula, and no CI test can compare them — vitest runs in node. They were checked once by extracting `VERT_SRC`/`FRAG_SRC` from `lut-gl.ts`, running them in headless Chromium (`/opt/pw-browsers/chromium`, `--use-angle=swiftshader`) against a known asymmetric cube, and comparing the readback to `sampleTetrahedral`: **worst 0.47 of an 8-bit code**, i.e. rounding only, with grey spread 0.00 (tetrahedral) vs 8.00 (trilinear). Redo that if either implementation is touched. Trap found doing it: the GPU writes an 8-bit framebuffer so LUT values outside [0,1] are clamped on write while the pure module does not clamp — compare against a clamped expectation or the check fails for the wrong reason.

## Exports already carry a `colr` colour tag — do not "add" one (2026-08-21)

**Fact, measured, not inferred.** Our MP4s are correctly colour-tagged today and nothing needs building. The chain, verified end to end: (1) Chrome's `VideoEncoder`, fed a canvas-sourced `VideoFrame`, populates `metadata.decoderConfig.colorSpace` with **primaries `bt709`, transfer `bt709`, matrix `bt709`, `fullRange: false`** — measured in headless Chromium 141 on VP8, VP9 and AV1; (2) both muxer sites forward that metadata verbatim (`webcodecs-export.ts` `output: (chunk, meta) => muxer.addVideoChunk(chunk, meta)`, and the same line in `overlay/export-overlay-seek.ts`); (3) mp4-muxer 5.2.2 writes a `colr` nclx box **iff** `decoderConfig.colorSpace` is present — verified in node by muxing with and without it: absent → no box, present → `type=nclx, primaries=1, transfer=1, matrix=1, fullRangeFlag=0`. **Why this is worth recording**: nothing in `src/` mentions colour metadata, so the pipeline *looks* untagged and invites a "fix" that would at best duplicate the library and at worst mis-tag. **How to re-verify**: log `meta.decoderConfig?.colorSpace` in the encoder's `output` callback, and parse an export with mp4box.js (already a dependency — it parses `colr` into `colour_primaries` / `transfer_characteristics` / `matrix_coefficients` / `full_range_flag`, though note it exposes them on the *sample entry*, not on `getInfo()`'s track object, and `hev1` puts them in a `colrs` array).

**Still unconfirmed**: H.264 specifically. This container's headless Chromium has no H.264 encoder, so the measurement used VP8/VP9/AV1. Chrome's RGB→YUV conversion sits in a shared frame-conversion layer ahead of the codec, so H.264 is expected to match — confirm on a real machine before relying on it.

**Note the relabel**: the canvas-sourced frame reports transfer `iec61966-2-1` (sRGB) and `fullRange: true`, and the encoded output reports transfer `bt709`, `fullRange: false`. Chrome converts the range but **relabels** the transfer rather than resampling the curve. That is the usual industry approximation, and it is exactly why the output transform keeps "→ sRGB" and "→ 2.2" as separate user choices rather than pretending one is the other.

**The hazard, now guarded.** mp4-muxer's lookup maps cover only `bt709`/`bt470bg`/`smpte170m` (primaries), `bt709`/`smpte170m`/`iec61966-2-1` (transfer), `rgb`/`bt709`/`bt470bg`/`smpte170m` (matrix), with **no bounds check**: an unmapped value becomes `u16(undefined)` → writes **0**, and for matrix 0 means Identity/RGB — an actively wrong claim, worse than none. `media/colour-tag.ts` (`safeChunkMetadata`) sits at both `addVideoChunk` sites and is **all-or-nothing**: unless primaries, transfer AND matrix are all present and encodable and `fullRange` is a real boolean, it strips `colorSpace` so no box is written. **The partial case is the reason it is all-or-nothing**, and the easy thing to get wrong: `{primaries:'bt709'}` alone still writes matrix=0, and a missing `fullRange` still writes 0 = limited, which is a guess — and guessing range wrong is a visible contrast error. It must never mutate its argument: the object is the browser's, and mp4-muxer `Object.assign`s it into state kept until `finalize()`. `colour-tag.mux.test.ts` drives the real muxer to prove the guard does not cost us the tag we already have — a pure unit test cannot see that failure mode. Note TypeScript cannot express the dangerous values at all (`pq`, `hlg`, `bt2020` are outside WebCodecs' enums), which is precisely why the check has to exist at runtime.

## HDR is not handled, and is out of reach in a browser (2026-08-21)

**Fact.** There is no HDR support at any stage, and the pipeline is 8-bit SDR **by construction**: `pickAvcCodec` probes only `avc1.64…`/`4D…`/`42E0…` (8-bit H.264 profiles — High 10 would be `avc1.6E…`); every canvas is default `srgb` 8-bit and the WebGL video texture uploads as `UNSIGNED_BYTE`; `transcode.ts` forces `-pix_fmt yuv420p`; WebCodecs' own `VideoTransferCharacteristics` enum has **no PQ and no HLG** (`bt709 | iec61966-2-1 | smpte170m`); mp4-muxer's maps have no bt2020 either; and `shared/lut/transfer.ts` is SDR-only by design. A grep for `hdr|bt2020|pq|hlg|smpte2084|10-bit|High10` over `src/` returns nothing.

**What happens today to HLG footage** (the Mini 4 Pro offers HLG beside D-Log M): it is not refused, it is **silently flattened to SDR** — the browser decodes and converts into the canvas's sRGB space, the LUT runs on whatever came out, and the result is re-encoded 8-bit and tagged bt709. Whether Chrome tone-maps on that decode is **unverified**; do not claim either way without measuring.

**Decision (maintainer, 2026-08-21): not doing it.** Real HDR would need 10-bit or float decode, escaping the 8-bit canvas bottleneck, a genuine PQ/HLG→SDR tone-mapping operator, and a High 10 encode that WebCodecs supports poorly — not a reasonable ask for a local-first browser tool.

**Amended 2026-09-17 — that ruling is about VIDEO, and it stands for video; for STILLS it is reversed.** Every argument above names a video constraint: `pickAvcCodec`'s 8-bit profiles, WebCodecs' transfer enum, mp4-muxer's maps, the High 10 encode. A photograph needs none of them — only float render targets (`EXT_color_buffer_half_float`, present) and a gain-map container (JPEG segments, writable by hand). So the photo editor carries headroom end to end and delivers **Ultra HDR JPEG** (an SDR base plus a gain map in an MPF container), while no video path gains PQ, HLG or a 10-bit encode and the HLG *notice* remains the only thing open here. **How to apply**: do not cite this entry to refuse HDR on a still, and do not cite the reversal to re-open HDR video. The brief is `docs/photo-editor.md` §4.4. **What is cheap and in keeping**: *detect and say so* rather than flatten in silence. `telemetry-summary.colorProfile` already carries the SRT's `color_md`, so an honest "this clip is HLG; the studio works in SDR" notice follows the same convention as the battery gauge drawing "—" instead of inventing a level. Not built yet — see the open item in `MEMORY.md`.

## Nothing in CI can see a broken shader — run `scripts/check-shader.mjs` (2026-08-21)

**Trap, and the remedy.** `typecheck`, `lint`, `test` and `build` are all blind to the GLSL: it is a template literal, vitest runs in node and never compiles it, and a compile failure **degrades silently** — `createLutRenderer` returns null, `makeFrameGrader` falls back to pass-through, and exports come out **un-graded with every gate green**. Two real bugs were caught this way that all four gates missed: a **backtick inside a GLSL comment terminates the template literal**, and **`flat` is a reserved interpolation qualifier** in GLSL ES 3.00 and cannot name a variable. **How to apply**: after any change to `lut-gl.ts`, run `npm i --no-save --no-package-lock playwright` once, then `node scripts/check-shader.mjs`. It compiles the real shader on a real WebGL2 context (SwiftShader is fine — this checks correctness, not speed), runs it against the pure module through Vite's `ssrLoadModule` so the `.ts` stays the single source of truth, and fails if they disagree by more than ~1.5 of an 8-bit code. Judge agreement in code values and clamp the expectation to [0,1]: the framebuffer is 8-bit and clamps on write while the pure module does not, so an unclamped comparison fails for the wrong reason.

## The shader honours the cube's input domain (2026-08-21)

**Decision.** `lut-gl.ts` takes `u_domainMin`/`u_domainMax` (uploaded from the `CubeLut` in `uploadLut`) and both lookups start from one `normalizeDomain()` helper that mirrors `latticeCoords` in `interpolate.ts`, span==0 rule included. **Why**: the shader used to hard-code `clamp(rgb, 0, 1)` while `sampleLut` honoured `DOMAIN_MIN`/`DOMAIN_MAX`, so a user-uploaded cube with a non-unit domain rendered *one way* at full strength — where `composeLutStack` returns the source cube untouched — and *another* the moment a slider moved or a second layer appeared, because the bake got it right. Same LUT, two looks, depending on whether a slider was touched. **How to apply**: the domain step composes **before** the texel-centre mapping (`scale = (N-1)/N`, `offset = 0.5/N`); swapping that order is the one way to get it subtly wrong. For the default [0,1] it reduces exactly to the old clamp, so no shipped look changes — none of the 19 cubes declares a domain, which is why this was latent. Verified on a real GPU across four domains (default, non-unit, per-channel asymmetric, degenerate zero-span): agreement within 0.5 of a code on both interpolation paths.

## A develop is the FIRST stage of the one cube (2026-09-13)

**Decision (the maintainer's, from `docs/photo-develop.md`; P1 built).** A picture's correction — exposure, brightness, contrast, highlights/shadows/whites/blacks, temperature/tint, saturation, vibrance — is a `DevelopSettings` record (`shared/develop/develop.ts`, pure, 28 specs) and it is applied as the fourth argument of `composeLutStack`: the first lattice stage, before every layer and before the output transform. Correction → look → delivery, always, the node order of every grading suite. **Why baked, not a shader stage**: the same three reasons as the transform (one `CubeLut` per consumer, node-testable maths, the `mix` at intensity 0), plus the one that decides it — all six renderers get the correction at once and `lut-gl.ts`, the file CI cannot see, is untouched. The decoder for RAW is decided too: `libraw-wasm` (P5/P6, not built).

**How to apply.**
- The maths is `developLinear`, in linear light, UNCLAMPED above 1 so a RAW developer can hand it headroom; `developStage` wraps it for the bake (sRGB codes in and out, clamped). Every luminance move (bands, contrast, brightness) is ONE ratio on Rec.709 luminance, so hue never rotates and a grey stays grey under every slider but temperature/tint — pinned by a spec over every key. The bands work on sRGB-ENCODED luminance (where "highlights" means what a photographer expects), each zero outside its half and at the end the neighbouring band owns: highlights/shadows are bumps peaking at 3/4 and 1/4, whites/blacks ramp to the extreme and are zero at mid-grey. Contrast pivots on 18 % grey, brightness is a gamma (ends fixed). A pixel above white takes white's ratio — that is how "whites −100" reaches a RAW's headroom.
- **An untouched pixel must come back bit-identical**: the sRGB encode/decode pair is not exact to the last ulp, so the ratio is skipped when the curve did not move the value. Without that, "highlights leaves mid-grey untouched" fails on `toEqual` and every "as shot" region of a picture drifts by an ulp per bake.
- The develop bypasses both bake shortcuts and takes the transform's **floor of 33** (its tone curve has the same shape near black). Measured here at 33³, tetrahedral: develop alone 24 ms, develop + transform 39 ms, transform alone 14 ms — the same class as the 28 ms the deferred bake already carries per slider step. The stage is resolved once per bake (`developStage(d)`), never per lattice point.
- `LutStack` carries `develop` / `setDevelop` and TWO cubes: `composed` (with the develop) and `composedForDeveloped` (without it), for a source developed AT DECODE — a RAW, once P6 lands — whose numbers were consumed there; grading it through `composed` would apply the correction twice. With a default develop the two are the same object and one bake: the common case pays nothing for the feature existing.
- `normaliseDevelop` is what a document migration and a file import read a stored develop through (clamped, junk → 0); `describeDevelop` is the one sentence every settled row prints (`+0.7 EV · highlights −40 · vibrance +15`, `As shot`). Storage (Trips v15, `ProjectMedia.develops`), the sheet and the RAW path are P2 onwards in the brief — nothing on screen changes with P1.

## A film stock is a LAYER generated from numbers, never a stage (2026-09-17)

**Decision (the maintainer's, `docs/film-simulation.md`; F1 built).** A film simulation's colour — tone, crossover, coupler rolloff — is a `LutLayer` with `source: 'film'` whose `customText` carries `FilmSettings` as JSON and whose cube is GENERATED by `shared/film/emulsion.ts` (`filmCube`) instead of fetched. **Why a layer and not a fifth `composeLutStack` argument beside the develop**: a conversion LUT must run BEFORE the film response (an emulsion applied to D-Log is nonsense), and only the layer list is ordered by the author — a fixed stage would apply film to log on every drone clip, silently. As a layer it needs no document migration, no bake change, and the strength slider, bypass, the three Trips rungs, the house style and both file formats work as they do for any look.

**How to apply.**
- The maths runs in STOPS from mid grey: sRGB → linear → `log2(v/0.18)`, per-channel softplus toe/shoulder curves (monotone, C∞), a row-stochastic coupling matrix, DIR inhibition (`k = inhibition · spread/(spread+1)`, so a neutral is untouched and a saturated primary rolls off), a paper stage for negatives (hard white at 2.65 stops — what restores the white the negative's shoulder rolled off), dye saturation. **Every curve is re-speeded so mid grey → mid grey exactly** (an input shift solved once by bisection); crossover comes from per-channel curve SHAPE, never from a hidden exposure change.
- **A film stock tints greys on purpose.** `develop.test.ts`'s "a grey stays grey" guarantee is the develop's, not the film's — do not carry that spec across.
- **`FILM_CUBE_SIZE = 33`, measured** (a negative-class stock, tetrahedral against the exact stage): worst error 3.45 codes at 17³, 2.16 at 33³, 1.24 at 49³, 0.91 at 64³ — a smooth shape deviation in the toe, which interpolation cannot band; only 8-bit output bands, and that is grain's job. **Generation is the cost, not composition**: 106 ms at 33³, 344 at 49³, 772 at 64³, against 4 ms to compose the layer at 70 %. So the generated cube MUST be cached by `filmSettingsKey` — the strength drag re-walks the composition and never the emulsion.
- `gradeKey` (`saved-grade.ts`) ignores `customText` because an uploaded cube's text never changes after its id is minted; a film layer's text changes on every dial move, so it must fold `filmSettingsKey` in for `source === 'film'` or two stocks under one id collide in `useGradeCubes`' cache.
- **The layer is wired (F3, 2026-09-17)**: `restoreLayers` takes a `film` branch BEFORE the built-in `else` (an older build drops the layer, never grades it as identity), `useLutStack.addFilm/setFilm` and `toSaved` carry the settings in `customText`, and every path builds the cube through `shared/film/film-layer.ts` so a stock is built one way. `GradePanel` lists the stocks under FILM in the same picker (ids `film:<stock>`, never through `builtin-luts.ts`, whose entries are files) and draws `FilmDials` under a film layer: stock, coupling, rolloff, dye, print + paper grade, and the three curves behind an All / R / G / B picker — a column has no room for eighteen curve sliders and per-channel editing IS the crossover, so the picker is the control, not a hiding place. The layer's NAME says where it stands (`Negative · portrait · adjusted`). Verified in headless Chromium on a canvas-made picture: mid grey 118 → 118, shadows cool and highlights warm under the portrait stock, a red rolled off, the dial departing the stock, the layer back after a reload. `readRollGrade` used to cap a layer's strength at 1 where every other reader allows `MAX_LAYER_INTENSITY` (3) — fixed here; one constant in `lut-stack.ts`, never a literal.
- **Grain and halation are NOT here and must not be retrofitted into `lut-gl.ts`**: they are spatial, they are the photo editor's P4 render core built twice (FBOs, a blur, two programs, seventeen grader call sites, a re-keyed `holdGrades`), and the maintainer chose to make them ONE `FilmNode` in `shared/render/` once it exists. **The pure maths is BUILT (F4′, 2026-09-17)** so the node inherits it, each stock declaring its `texture`: `film-texture.ts` (the record, its reader, `filmTextureKey`, `grainUniforms` / `halationBuffer` with the two one-line proofs of resolution independence — a cell is `grainSize × renderH` at every size, and the blur buffer's height and sigma depend on the RADIUS alone), `film-noise.ts` (a 256² tile of four independent white-noise channels from the suite's one `mulberry32`, now in `shared/lib/prng.ts` and shared with the stagger; a golden-ratio phase per source frame so consecutive frames land cells apart and never crawl), `film-grain.ts` (`grainWeight` — zero at crushed black and blown white, peak near 0.42 —, the CPU twins `applyGrain` / `screenHalation` / `extractHighlight`, `gaussianKernel` and `blurSeparable`, which the shader's passes are compared against by `readPixels`). The three requirements the node must meet are `docs/photo-editor.md` §11 items 5–7; the design is `docs/film-simulation.md` §6. Nothing draws any of it yet.

## The LUT bake is deferred, not debounced (2026-08-21)

**Decision.** `use-lut-stack.ts` wraps the bake's three inputs in `useDeferredValue` rather than debouncing the slider or committing on pointer-release. **Why**: `setIntensity` maps to a new `layers` array, so every drag step re-ran `composeLutStack` synchronously *during render* — measured tetrahedral, per step: 6.6 ms for one look, 28 ms with an output transform, **38 ms for three looks and a transform (~26 fps)**, before React's re-render and the ~575 KB 3D-texture re-upload. Commit-on-release was rejected: it kills the live preview, and watching the image while dialling strength *is* the interaction.

**What it actually buys, measured in a browser against a 30 ms memo — and what it does not.** The control commits **0 ms** after the change instead of **31 ms**: the urgent render skips the memo and the bake follows in a transition. It does **not** reduce the number of bakes (React already batches a burst of synchronous updates into one, with or without it) and it does **not** make the bake cheaper or non-blocking — it reorders the work. On a heavy stack the image still trails the thumb; the next step there is moving the bake off the render path, not stacking a debounce on top.

**Trap in measuring this**, which cost two wrong answers: counting bakes shows no difference, and timing to the next `requestAnimationFrame` shows no difference either — the rAF callback is itself blocked by the bake, so it reports the same number both ways. Instrument the React commit directly (a `useLayoutEffect` keyed on the urgent value) or the effect is invisible.

**That deferral is why the stack cannot be the only baker (2026-09-15).** `useLutStack` is ONE set of parsed layers with one deferred bake — right for the grade under the author's fingers, and unable to answer for any other. A screen that must draw several grades at once (a Trips deck whose pictures each carry their own look, `roadtrip.md`) takes the read-only half instead: `shared/lut/use-grade-cubes.ts` resolves stored grades and bakes one cube per (grade, develop), with no editing, no deferral and no write-back. Both go through ONE layer resolver — `saved-grade.ts` (pure: the stored shape, `gradeKey`, `gradeOrNull`) and `restore-grade.ts` (fetching: `loadBuiltinLut`, promise-cached). **Keep that split**: `builtin-luts.ts` imports the `virtual:luts` Vite module, which does not exist in a node test run, so any document module that reads a stored grade must reach only for the pure half.

## Composer composites on a single canvas, with a snapshotted map (2026-08-20)

**Decision.** The Composer draws the (graded) video and the map's WebGL canvas into computed panes, then the readout, per frame. For export, the map is built once at full resolution, framed to the whole track, rendered and **snapshotted**; each frame draws that snapshot and places the aircraft marker via `map.project()`. **Why**: the per-frame draw in the export pipeline is synchronous, so MapLibre cannot be re-rendered per frame. **How to apply**: the compositing map needs `preserveDrawingBuffer` (otherwise its canvas cannot be `drawImage`d) and the marker must be a GL layer — a DOM marker is not captured. Panes are drawn with a cover-fit rect so a resize never stretches the map.

## The overlays run on the SOURCE clock unless a caller asks for the delivered one (2026-09-13)

**Decision.** `VariantRenderOptions.overlayClock: 'source' | 'delivered'` (default `source`). On `source` — the Studio — `drawOverlays` gets the source timestamp and the trim's in point as `originSeconds`, so cues, the capture clock and the heading smoothing index the source timeline and a re-timed variant plays its intro at the re-timed pace (that IS the Studio's re-time). On `delivered` — Road Trip's hook and content clips — it gets `(t − trim.start) / speed` from an origin of 0: a badge composed to slide in over 0.6s slides in over 0.6s of the viewer's time whatever speed the clip plays at, which is what the stage previews. **Only for a caller with no cues**: a source-indexed readout under a delivered clock would read the wrong frame's value. **How to apply**: never flip the default; a new caller that burns animations over a re-timed clip and reads no telemetry passes `'delivered'`, one that reads telemetry stays on `'source'`.

## `exportVariantVideo` has one hook for painting between picture and overlays (2026-08-24, rev. 2026-09-13)

`VariantRenderOptions.paintUnderOverlays?(ctx, w, h, t)` runs once per frame, after the cover-crop and before `drawOverlays`; `t` is seconds since the first EXPORTED frame, **on `overlayClock`** — the trim's in point is zero either way, and under `'delivered'` it is additionally divided by `speed`. Added for Road Trip's scrim and vignette; since 2026-09-13 it is also where a hook VARIANT paints (the scrub's tape and flashes), which is why it now carries the clock — the earlier "nothing with its own timing goes through here" rule was superseded by the hook engine, whose variants are a declared, tested timing model rather than an unknown callback (`docs/hook-engine.md`). Its sibling `elementsAt?(t)` swaps in overlays whose TEXT changes as the clip plays, on the SAME `t`. **Both are deliberately kept on one clock with `drawOverlays`' own `timeSeconds`**: a hook can now be re-timed (a slide's speed), and a hook variant's drawing has to keep pace with the badge's entrance under that re-time or the scrub's tape and the numeral it steps would desync from the words around them. The Studio sets neither `paintUnderOverlays` nor `elementsAt`. The ctx is `CanvasRenderingContext2D | OffscreenCanvasRenderingContext2D` — anything drawing through it must be typed for both.

## Audio the suite MAKES is encoded; a bed is rendered ahead of the AAC priming (2026-09-13)

**Decision.** The copy-only rule stands for footage by default (see the next entry for when a clip's sound is re-encoded: only on request). Audio the suite synthesises — a hook's tick bed — is rendered offline (`shared/audio/render-bed.ts`), encoded to AAC-LC in full BEFORE the muxer is built (`shared/media/audio-encode.ts`), and handed to `encodeFrames` as `audio`; a browser that cannot encode it gets a clip with NO audio track and a sentence (`onAudioSkipped`), never a half-declared track and never a failed export.

**The trap, measured on Chrome/macOS by rendering ticks at known times, muxing, and decoding the MP4 back:** the AAC encoder stamps its first packet 0 and carries **2112 samples of priming** inside it, and mp4-muxer writes **no edit list**. Every tick decoded 44ms after its frame. Two fixes do NOT work and must not be re-proposed: stamping the audio packets early (`addAudioChunk` throws on a negative timestamp), and stamping the video frames late (without an edit list a track's start offset is simply lost — mp4box showed both tracks starting at 0 and the drift unchanged). **What works**: `renderBed(score, seconds, { leadSeconds: aacPrimingSeconds(48000) })` schedules every sound that much early — measured drift 0.0ms on every tick, ≤0.3ms through the full `exportHookStillVideo` path. The one cost: a sound in the first 44ms cannot move before zero and lands up to 44ms late (on the scrub, only its opening tick). An encoder priming by 1024 would leave ticks ~21ms early. **How to apply**: any future audio the suite renders goes through the same lead, and a claim that it is "in sync" is only made after the same decode round trip — no unit test can see this.

**The voices are seeded.** The ported `clickSynth` noise used `Math.random()`; `voices.ts` seeds each hit from its time, so the same piece exports the same bed.

## A clip export decides its audio BEFORE the muxer exists: copy, bed, or mix (2026-09-13)

**Decision.** `exportProcessedVideo` takes an optional `bed` (a factory asked for audio in the format the pipeline needs) and `mixBed`, and `audio-plan.ts` (pure, tested) picks one of four outcomes before the muxer is built — its audio track is fixed at construction. **`copy` stays the default whenever a clip has sound**: re-encoding someone's recording is never done behind their back, and a bed left out says so (`onAudioSkipped`). **`bed`** becomes the track when there is no clip sound to keep — a clip recorded without a microphone (most drone footage: this is the COMMON case for the maintainer, and it needs no decoding at all) or a re-timed export. **`mix`** only on request: the clip's AAC packets overlapping the window are decoded with `AudioDecoder` straight from the demux's samples (nothing re-reads the file), laid out by their timestamps, the bed summed in at the clip's own rate and layout (`mixPlanar`, clamped, channels folded sensibly), and encoded once. Any step that cannot be done falls back to `copy` with a sentence — never a failed export, never a declared-but-broken track.

**Measured by decoding the MP4s back** (a clip made with a beep at 0.5s, and a silent one): silent clip → the tick at exactly 1.000s; mix off → the clip's beep untouched at 0.5025s and the ticks reported left out; mix on → beep 0.5026s and tick 1.000s. **On a TRIMMED clip the mix is more precise than the copy**: the copy's beep landed at 0.7132s where 0.7025s was expected — `copyAudio` cuts on an AAC frame boundary (its documented ~21ms) — while the mix, placed by decoded timestamp, landed at 0.7026s. **The encoder's flush emits tail padding** stamped past the signal; kept, the made track ran ~75ms longer than the picture and so did the file. `encodeAudioBuffer` drops packets stamped at or past the end; the track now ends within one AAC frame of the video.

## A LUT picker shows the look before it's picked (2026-09-18)

**Decision.** `LutGalleryModal.tsx` (+ `LutThumb.tsx`, `lut-preview.ts`) is a grid-of-thumbnails picker over `BUILTIN_LUTS`/`LUT_GROUPS` (and, from `GradePanel`, the film stocks), wired in from both legacy `LutPicker` and `GradePanel`'s "Add a look" as a "Browse looks" icon button beside the existing `<select>` — the select stays, for a quick known-name pick. Every tile bakes the look onto a shared sample bitmap and draws it live; clicking a tile IS the pick, nothing to confirm, because seeing it first was the point.

**Every list of looks is grouped the same way, with native `<optgroup>`s (2026-09-19, the maintainer's ask).** `GradePanel`'s "Add a look" select used to flatten the families into one list whose group was a prefix on every line (`DJI · …`); it now draws `FILM`, the root looks, then one optgroup per folder — the order the gallery's sections and `LutPicker` use — through `NativeSelect`, since `SelectField` takes flat options only. **How to apply**: a new family of looks (a purchased pack, say) is a new optgroup in every select AND a section in the gallery, never a label prefix. Native optgroups do not nest: a second level (author → category) has to be flattened into the group's label.

**Baking is CPU, not GPU** (`bakeLutPreview` in `lut-preview.ts`, pure/DOM-free, tested): a plain per-pixel `sampleWith` loop over a small (96×96) `Uint8ClampedArray`, never `makeFrameGrader`/`createLutRenderer`. A gallery of ~30 looks would mean 30 throwaway WebGL2 contexts — exactly the churn `frame-grader.ts`'s own `dispose()` note warns against — for a thumbnail size where the GPU buys nothing. Intensity blends exactly like the shader's `mix(original, graded, intensity)` so a thumbnail reads the same as the real grade.

**Loading never blocks a frame.** Every item resolves one at a time with a tick (`setTimeout(0)`) between each: a built-in fetch+parse is cheap, but a film stock's cube is ~106ms of real CPU (`filmCubeFor`, see the film-layer entry above), and a screenful of them as one synchronous burst would freeze the modal. Both loaders are the SAME caches the rest of the app already uses — `restore-grade.ts`'s `loadBuiltinLut` (promise-cached) and `film-layer.ts`'s `filmCubeFor` (settings-cached) — so a look already loaded elsewhere in the session, or by a previous open of the gallery, comes back instantly and nothing is fetched twice.

**The sample image, in priority order**: a picture already open in the host tool (`GradePanel`'s new `previewImage` prop — `StudioEditor` passes its decoded `photo`), else one the author loads right in the modal ("Preview on a photo…", via `decodePhoto`), else a procedural test chart (`syntheticPreviewSample`: sky gradient, neutral grey ramp, saturated bars, a skin-tone and a foliage patch — deliberately NOT a shipped photo asset, since the repo ships no raster sample and generating one at runtime needs no new binary to keep in sync). **No CLI/script was added to bake previews from a photo on disk** — the in-modal "Preview on a photo…" picker already does exactly that, live, for any image the author has; a second, offline way to do the same thing would be speculative surface for no asked-for use case. `LutPicker`'s three legacy consumers (LUT Studio, Overlay Studio, Composer) don't pass a `previewImage` yet — they're video tools with no decoded still readily at hand, so the gallery there always starts on the synthetic chart or a loaded photo, never the active clip's frame; grabbing one is a deferred follow-up, not started.

## Curves and levels ride the same stage, and the develop record stopped being flat (2026-09-17)

**Decision (P1 of `docs/photo-editor.md`).** `shared/develop/curves.ts` (pure, 23 specs) adds the two controls eleven sliders cannot express — one part of the range moved while the rest stays — as two OPTIONAL fields on `DevelopSettings` (`curves`, `levels`), applied inside `developLinear` and so inside the one baked cube. **Why inside the record rather than beside it**: every host already stores, clones, presets, copies and batch-applies a develop, so a field costs no host code at all — Trips' slides, `ProjectMedia.develops` and a roll's pictures carried it the day it existed, with no migration (absent reads as null). Both work on **encoded** sRGB values, where "the three-quarter tone" means what a photographer points at.

**How to apply.**

- **Five curves, Capture One's own, and the difference between them is the feature**: `luma` is applied as ONE RATIO on luminance, so a grey stays grey — the guarantee every other tonal control in `develop.ts` keeps; `rgb` runs all three channels through the same map DIRECTLY, which does move saturation and is what that control is for; `red`/`green`/`blue` tint on purpose. Specs pin all three, including that the rgb curve saturates a colour while the luma curve leaves its saturation alone.
- **The order is fixed**: levels (master, then the channel) → curves (master, then the channel), after the sliders' tone curve and before saturation. Two documents must never disagree about what a number means.
- **Monotone cubic (Fritsch–Carlson), and the tangent clamp is load-bearing** — a natural or Catmull-Rom spline overshoots between control points and can run BACKWARDS, which on a tone curve reads as banding and inverted tones, i.e. as a broken tool. Do not remove it as "smoothing".
- **A curve is DISPLAY-REFERRED**: drawn on [0,1], so a RAW's headroom is read at white. Where the map leaves that value alone the linear value is handed back UNTOUCHED, so headroom survives a curve that does not reach it — and an unshaped pixel stays bit-identical, the encode/decode pair not being exact to the last ulp. The tone bands' own trick, for the same reason.
- **Resolve once** (`makeDevelopShapers`, passed into `developLinear`; `developStage` does it): the bake calls it tens of thousands of times — the `makeTransfer` rule.
- **The record is no longer flat numbers, and two habits had to change.** `{ ...settings }` now SHARES a point list, so a preset and the picture it was saved from would hold the same one and an editor moving a point would move both — the clipboard, `savePresetIn` and any keeper clone through `cloneDevelop`. And a key-by-key `===` calls two structurally identical curves different, so equality is `sameDevelop` (engine-level, re-exported by `roll-editor.ts` where it used to live) and compares shapes by value. `DevelopKey` now EXCLUDES them: they are not sliders, and a panel must not try to draw one.
- **The 33 floor stays, measured rather than assumed.** Worst error against the exact stage, in 8-bit codes, at 33³ / 49³ / 64³: a gentle S on luma 2.63 / 1.70 / 1.36, the same on rgb 0.13 / 0.06 / 0.03, a hard S on rgb 0.53 / 0.24 / 0.15, lifted blacks and a red cast under 0.06 throughout — the luma path is the worst because it is a ratio, and all of it is at or under the quantisation step for a ~40 ms bake against ~250 ms at 64³. A near-vertical cliff costs 10.7 codes at 33³ and STILL 3.2 at 64³, so the lattice is not its remedy and raising the floor would buy visible banding at the price of the freeze this file already forbids. **A curve steeper than roughly 1:10 is an approximation until the render core evaluates it per pixel** (`docs/photo-editor.md` P4, which retires this error class). The numbers live beside the spec that pins them in `lut-stack.test.ts`.
