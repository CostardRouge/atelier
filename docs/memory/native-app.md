# The native app (`apple/`) — decisions, reasons, traps

Read before touching anything under `apple/`: the Swift kernel
(`apple/Packages/AtelierKit`), the SwiftUI app (`apple/Atelier`), the Xcode
spec (`apple/project.yml`) or the Apple CI (`.github/workflows/apple.yml`).
The run-sheet — what is built, what comes next, in commits — is
`apple/README.md`; the briefs are `docs/native-app.md` and
`docs/native-stack.md`. This file holds only what neither the code nor the
run-sheet says.

## The shape

- 2026-09-23 — **Swift + SwiftUI, one source tree for iPhone, iPad and Mac** — the maintainer's call after the stack brief (*"create a native swift app for me: compatible both on iphone and macOS, feature parity and native ui design"*). Two application targets over the same `apple/Atelier/` files, `#if os(...)` where a platform differs (a tab bar on iOS, a sidebar on the Mac; `horizontalSizeClass` exists only on iOS). Not a wrapper, no web view: the kernel is PORTED, not bridged, and the pixel path is Core Image. **How to apply**: a screen is written once; anything platform-specific is a small `#if`, never a second view.
- 2026-09-23 — **The Xcode project is generated, never committed.** `apple/project.yml` (XcodeGen) is the source; `Atelier.xcodeproj` is gitignored like `dist/`. Two hand-edited pbxproj files never merge; a spec does. `brew install xcodegen && xcodegen generate` is the whole setup. Info.plists are generated from the spec too (`Support/Info-*.plist`, gitignored); the macOS entitlements are a real file (`Support/Atelier-macOS.entitlements`, sandboxed with user-selected files, app-scoped bookmarks and the Photos library) and the iOS target has none.
- 2026-09-23 — **The kernel is a SwiftPM package with no Apple framework** (`AtelierKit`: Foundation only), so it builds and tests on Linux — the platform this project is written from, where no Xcode exists. Every web module it ports has its specs ported beside it (Jest's `toBeCloseTo(x, digits)` is `assertClose(_, _, digits)` with the same tolerance, `10^−digits / 2`). **How to apply**: new logic goes in the package with a `.test` twin, never in a view; a view holds only what a browser could not do.
- 2026-09-28 — **What is native, when he asks** (he did, after the first green build, suspecting the galleries were web pages): NOTHING is web — no `WebKit`, `WKWebView`, `JavaScriptCore` or HTML anywhere in `apple/` (grep it before answering again); the screens look like the site because they wear its tokens. The HEAVY paths are the platform's: Core Image on a Metal `CIContext` with the web's shaders as `.metal` kernels, `CIRAWFilter` for RAW, `AVAssetReader` → Core Image → `AVAssetWriter` (H.264/HEVC on the hardware codec) for video, Vision for the subject, ImageIO for stills, MapKit. On the CPU BY DESIGN: the kernel's arithmetic and the overlays painted with Core Graphics into a raster Core Image then composites. His rule: a light screen may look like the web, an export or an encode must be native and use the phone's hardware — so what an export still lacked (it stopped with the app, and said nothing on the Lock Screen) is the work that follows. **HDR video** (10-bit HEVC keeping HLG/PQ; today a HLG/PQ source is converted to Rec.709, `Video/VideoSource.swift`) is within reach natively and DEFERRED by him (*« plus tard »*, 2026-09-28) until the first run on his iPhone; the web's SDR ruling stays the web's.
- 2026-09-28 — **An export keeps running when he leaves the app, through ONE line**: `BackgroundRun.keep(handle)` right after the export's `TaskCenter.start` (Develop's run, the Studio's, Trips', the Composer's, the LUT studio's — `Tasks/BackgroundRun.swift`), which holds, while any kept task runs: on iOS 26 a `BGContinuedProcessingTask` submitted while on screen (`.fail`, the GPU asked for where `supportedResources` has it, retried without), the system drawing its own progress UI; on iOS 17–25 (or a refused request) `beginBackgroundTask`, about 30 s; on the Mac `beginActivity(.userInitiated)`, no App Nap. Every expiry cancels the kept tasks through their OWN Cancel, so what was done is kept. The Live Activity (`Widgets/`, attributes in `Shared/ExportActivity.swift`, a 20 s keep-alive because an activity goes stale after 60 s without an update) STANDS DOWN beside iOS 26's system UI (`activityBesideSystemUI`) — two bars for one export is noise. **The open risk, first thing to measure on the phone**: whether Core Image's Metal work and `AVAssetWriter` answer in the background WITHOUT the GPU grant; if not, a kept export fails there instead of finishing. The GPU entitlement (`com.apple.developer.background-tasks.continued-processing.gpu`, as remembered) is deliberately NOT declared, since an unknown entitlement can block signing on the first device run: add it once a device says it is the one. The task list knows that an export ended, not whether it succeeded, so a finished activity says Finished either way.

- 2026-09-28 — **Screens built in parallel meet at CONTRACT files** — a host calls a view by a name and initialiser fixed BEFORE the work starts, held by a stand-in in one `Pending*.swift` file (Develop's inspector, the Trips screens, the piece editor's tabs, the openers): one block per owning task, the owner defines the real view under the same name and deletes only its block, the last one deletes the file; the stand-in always SAYS what is coming. Shared state crosses the same way (`TripSelection`), and a seam found missing mid-way is an environment action the host injects (`adjustLegOnCalendar`, `chooseOpenerPictures`), never a second implementation. **How to apply**: before splitting a screen across tasks, write the contract file and commit it; the merge conflicts that remain are then the stand-in blocks themselves.

## Documents

- 2026-09-23 — **A roll made here IS the web app's `RollDoc`** (v6), written as the same JSON under `Application Support/Atelier/rolls/<id>.json`, so it opens in the browser and on a Winnow unchanged. Every reader takes a `JSONValue` — the enum that stands in for the web's `unknown` — and clamps, falls back and leaves junk behind exactly as `normaliseDevelop` / `readRollDoc` do on the web; it never decodes a document strictly. **The trap this exists for**: a field this port does not yet interpret (on a picture: border, keystone, lens, its profile, detail, vignette, repair, layers; on a develop: rawWb alone since 2026-09-25, when the mixer, mono and grading became typed accessors over the same `carried` keys and render inside `developLinear` in the web's order; on the export: metadata, watermark) is CARRIED through untouched in a `carried` dictionary and written back verbatim — a roll edited on the phone must never lose what the web app wrote. A carried stage is never DEFAULT (a picture holding one is edited, `pictureEdits`), and the stage SAYS which stages it is not rendering. A lens profile taken off (`lensProfile: null`) stays a null: the web tells it from "never decided" (absent). The web's own "nothing" spellings — `null` for the five records, `[]` for the two lists — are not carried, so reading a roll back is the identity.
- 2026-09-23 — **The writer diffs cleanly against the web's**: whole numbers are written as integers (`1`, not `1.0`), keys are sorted, and a slash is never escaped (`.withoutEscapingSlashes` — Foundation writes `\/` by default, which the web never does). `DevelopSettings` encodes through its own `json` (the sliders, the five shapes, the material, nulls where the web writes nulls), never through synthesized Codable, or `encodeIfPresent` would drop the nulls.
- 2026-09-23 — **Where a picture's BYTES are is a side table beside the roll, never in it** (`<id>.locators.json`): a Photos pick has no persistent handle without library permission, so its bytes are COPIED into the app's container (`media/`); a file picked in Files or the Finder is remembered by a security-scoped bookmark and never copied. The web keeps the same thing in IndexedDB (a folder handle) and on a ref (`assetId`). `partial-hash.ts` is ported (`Lib/PartialHash.swift`, Winnow's `content_hash`, pinned by the web's fixtures) and the Library hashes each file it adds; a roll's picture added before that still matches by name and size — never write a different hash under the same key, or `sameMediaRef` misleads across clients.

## Pixels

- 2026-09-23 — **Preview = export by construction, through the kernel's own bake**: the develop is composed by `composeLutStack` into ONE cube and handed to `CIColorCubeWithColorSpace` on sRGB codes (the filter converts around the lookup), so the stage and the export take the web's numbers through the same function (`PictureRenderer.compose`, one recipe for both). The stage works to a pixel budget (long edge 2560, `device-memory.md`'s rule); the export renders whole. The cube is now sampled TETRAHEDRALLY by a Metal kernel of our own (`CubePass`), held to `sampleTetrahedral` by the render gate — `CIColorCubeWithColorSpace`'s trilinear lookup was the one measured gap of v0 and is gone.
- 2026-09-23 — **The framing transform runs in Core Image's y-UP coordinates**: the web's clockwise angle becomes `-t.angle` and its downward pan `-t.panY`; the mirrors are the same scale by −1. The crop is `deliveredSize` (the largest box of the aspect inside the picture) + `framingTransform` — the web's own cover-fit, so a straighten zooms to cover exactly as there. Unverified on a device: only reasoned, not measured, against a rotated picture.
- 2026-09-23 — **A RAW is developed by `CIRAWFilter`, not LibRaw**: Apple's demosaic with its own defaults, so a web develop's `base: gain` + `rawGain` does not mean the same pixels here yet — the web measures its own gain on LibRaw's linear output. Recorded, unmeasured; the sensor path is run-sheet #6/#10.
- 2026-09-23 — **A delivered file carries the ORIGINAL's metadata the way the web's `stamp-exif` does**: ImageIO's `{TIFF}`, `{Exif}`, `{GPS}` dictionaries copied from the source through `CGImageDestination`, orientation reset to 1 (the pixels are upright now), the pixel dimensions told the truth, `Software: Atelier` — and the name is EXACTLY the picture's (`DJI_0101.JPG` → `DJI_0101.jpg`), `develop-roll.md`'s rule.

- 2026-09-26 — **The render gate runs on CI's macOS runner WITH a Metal device** (`AtelierTests`, run by `xcodebuild test -scheme Atelier-macOS`: 27 tests on the first run, the tetrahedral cube kernel held to `sampleTetrahedral`), so a Core Image kernel is compiled AND measured on every push touching `apple/`. Two traps it paid for: a `coreimage::sampler`'s `sample()` takes SAMPLER-space coordinates, never pixels (`s.sample(s.transform(p))`), and Metal's `mix()` is undefined outside [0, 1] while the web's strength goes to 1.5 — the blend is written out. **How to apply**: every pass is a Metal kernel + a gate test against its AtelierKit twin, never a second Swift re-implementation.
- 2026-09-26 — **Colour management is OFF in the render context** (working and output colour space `NSNull`, RGBAh): kernels see sRGB-ENCODED codes with headroom, as the web's float16 buffers do, so every ported formula applies unchanged. Its cost, recorded rather than hidden: a Display P3 picture (every iPhone photo) is read as sRGB codes and looks slightly flatter than a colour-managed viewer shows it — the web does the same in Chrome; the cheap native cure is a P3→sRGB conversion at decode, not in the graph. A RAW's `CIRAWFilter` linear output is encoded with `CILinearToSRGBToneCurve` at decode — reasoned, not measured. Video frames are labelled sRGB on the way in and bt709 on the way out, so codes pass through as Chrome passes them.
- 2026-09-26 — **A Core Graphics shadow offset is turned by the CTM's FLIP, not by its scale** — measured on CI's macOS 26 runner: in a bitmap context whose CTM is flipped to a y-down frame, `setShadow(offset: (0, -30))` (what "30 px down" is in a y-up device space) dropped the shadow 30 px UP the frame, in three canvas specs and the legibility halo at once. `PaintCanvas.deviceShadow` hands CG the device offset with its y turned back when the current CTM's determinant is negative, and the blur trick goes through it too. **How to apply**: never call `cg.setShadow` outside `PaintCanvas`; a new shadow is a canvas state, and its direction is a spec in `PaintCanvasTests`, since only the macOS job can see it.
- 2026-09-26 — **The built-in LUTs are BUNDLED, whole, as FOLDER references to the web's own `public/`** (`luts/` 37 MB, `lut-thumbs/`, `reference/`; `project.yml`, both targets) — the coordinator's call for parity, since the site ships all of them: never a copy under `apple/`, so a `.cube` added to `public/luts/` reaches the app with no code change, and ids are derived by the kernel's `lutManifest` from the same relative paths as the web's (`builtin:<id>` resolves identically). The web's `public/geo/cities.json` is bundled the same way for the offline place name.
- 2026-09-26 — **ONE vault per device** (`Look/SharedVault.swift`, over `FilePackStore` in `Application Support/Atelier/looks/`), read by the pickers (`LookLibrary`, main actor) AND the render plan (`DevelopLooks`, synchronous, resolving pack lattices ahead in `prepare`). Two agents had each built a store and a `ResolvedLook`: two vaults over one folder keep two caches and two listener lists, so a pack imported in the gallery would not reach the stage. `LookLibrary.reloadPacks` tells `DevelopLooks` to forget its misses. **How to apply**: a new reader of looks takes `SharedVault.vault`, never `PackVault(store:)`, outside previews and specs.
- 2026-09-26 — **A RAW is OPENED on the camera's render inside it and DEVELOPED from the sensor only on a rung above the proxy** (`DecodedPicture.isRaw` = a sensor is reachable; `systemDeveloped` = the system decoded a RAW that carries no render). Anything that asks "on the sensor?" reads `shownBase != .proxy` (the lens profile applies by itself there, is only offered on a render), and an export sizes from `plan.sourceSize` — a DJI sensor is 8064 × 4536 where its render is 960 × 540 — after `plan.prepare`. `CIRAWFilter` runs at its plainest (no lens correction, no noise reduction, no boost) because the graph applies the DNG's own opcodes, as the web does over LibRaw.
- 2026-09-28 — **A file of the capture is DECODED UNDER ITS OWN NAME** (`RunPictureSource.sourceName` → `PictureJob.sourceName`, `Develop/Store/RollEditor+Renditions.swift`): the export decoded a fetched original under the PICTURE's name, so an ARW fetched for a HIF picture was read as a plain image and lost its RAW base. The fidelity chip lists a capture's files for ANY picture — siblings by base name (a folder's, the Library asset's) only once their head is read, never an export of ours (`Software: Atelier`), an instance's original and companion with a RAW's render size read from a 1 MB head — the choice stored in `RollPicture.rendition` (nil = where it opens); a failed or cancelled fetch clears it, one undo step, as the web.
- 2026-09-26 — **DJI's own `.cube` files separate with TABS**: the web's `\s+` reads them, and the first Swift parser (spaces only) refused every DJI LUT without a word — `parseCube` now splits on any whitespace, pinned by a spec.
- 2026-09-26 — **The native audio bed is NOT rendered ahead of the encoder's priming**: the web renders its tick bed 2112 samples early because mp4-muxer writes no edit list (`media-pipeline.md`); `AVAssetWriter` records the priming in its edit list, so here `renderBed(..., leadSeconds: 0)` and `decodeAacWindow`'s shift is deliberately not ported. The Swift voices match Chrome's own render of `renderBed` to 1.82e-6 per sample (four Chrome departures from the Web Audio spec reproduced: oversampled start frames, the 440 Hz first block, the two-table triangle, Blink's direct-form-I band-pass). Sync is claimed only after decoding a native export back — not yet done.

- 2026-09-28 — **A RAW's sensor decode has no Cancel** (`CIRAWFilter` cannot be stopped part-way): the task says so and runs to the end, unlike the web's LibRaw worker whose turn is dropped. Lensfun's answers are kept in `lens-profiles.json` beside the rolls, and a crop gesture writes the roll ONCE at its end — the web writes through a 200 ms draft; same document, fewer renders of the whole picture.
- 2026-09-28 — **The loupe never decodes the file whole on an iPhone or an iPad** (`Develop/Stage/StageLoupe.swift`): every iOS device counts as CONSTRAINED, the web's `device-class.ts` rule, so past the stage's 1:1 the loupe renders at the `.loupe` budget and SAYS "as close as this device goes"; the Mac decodes the file at its own density. It shows only over the stage render it was made for, one render in flight and one owed, and lets the file go 3 s after the view comes back. The wipe's before side is the stage's own pixels, not the file's (the web draws the file's), recorded in PARITY.

## Screens

- 2026-09-23 — **Studio Papier is SwiftUI colour tokens read from the environment** (`\.palette`): `Palette.paper` follows the system appearance by day and night (the web's `[data-theme='dark']` values), `Palette.darkroom` is the hue-less grey a picture is judged in, and a screen enters the darkroom with ONE modifier (`.darkroom()`: the palette, `preferredColorScheme(.dark)`, the tint) — never a second set of views. Light ink ON a picture is `onMedia`, fixed, as on the web.
- 2026-09-25 — **The brand's four faces are BUNDLED** (`Resources/Fonts`, the OFL TTFs from `google/fonts`: Space Grotesk and JetBrains Mono as VARIABLE files, Instrument Serif regular + italic, VT323) and registered at launch by `Brand.registerFonts()` through `CTFontManagerRegisterFontsForURL` — never `UIAppFonts` / `ATSApplicationFontsPath`, so both targets take one code path and the spec names no file. A weight is set on the variable file's `wght` AXIS (`Brand.sans(15, weight: .semibold)` is exactly 600): Google's variable files carry no SemiBold instance (Space Grotesk: Light · Regular · Medium · Bold; JetBrains Mono: no 600 either), so `Font.custom(...).weight()` would have snapped to a neighbour. The variable files answer to their DEFAULT instance's PostScript name (`SpaceGrotesk-Light`, `JetBrainsMono-Regular`), which is the name `Brand` registers and asks for. A slot whose file did not register falls back to the system face, never to Times. The web serves the same faces from its own origin (`@fontsource/*`, `local-first.md`), so the two apps now draw the same letters.
- 2026-09-23 (rev. 2026-09-28) — **A tool the app does not carry yet says so on its screen** (`PlannedToolView`), never an empty page or a spinner. Every tool is carried since 2026-09-28 and the view is unused; it stays for the next tool added to the registry.
- 2026-09-23 — Edits are written THROUGH with no Done (`RollEditor` → `RollStore.update`, debounced 300 ms to disk, flushed when the app leaves the foreground), as the web's Develop; the stage re-renders per change with the previous render cancelled, the cube re-baked per develop and its packed `Data` cached on `sameDevelop`.

- 2026-09-28 — **The TOOLBAR stands in for the web's masthead**: `.taskPill()` sits on every stack root and on each pushed screen with a bar of its own (the Develop and Studio editors), absent while nothing runs; `TaskCenter` (`@Observable @MainActor` over the kernel's `TaskRegistry`) is the one registry and `TaskCenter.tracked` the native `trackedFetch`. **Trips owns ONE NavigationStack** over `TripsRoute` (a stack inside a stack is unsupported, so `Tool.stack` does not wrap it again) and applies the pill and its banners around it — the screens it pushes add neither.
- 2026-09-28 — **The Studio follows the Library's ACTIVATIONS, not its active id**: a counter of puttings-to-work while the editor is on screen — a phone keeps every tab alive, so reacting to `activeId` would add to a project a picture tapped for Develop. A project's instance media lost to a relaunch is fetched back when it opens (a connected instance only), the bytes held for the session (a hard link), never cached; `LibraryStore.addFetched` registers each file's identity (the web's `materialize`), which is what wakes the Studio export's capture fetch and the finals home. The overlay panels are pure views over `Binding`s, wrapped in `DevelopSection` by their host.
- 2026-09-28 — **The Studio's and Trips' develop sheets draw ONE stage** (`Develop/Sheet/`): a host hands its decoded picture, a binding to its draft develop and a grading closure through its own grader (`DevelopSheetGrading`), and gets the Develop tool's wipe, 4000 % zoom, clipping on `J`, grey dropper, fidelity chip and session clipboard. Two departures from the web's sheet, both the Develop tool's own: an `A/B` switch, and the zoom pill at every width. **How to apply**: a develop control added to the Develop stage reaches both sheets through `DevelopSheetStage`, never a copy in a host.
- 2026-09-28 — **The web's hash routes are an `atelier://` scheme** (`App/AppLinks.swift` over the kernel's `Shell/AppLink.swift` + `DevelopRoute.swift`, specced): `studio/open/<id>`, `roadtrip/<trip>/<day>/<piece>`, `develop/<roll>/<picture>`, an instrument's path, and `connect?instance=…&return=…`, which only FILLS the address — nothing connects until Allow, and `return` is honoured only for a path of ours. Winnow's timeline links are parsed and kept OFF, as the web's `TIMELINE_SYNC_ENABLED = false`. On the Mac `.handlesExternalEvents` routes a link to the open window (guessed).

## The loop

- 2026-09-23 (rev. 2026-09-25) — **The cloud container CAN have the KERNEL's compiler, and CI stays the compiler for the app.** swift.org is refused by the proxy and Docker Hub's own registry counts anonymous pulls against the proxy's shared address (`TOOMANYREQUESTS` on the first try), but **`mirror.gcr.io` serves the official `swift:5.10-jammy` image anonymously and unlimited**: `apple/Scripts/linux-toolchain.sh` pulls its four layers (~2.5 GB unpacked), bind-mounts `/home`, `/tmp` and `/root` into the rootfs and installs `swift` / `swiftc` wrappers that chroot into it — `swift build` of AtelierKit in 8 s, the 307 specs in 3 s, the very compiler CI's `kernel-linux` job runs. The container is root and allows chroot and bind mounts (checked before building the script). **How to apply**: run the script first thing in a cloud session that touches `apple/`; every kernel change is then compiled and tested locally before a push, and only SwiftUI / Core Image / the app targets wait on CI (`swift test` on ubuntu and `macos-latest`, then `xcodebuild` for both targets unsigned, gated on `paths: apple/**`). Still true: write for Swift 5.10's type checker (an arithmetic line over several optionals or tuples is split into named `let`s, and a view `body` past some thirty chained modifiers is cut into pieces — `lifecycle(keyed(presented))` in the Studio editor, which the macOS compiler refused whole while iOS built it — Linux refused ONE such expression where Xcode's newer compiler did not), and a PR in merge conflict runs NO workflow at all: merge `main` in before expecting CI.
- 2026-09-25 — **The kernel is ONE module, so every public top-level name is shared by ~100 files ported in parallel** — the first merges collided on `clamp`/`clamp01` (Geometry vs Framing/Transfer), `splitName` (a private helper shadowing UniqueName's public one makes the file's own calls AMBIGUOUS, not private), `lumaOf` (detail.ts and mask.ts each carry a copy on the web; the kernel keeps Mask.swift's) and two `BrushRaster.swift`. And **SwiftPM refuses two files with the same BASENAME in one target** (`multiple producers … Geometry.swift.o`), whatever their folders — hence `Render/Keystone.swift` beside the root `Geometry.swift`, `Render/GainMapGrid.swift` beside `HDR/GainMap.swift`. And a kernel type named like an Apple framework's LOSES in any app file importing that framework: `DocumentGroup` is SwiftUI's scene there, and the first Studio gallery failed the iOS build on it (2026-09-28) — the app writes `AtelierKit.DocumentGroup`, as it writes `AtelierKit.Point`, and the guard refuses the bare name. The same holds ACROSS the app and the kernel: the app may declare a type the kernel also has (`CellMotion` twice, 2026-09-26) and win silently inside its own module, but the render gate imports both and refuses it — `apple/Scripts/check-test-names.sh` now lists such twins. **How to apply**: before a new public name or file, grep the package; a helper is `private` AND named for its file (`splitBaseExt`), never a generic word; a web module that exists twice on the web lands once here. The port brief (`apple/README.md` names the rules) carries the list of taken names.
- 2026-09-25 — **Apple's XCTest is not Linux's: `XCTestCase` has an instance method `record(_:)` (an `XCTIssue`)** that shadows a kernel global `record(...)` inside any test class — the macOS job refused every call and cascaded into "generic parameter T could not be inferred", while the Linux chroot passed. A spec calls such a global QUALIFIED (`AtelierKit.record(...)`). Checked: no other kernel global shares a name with an `XCTestCase` member (`measure`, `wait`, `expectation`, `run`, `name`…) — keep it that way. It struck a second time (2026-09-26) through a SPEC's own private helper named `record`, so `apple/Scripts/check-test-names.sh` now refuses any unqualified `record(` under the test folders, run first by the Linux job and by hand before a push: the local toolchain cannot otherwise see this class of error.
- 2026-09-24 — **A clone under `~/Documents` opens in Xcode with two errors that are one macOS refusal**: `failed to read asset tags: … actool --print-asset-tag-combinations … "Contents.json" couldn't be opened because you don't have permission to view it … Operation not permitted`, then `Missing package product 'AtelierKit'`. The first line is XCODE's build system (it runs `actool` over each catalog at load — the same format appears on projects with no XcodeGen at all), and `Operation not permitted` (EPERM) is the privacy layer on Documents / Desktop / Downloads / iCloud Drive, never a POSIX mode: the same refusal stops SwiftPM from LISTING the package directory (`Resolving Package Graph Failed … cannot be accessed (encountered an I/O error (code: 1))`), which Xcode reports as a missing product. The project itself opens because a double-clicked `.xcodeproj` is granted by user intent, that bundle alone — its siblings are not. Not the spec — CI generates and builds both targets from it. **How to apply**: never read the pair as an XcodeGen or `project.yml` fault; the remedy (Files and Folders for Xcode, or a clone under `~/Developer`) and the one-line terminal test that says whose read is refused are in `apple/README.md`, «If Xcode refuses the project on your Mac». `Missing package product` on its own, after a regenerate with Xcode open, is Reset Package Caches.
- 2026-09-23 — **Nothing has run on a device.** The app was reasoned, compiled by CI, and never seen; the first run on a phone (run-sheet #6) is where every assumption above — `CIRAWFilter`'s output, the export's EXIF, the Photos and Files paths, the darkroom — gets measured.
