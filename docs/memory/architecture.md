# Architecture

Read before touching the shell (`src/app/`), the tool registry, the shared asset library, or when adding/removing a tool.

## One registry drives the whole suite (2026-08-20)

**Decision.** `src/app/tools.tsx` exports `TOOLS`, and both the masthead nav and the hash router derive from it. **Why**: the suite grew from two tools to nine; anything duplicated per tool (a nav entry, a route, a sidebar flag) drifts. **How to apply**: adding a tool is one `Tool` entry (`id`, `path`, `label`, `subtitle`, `blurb`, `Component`, optional `accepts`) plus its component under `src/tools/<tool>/`. Never add a route or a nav item by hand elsewhere.

## `shared/` never imports `tools/` (2026-08-20)

**Decision.** Generic building blocks (`src/shared/*`) know nothing about any specific tool; tools are self-contained and may import `shared/`, never each other's internals. **Why**: it is what keeps a tool deletable and the core reusable outside the browser. **How to apply**: if a tool needs something generic, move the generic half into `shared/` (that is how `webcodecs-export.ts` and `frame-grader.ts` came to be) rather than importing across tools.

## Pure logic lives in DOM-free modules (2026-08-20)

**Decision.** Parsing, geometry, planning and maths sit in dependency-free, DOM-free modules (`srt-parser.ts`, `motion.ts`, `find-cue.ts`, `flight-path.ts`, `compose-layout.ts`, `compare.ts`, `exif-parser.ts`, `cube-parser.ts`, …); only the thin React/canvas glue touches the DOM. **Why**: it makes the logic unit-testable in a plain node environment and reusable as-is by a future native shell. **How to apply**: new logic goes in its own module with a `.test.ts` beside it, not inside a component. See `testing.md`.

## One asset library, capability-matched per tool (2026-08-20)

**Decision.** `src/shared/library/` holds a single app-wide pool of `File` handles. `buildAssets` groups raw files into logical *assets* keyed by the lowercased base name (so `DJI_0001.MP4` + `DJI_0001.SRT` is one `video+telemetry` asset, `IMG_8801.RAF` + `IMG_8801.JPG` one `photo` asset), and each tool declares the `AssetKind`s it `accepts`; `capabilities.ts` projects the pool down to those. **Why**: import a folder once and switch tools freely. **How to apply**: the one non-obvious matching rule is that a `video+telemetry` asset satisfies a tool asking only for `video` — keep it when touching `capabilities.ts`. Files the classifier does not recognise (`.LRF`, `.THM`, dotfiles) are ignored, and the first file to claim a slot wins so grouping stays deterministic — **with one exception, added 2026-08-24**: a RAW holding the image slot yields it to a non-RAW sibling (`isRawImage`, the one list of camera extensions, also read by `image-meta.ts`). A `.RAF` + `.JPG` pair is one photo and the half the browser can decode is the one the EXIF tool, Compare, Road Trip and the Studio all want to draw; which of the two the directory listed first must not decide that.

## Only `File` handles are held; nothing is read eagerly (rev. 2026-08-21)

**Decision.** The library layer stores handles, never bytes; covers/metadata are built lazily per row (as it scrolls into view) and thumbnails are revoked on remove/clear. **Why**: a `File` is a lazy reference to disk, so listing dozens of multi-GB videos is instant — reading them to list them would not scale. **How to apply**: never read a file just to display a list. Object URLs must be revoked when the source changes or the component unmounts.

**The one read the list does make** (2026-08-21): 128 KB from each end of the `.srt`, to measure the clip's cadence (`telemetry/srt-probe.ts`). It is a sidecar, not the media — kilobytes against gigabytes — and it is the only place a *capture* frame rate is written. `probeContainer` stays banned from this path: its 48 MB cap per file is for the one active clip, and on a conformed file it would report the playback rate anyway. **How to apply**: a new derived `MediaMeta` field must merge onto the existing entry (`patchMeta`), never replace it — the cover and the cadence are independent async reads of the same asset, and whichever lands second used to erase the first.

## Almost nothing is persisted (rev. 2026-08-21)

**Decision.** Since the Scopes and Cull tools were retired (phase 0 of the studio merge, PR #29), the only stored state is the sidebar collapse flag in `localStorage`; the old `atelier:verdicts:v1` key is actively cleaned up on load in `AssetLibraryContext`. **Why**: Cull was the sole consumer of triage verdicts. **How to apply**: the unified studio's project persistence (phase 2) starts from a blank slate — IndexedDB for project documents, directory handles and thumbnails; `localStorage` stays for UI preferences only. See `studio.md`.

## The overlay engine is shared, not a tool internal (2026-08-21)

**Decision.** Everything that defines, draws, edits and exports overlay elements — `overlay-types`, `field-format`, `draw-overlays`, `guides`, `draw-guides`, `fonts`, `use-overlay-stage`, `export-overlay(-seek)`, and the `ElementList`/`ElementPanel`/`GuidesControl` editing components — lives in `src/shared/overlay/`. `tools/overlay/` keeps only the page (`OverlayStudio.tsx`). **Why**: the unified studio (`tools/studio/`) builds on the same engine, and `shared/` never imports `tools/`, so the engine had to move rather than be reached tool-to-tool. **How to apply**: overlay capabilities (new element kinds, title styles, glow) are engine work under `shared/overlay/`, picked up by both pages for as long as the overlay page survives the transition; page-specific layout stays in each tool. `StylePanel` joined them on 2026-08-23, when Road Trip's day badge became a second consumer of the title-style theme — the rule that produced the move is the general one: a second tool needing an editing component means moving the generic half out, never reaching across tools. `tools/exif/exif-parser.ts` → `shared/exif/exif-parser.ts` on 2026-08-24 is the same move for pure logic: Road Trip reads `DateTimeOriginal` to know the day a picture was taken. `tools/studio/SectionLegend.tsx` → `shared/ui/SectionLegend.tsx` on 2026-09-07 is the same move again — the legend whose explanation folds behind an ⓘ, once Road Trip's piece editor started folding its own prose the same way; `shared/ui/` is where a generic control that belongs to no engine goes. When the promoted component already titles itself and the new consumer titles the section too, give it an optional slot rather than a second label: `StylePanel` took a `heading` prop so Road Trip's "Title style · Trip" legend replaces its own "Style".

## One tool hands a document to another through a ROUTE (2026-08-24)

**Decision.** Road Trip opens a Studio project by navigating to `#/studio/open/<id>`; the Studio loads it, opens it and rewrites the hash to `/studio`. **Why**: neither tool reaches into the other's state, the handover survives a full reload of the app, and the receiving tool keeps its own permission and reconciliation logic. **How to apply**: a consumed route must rewrite itself on arrival (a reload would otherwise re-run the open, and Back would bounce), and it is guarded by `isWithinRoute` like every other route effect.

## Hash routing (2026-08-20)

**Decision.** Navigation is hash-based (`#/telemetry`, `#/lut`) through a minimal `useSyncExternalStore` router. **Why**: the site is served as static files from GitHub Pages, where a history-API path would 404 on deep-link/refresh. **How to apply**: do not introduce a history-API router without solving the static-hosting fallback first.

## A tool's route redirect must be guarded by `isWithinRoute` (2026-08-24)

**The bug, reproduced**: from the Road Trip gallery, picking Studio in the switcher did nothing — the hash went back to `#/roadtrip/home` and the page never changed. Both tools with sub-routes (`/studio`, `/roadtrip`) redirect an incomplete route to their gallery (`if (path !== HOME_ROUTE && !open) navigate(HOME_ROUTE)`), and a tool is still mounted and still subscribed to `useHashRoute` at the instant the hash becomes another tool's. It read `/studio`, found it "not my home route", and navigated back. It only bit with no document open, which is exactly why it looked intermittent.

**How to apply**: any route effect in a tool must first check the path is its own — `isWithinRoute(path, BASE_ROUTE)` in `app/use-hash-route.ts` (which also refuses `/roadtrip-notes` for `/roadtrip`). More generally: **a mounted component may observe a route that no longer belongs to it**, so never navigate from an effect without asking whose route it is.

## A tool crash must not blank the app (2026-08-20)

**Decision.** `ErrorBoundary` wraps the active tool and resets on route change. **Why**: one tool's exception used to take the whole suite down. **How to apply**: errors are logged to the console only — nothing is reported anywhere, by design (see `local-first.md`).

## The source seam: documents carry a `sourceId` from day one (2026-08-31)

**Decision.** `shared/sources/source.ts` holds the source model the Winnow bridge rests on (`docs/winnow-bridge.md` §3): a source is where projects, state and later scheduled work live, and `local` — this browser, its File System Access layer, its IndexedDB stores — is source #1 and today the only entry in `listSources()`. `ProjectDoc.sourceId` names it (v14; the migration files every older document under `'local'`, the only place it can be), and the studio gallery groups its cards by source **even while local is the only group**, with a `source: local · N projects` header.

**Why**: the seam is the cheap half of multi-instance. Grouping an existing gallery and re-keying documents *after* a second source exists is a refactor across every consumer; carrying the id and the grouping from day one makes "add a Winnow instance" a data change. The maintainer accepted the limit that makes this tractable: **a project belongs to exactly one source**, media and documents co-located, so sync and merge never exist; crossing sources is the portable file, explicitly.

**How to apply**:
- `sourceId` is **bound-half**: it must never enter `.atelier.json` or its four places — a template mailed to someone comes from no source. `applyProjectFile` keeps the receiving document's own `sourceId` (tested).
- `groupBySource` never hides a document whose source this session does not know — it gets its own group and the header says "not connected", following the say-why rule. `local` always leads.
- `LOCAL_SOURCE.capabilities` answers honestly (`scheduling: false` — a tab cannot run reminders); a UI must read capabilities rather than offer a button that cannot work.
- The media/document **adapter interfaces are deliberately not typed yet** — phase 1/3 will shape them against the real Winnow client; an interface nothing implements would only be a guess. Do not "complete" the contract speculatively.

## Remote sources: a Winnow is fetched and WRAPPED, not streamed (2026-09-01)

**Decision.** `shared/sources/winnow/` is the first remote source: a client (`client.ts`, `fetch` injected, errors typed `unauthenticated | forbidden | unreachable | notfound | conflict | protocol`), a `localStorage` store of connections mirrored into `listSources()` (`store.ts` → `setRemoteSources`), and `materialize.ts`, which turns a picked asset into ordinary `File`s — the proxy by default (H.264/AAC mp4 for a clip, WebP for a photo), the original on request, the `.srt` flight log alongside either. The shell owns the entry points: the sources screen (`app/SourcesScreen.tsx`, `#/sources` and its older name `#/connect?instance=…`) and, in `AssetSidebar`, the instance's own tab (below) whose "browse all" opens `WinnowBrowser` (a month of `/api/assets/calendar`, then a day of `/api/assets`).

**Why fetch-and-wrap**: the whole pipeline holds `File`s — `buildAssets`, the stage, the filmstrip, WebCodecs, the exporter — and a `File` cannot be virtualised over a URL. Wrapping the proxy costs one download per clip and touches nothing downstream; a URL-backed asset would touch every consumer. It is the same trade `transcode-store.ts` already makes. Streaming preview by URL stays possible later, behind the same seam.

**How to apply**:
- **Never hash a fetched proxy's own bytes.** `materialize` vouches for every file with the ORIGINAL's `content_hash` and Winnow id (`registerMediaIdentity`, consulted by `mediaHash`/`hashedMediaRef` before any read). The `assetId` is `"<host>/<id>"`, scoped to its source. Names keep the original base name so the clip pairs with its `.srt` exactly as from a folder. **That id is what the write-back sends** (2026-09-06, `finals.ts`): `splitAssetId` takes the host off, refuses to link on any other instance, and the numeric id travels as `original_asset_id` so Winnow's reconcile links exactly instead of guessing on basename + capture time. The Studio keeps the last run's rendered `File`s (`lastRun`) for that one purpose and lets them go on the next run or a media change; finals go one request per file (the body limit is per request), then one `/api/reconcile`. The path under the finals root is Winnow's nouns only (`<chapter>/<name>`; the Studio knows no chapter today, so the root) — never a trip's slug.
- **A fetched file is dated at its CAPTURE, never at the moment it was copied** (`captureMtime`, `materialize.ts`). `lastModified` is what a folder's file would have carried and what every date fallback in the suite reads (Road Trip's day, `readCaptureDate`), so `Date.now()` there files a 2025 photograph under today. `captured_at` first; a row that has only `capture_date` is taken at LOCAL NOON, because midnight lands on the day before in any zone west of the reader; now is the last resort and means "nothing knows".
- **No request at boot.** Connecting is the user's click on `#/connect`; the link may *propose* an instance, the person confirms it. A 401 means "sign in there" and the UI says so with the link — it is not an error to hide. Since 2026-09-06 `#/connect` also takes `return=<in-app path>` (a hash path starting with `/`, never `//` or a URL) and lands there once allowed — how a Road Trip timeline link whose host is not yet connected comes back to its proposal.
- The `<img>` thumbnails need `crossOrigin="use-credentials"` or the cookie is not sent; a `fetch` needs `credentials: 'include'`. Both are cross-origin, same-site.
- `listSources()` in `source.ts` stays pure: it holds what `store.ts` mirrors in, it reads nothing.
- **Follow `next_cursor`.** One `/api/assets` page is 200 rows and a shooting day in this library reaches 300+; a browser that reads one page shows the day two-thirds full and says nothing. `WinnowClient.allAssets` walks the cursors (capped at 2 000).
- **The browser has three ways in and one row of filters.** By day (`/api/assets/calendar`) because Road Trip is day-keyed; by folder (`/api/sessions` — a Winnow *session* is one ingested shoot folder, the closest thing it has to "that folder"); and, since 2026-09-06, **by leg** (`/api/assets/timeline` → chapters, then `/api/assets` over the leg's calendar DAYS — Winnow has no chapter filter and its filter schema strips unknown keys, so the `chapter_id` first written there narrowed nothing and quietly listed the whole library; the panel prints the leg's own count beside the rows, because a shared travel day makes the day query wider). The tab is offered unless the instance says `timeline: false`: no capability flag announces a timeline and requiring one hid a working feature, so a 404 from the route is what “this instance serves none” looks like and is said as that. **The wire keys live in ONE function, `chapterFromWire` (`client.ts`)**, checked against Winnow's own `lib/timeline.ts` rather than assumed, and nothing downstream reads the wire; `WinnowChapter` deliberately has the same field names as `TimelineChapter` (`roadtrip/timeline-import.ts`) so a chapter list is handed to the import unchanged with neither module importing the other (a spec asserts the assignability). A date the wire sends is kept WHOLE — an instant reaches the import and is refused there, never sliced here. A chapter is a prefilled list, never a download; ticking stays the user's. Type / extension / device come from `/api/facets` and are sent to the calendar, the day, the sessions and the rows alike — Winnow honours the same cumulative filters everywhere, so one choice narrows the whole modal, counts included. The month is a `<select>` with an `<optgroup>` per year over `bounds` (`monthOptions`): fifteen years of media is two clicks, not a hundred arrow presses. Do not add a filter Winnow cannot apply to the calendar too — a count that disagrees with the day list reads as a bug.
- **An aggregate over no rows is a row of NULLs, not no row.** Winnow's calendar answers a filter that matches nothing with `bounds: { min: null, max: null }` — an object, never `null` — and reading `.min` from it during render crashed the browser (and, before the boundary below, the whole app). `WinnowClient.calendar` collapses that to `bounds: null` at the boundary, once, so every reader can treat a non-null span as two real dates. Normalise a wire shape where it enters; do not defend against it at five call sites.
- **The library sidebar has its own `ErrorBoundary`** (`App.tsx`). Only the tool was wrapped, and the sidebar — which renders a source's browser — sits beside it, so a crash there blanked the suite despite the "a tool crash must not blank the app" rule. Anything the shell renders outside the tool needs its own guard.
- **The browser reopens where it closed**, per instance (`browse-state.ts`, `localStorage`): view, filters, month, the open day or folder, and the fidelity. Picking a trip's media happens over several sittings, so starting from today's month every time made the second sitting cost as much as the first. What is deliberately NOT remembered is the **selection** — "Add 12 to library" pulls gigabytes, and a tick list restored from another sitting is a list nobody just looked at. A remembered month also suppresses the jump-to-newest-month-with-media landing, or the restore would be overruled the moment the calendar answered. Removing a connection forgets its place.
- **A thumbnail retries; a tile that gives up says so — and EVERY Winnow thumbnail in the suite is `shared/sources/winnow/WinnowThumb.tsx`** (rev. 2026-09-10). A busy day fires a hundred-odd image requests at once down a tunnel to a home server, and an `<img>` has no answer to a lost one: it fires `error` once and stays a black rectangle for the session. Reported on a day of 132, intermittent ("it loads as soon as I open the inspector" — timing, not logic), and again from a **phone** where every tile of a day was black while the same day loaded on a desktop. The tile retries with a widening delay (the failures are load-shaped; retrying at once makes the pile-up worse), then falls back to a legible label. **Attempt 0 uses the plain URL** so the ordinary path stays cacheable; the first retry asks for that same URL again once the entry has been HEALED (next bullet), and only the later ones carry a `?retry=N` discriminator, which is a genuinely new request a cache cannot answer. Do not "fix" flaky media loading by disabling the cache; make the failure self-healing and visible instead.
- **The cache entry that fails before the request leaves the machine — diagnosed, measured and cured 2026-09-21** (`shared/sources/winnow/cache-heal.ts`). Winnow adds `Access-Control-Allow-Origin` only when the request carried an `Origin`, serves derivatives `immutable` for a year, and sends **no `Vary: Origin`**; Chrome partitions its HTTP cache by SITE, and `winnow.steeve.website` and `atelier.steeve.website` are one site. So browsing Winnow's own pages — whose `<img>` tags send no `Origin` — stores those derivative URLs **without the CORS headers**, and every later Atelier request for them is served that entry and fails the check before reaching the network: a tile draws black, `client.fetchFile` throws a TypeError, and the one sentence this client can honestly produce for that is *"did not answer (offline, wrong address, or this origin is not allowed there)"* — which is what the maintainer reported from the Develop tool while the JSON routes on the same host answered fine. It is per-DEVICE (his other computer opened the same album), it never heals (the request never leaves the machine, so a reload changes nothing), and *Disable cache* in DevTools is what made it go away — how he found it. **The cure is `cache: 'reload'`**: it goes to the network AND REPLACES the entry, so the plain URL works afterwards for an `<img>` and a `fetch` alike. Measured in Chromium against a two-origin stub, with the shipped client: the poisoned proxy fetch now succeeds and a later credentialed `<img>` on it draws from cache with no request at all. Applied in three places over ONE per-session memo: `request()` replays a READ that threw (never a write — it may have landed) and says *"even asked again past this browser's cache"* when that fails too; `WinnowThumb` heals before its first retry (and skips straight to a discriminated URL when the heal says the instance is simply not answering); `MediaLightbox` takes a `heal` prop its two instance callers pass. **How to apply**: the `?retry=N` trick only routes AROUND a bad entry and leaves it there to fail again on the next page load — prefer replacing it. **The root fix is not here**: `Vary: Origin` on Winnow's derivative routes, measured to prevent the whole thing, and it belongs in that repository.
- **That component was private to `WinnowBrowser`, and the bug was therefore paid three times.** The two grids written later — the Library's Winnow tab (`WinnowScopeGrid`) and the piece editor's day strip (retired 2026-09-20, `roadtrip.md`) — each drew a bare `<img>` with no retry, so the phone report was the same defect in a file that had never seen the fix. It is the SECOND lesson that strip re-paid from `WinnowBrowser` (the first was `aspect-square` on a grid tile, `frontend.md`). **How to apply**: a fix that a second surface could need does not stay a local function — the suite's own rule, the one `StylePanel`, `GradePanel`, `ImportDocumentModal` and `exif-parser.ts` each followed on their second consumer. The tile also owns its own attempt count now, where the browser held a `Map` of them: a failing tile re-rendered the whole grid, 132 times on the day that prompted the retry, and its pending timers outlived the grid.
- Ruled out while chasing that one, worth not re-deriving: **Next middleware response headers DO reach a route handler's response** — measured against the deployed instance, `GET /api/health` with an `Origin` comes back with the full CORS set. So a derivative's `304` is not silently losing them.
- **The client writes DOCUMENTS in exactly one place** (since 2026-09-06; the finals write-back above is the other write, media only): the opaque document bucket `/api/apps/:app/docs[/:id]` (`listDocs`/`getDoc`/`putDoc`/`deleteDoc`, app namespace `atelier`, kinds `trip` and `project`; the shared reducer, pill and plumbing sit beside it in `shared/sources/`). Every write carries `If-Match`, a stale etag is a 412 mapped to `WinnowError.kind === 'conflict'` with `theirs` (the server's etag + `updated_at`) so the caller can decide; the client never retries a write by itself. 404 is `notfound` for every route now (it was `protocol`), 304 is an answer, and `Content-Type: application/json` on the PUT is deliberate — it forces the preflight only the allowlisted origin passes. Who consumes it and why: `roadtrip.md`, «The mirror's bookkeeping»; the server side: `docs/roadtrip-persistence.md` §7.
- **"Open in Winnow" lands on the media's SESSION, because Winnow has no page for one asset** (2026-09-09, read in its own repo at `009ff02`). Its `MediaViewer` is an overlay that every consumer holds in local React state (`SessionGrid`, `GalleryShell`, `TimelinePanel`, `SwipeDeck`…) and no route carries an asset id — the only per-asset URLs are API routes. So `client.sessionUrl(session_id)` → `/sessions/<id>` is the closest a link gets: the grid the picture lives in, which is what the verb is actually for (its neighbours in the shoot, its verdicts, its exports — the one thing the lightbox cannot show). `assets.session_id` is `NOT NULL` and both asset routes select `a.*`, so the id was already on every row and merely missing from `WinnowAssetRow`, the same miss `lens` was. **Do not invent a deep-link parameter** to open the frame itself: that is Winnow's to add, and a guessed key is precisely what made `chapter_id` narrow nothing and list the whole library.
- **Tiles own their height** (`h-[90px]`, `auto-rows-max`), and the day column is the element with the bounded height + `overflow-auto`. An `aspect-ratio` tile inside a height-constrained flex/grid chain gets squashed to whatever the rows are dealt — that was a real bug at 132 media, and it looked like a data problem.

## Connecting and managing a source are ONE screen (2026-09-08)

**Decision (the maintainer's, choosing "variant A" out of four drawn as an artifact).** `app/SourcesScreen.tsx` is the single page where a remote source enters the app, is looked at and leaves it: `local` first, then a row per connection carrying its health, its capabilities, how many of this browser's documents came from it, and its verbs — with the connect form at the bottom of the same page. It answers on `#/sources` **and** on `#/connect`, which stays the name an instance's own app rail links to, query and all (`?instance=`, `?return=`); `App.tsx` matches both bases and slices the query off whichever matched.

**Why**: connecting used to write to a store nothing rendered. Dropping a connection meant clearing site data, an instance that was down showed as an empty media tab with no reason, and a capabilities sheet read once at connect time silently hid features that had shipped since (the bucket trap). A list without a form would have been a second screen for one verb; a form without a list was the bug.

**How to apply**:
- **The probe IS the refresh** (`winnow/use-source-health.ts`): opening the page asks each connection `/api/capabilities` once, stores the answer back on the connection with a `refreshedAt` stamp, and shows the round trip. So the screen that reports a stale sheet is the screen that fixes it, and "Refresh"/"Retry" is the same call on demand. Still **nothing at boot** — the page is somewhere a person navigated to.
- The effect probes on the connection **ids**, never on the array: a successful probe writes to the store, which hands back a new array, and an effect keyed on it probes forever.
- **Four states, four verbs**: reachable · sign-in needed (401/403 — an anchor to the instance's own `/login`, never a form here) · unreachable · asking. The mapping and its sentences are pure and tested (`shared/sources/source-ledger.ts`), because the rail and the galleries will want the same words.
- **A forget counts before it asks**: `countBySource` over the two local stores + `forgetWarning` — "8 projects and 3 trips came from it — those stay on the instance". Documents are never deleted by forgetting, and the copy says so.
- **A host goes by its first label in a tab** (`shortHost`/`shortHosts`): `winnow.steeve.website` truncated to `WINNOW.STEEVE.…` in the 288px rail read as a defect. The full host stays in the `title` and on this screen; two hosts sharing a first label both stay long rather than both reading "winnow".
- The rail's gear (beside "collapse") is the way in from any tool — sources are the shell's business, so the entry point is the shell's rail, not a tool's panel.
- **Still first-wins**: `use-connection.ts` continues to hand every media surface `connections[0]`. Connecting a second instance is now easy, so that limitation is visible where it was theoretical — the answer designed alongside this screen is a tab per instance in the rail, which is where `useWinnowSource(id)` will replace the hook.

## The Library has two tabs, and the instance's tab is a VIEW (2026-09-07)

**Decision, the maintainer's own design.** With a Winnow connected, `AssetSidebar` shows `Local` and the instance as two tabs that never mix — his words: *"un tab pour changer de type de sources: locales ou winnow, comme ça pas de mélange"*. `Local` is the pool of files opened from this machine, exactly as before. The instance's tab **lists what the instance holds for the span the active tool is on**, asked live (`winnow/use-scope-rows.ts`, `date_from`/`date_to`) and re-asked when the span changes — *"à chaque fois que l'on change de date […] ça change automatiquement les médias affichés"*. **Why a view and not a pool**: the complaint was a pile that grew with every day visited and needed clearing; a listing derived from the span cannot accumulate, so there is no clean button to design — *"plus besoin de clean button"*.

**How the span reaches the shell**: `shared/sources/media-scope.tsx`. The tool PUBLISHES (`usePublishMediaScope`, taken back on unmount) and the sidebar READS (`useMediaScope`) — the asset library's direction reversed, and the tool→shell twin of the route two tools use between themselves; `shared/` stays free of `tools/`. A plain `{ from, to, label, publisher }` of `YYYY-MM-DD` strings, deliberately not Road Trip's `IsoDate`. Road Trip publishes its piece's day (or span) and the overview's selected day; with no publisher the tab offers a `<input type="date">`, so the Studio can use it too. **Day granularity by default** (his call); a stage/leg is a publisher away, never a new sidebar.

**How to apply**:
- A fetched picture is an ordinary pool asset (`addFiles` → `setActive`, and since 2026-09-20 this tab is the ONE surface that fetches one — `roadtrip.md`); the pool is split by provenance for display only (`shared/library/asset-source.ts`, reading `mediaOrigin`), so nothing the pool holds is ever invisible: in-span assets are marked tiles, out-of-span ones list under "Also in the library" with their ✕. Never hide a pool asset from every tab.
- The tab's "all / none" acts on that tab's assets only (`AssetLibrary.select(ids, on)`); `selectAll` would tick the other tab's too.
- Nothing is asked while the tab is closed (`enabled`), and nothing at boot. The remembered tab (`atelier.library.tab`) falls back to `Local` when no instance is connected.
- Both media surfaces take the instance from ONE hook (`winnow/use-connection.ts`); multi-instance is answered there once, and is deferred.
- Tiles are fixed-height (`h-[74px]`), never `aspect-square` — `frontend.md`.
- **The tab also picks which HALF of the instance's library it lists** (2026-09-08): `All · Incoming · Gallery`, a segmented row under the span. Winnow splits its roots into `incoming` (still to cull: kinds `source`/`inbox`) and `final` (finished exports, its Gallery), takes `/api/assets?kind=incoming|final` with absent meaning both, and calls the three cells exactly those words in its own `LibrarySourceTabs` — so Atelier says the same rather than inventing a second vocabulary for one shelf. Remembered in `atelier.library.winnow.half`, and the same choice is a select in `WinnowBrowser` (where, sharing `filterParams`, it narrows the calendar, the folders and the legs too).

## The tab can look BESIDE the tool's day without moving it (2026-09-13)

**Decision, the maintainer's.** The `DayPicker` stepper is drawn whether or not a tool publishes a span. With one, it opens on the tool's day and its arrows look at the day before / after — for a teaser, or to put yesterday's picture on today's piece — while the piece keeps its date. **Why**: the stepper vanished the moment a trip opened, and the neighbouring days were exactly what he wanted from a piece. **How to apply**:
- The override is the SIDEBAR's state, never published back: the tool never learns of it, so the seam stays one-way and no date on a document can move (`shared/sources/scope-override.ts`, pure and tested).
- It is ANCHORED to the span it was taken from and applies only while that span is still published — another piece, another heatmap day gives the tab back to the tool with no reset effect (his call: reset on change). Not persisted: a remembered override is the pile the tab was built to never become.
- Always ONE day: out of a multi-day piece the arrows step from its edges (his call). Stepping back onto a single-day anchor IS following again (`overrideTo` → null), not a look-alike state.
- The legend stays the tool's day; the stepper wears the accent border at rest while elsewhere, the line under it says where against the ANCHOR ("the day before", "day 2 of 3" — never "3 days ago"), and `↺ <day>` resets. The intent is unchanged: in the editor a click still puts the picture on the slide, whatever day it comes from.
- The month popover MARKS where that sits: a lane under the strip (a foot on each calendar cell) in accent for the tool's days and in `line-strong` for `MediaScope.within`, a wider span the publisher names (Trips: the trip's two dates and name). A mark only — nothing is listed by `within` — and its own row, because the bars already spend their colour on the counts. The key under the month is drawn only when a mark touches that month.
- **The preview pages PAST a day** (his call, 2026-09-13): `WinnowLightbox`'s deck is `[before, ...pictures, after]`, two `uncounted` edge cards naming the nearest day WITH media each way (`winnow/day-walk.ts` + `use-neighbour-days.ts`: a 62-day calendar window, then the rest of the way to `bounds`, same half as the tab). Landing on a card in the direction it points moves the tab through the same `goToDay` as the stepper (so it IS the override, visible behind the sheet) and reopens on the first picture, or the last going back; against its direction (across the wrap) it only shows. **Why edge cards and not a wrap-detect**: the shared deck wraps modulo, a wrapped neighbour would slide in before the swap, and two items cannot tell forward from back — two cards make every deck ≥ 3 and leave `use-media-viewer.ts` untouched. The sidebar keeps the sheet open across the roll by remembering the rows it LEFT: the render that changes the span still holds the old answer, and reopening on it would land on the wrong day.

## A click on an instance's tile means what the TOOL says it means (2026-09-07)

**Decision.** `MediaScope` carries an `intent`: `pick` when something on screen is waiting for a picture (a piece's slide — `PostEditor`), `browse` otherwise (a trip's overview, a day picked by hand in the sidebar; absent reads as `browse`). With `pick`, a click on a tile fetches it and makes it active, as before. With `browse`, it opens `WinnowLightbox` — the picture large, ← / → across the same filtered list the grid draws, `Add to library` as a button in there.

**Why**: a 74px tile is enough to recognise a frame you already know and not enough to choose between two of them, and outside the editor there is nothing to fetch INTO — the maintainer's own framing, "dans l'overview cette barre peut avoir un comportement différent". The intent lives on the scope because only the publisher knows whether anything is waiting; the sidebar must not guess from the route, and `shared/` cannot ask a tool.

**How to apply**:
- The sidebar owns the filtering (`remoteShown`) and hands the same array to the grid and the lightbox: two copies of the predicate would eventually disagree about which picture index 3 is.
- Bringing one picture across is `usePickFromInstance` (`winnow/use-pick.ts`), above both surfaces — one answer to "is this already here?", one in-flight tile, one sign-in link on a 401.
- The lightbox shows the **proxy**, never the original: it is the rendition the pool would hold, so what is on screen is what the editor would get, and looking at a day pulls no captures. A clip is `preload="metadata"` for the same reason.
- The preview closes on anything that changes what the list IS (span, tab, filter) — an index into a list that has been replaced points at another picture.

**The bug that prompted it, worth not re-deriving**: the ✓ badge ("in the library") was drawn only when the tile was NOT active, so clicking B moved the ring to B and made A's ✓ appear. Every click looked like it had ticked the PREVIOUS picture, and the maintainer read the badge as a selection he could not explain. **Two independent facts must be drawn independently** — the ✓ now shows on the active tile too, in the accent colour. A state hidden by another state is not a simplification; it is a third state nobody designed.

## A tool publishes VERBS for a picture, the shell draws them (2026-09-09)

**Decision.** `media-scope.tsx` carries a second publication beside the span: `MediaActions` — a heading and a list of `{ id, label, hint, run }` the active tool offers to START from a media. The shell's two preview sheets draw them through one component (`shared/ui/MediaActionRow.tsx`); a tool that publishes none draws nothing. Same direction and same reason as the scope: the sheet where a picture is looked at large belongs to the shell, and what is worth making of that picture is the tool's business alone, so `shared/` still never asks about `tools/`.

**The contract that keeps it thin: `run` is called with the media already in the library and ACTIVE.** The publisher never learns where the bytes came from — a pool asset is activated, an instance's row is fetched first — and the picture reaches whatever is created by the ONE path that already exists (the Library's active asset, `use-slide-library.ts`), never by a second one. So no verb takes a media argument, and none of them writes a media ref.

**Two consequences, both load-bearing.** `usePickFromInstance().pick` now resolves with the Library asset id it landed on, or **null** when nothing arrived: a verb chained onto a fetch must not run on a fetch that failed, or the new piece opens over a placeholder (the thumbnail rule in `roadtrip.md`). And the record is compared by IDENTITY, not field by field like `sameScope` — it carries closures — so the publisher memoises it; only one screen of one tool is ever mounted to publish.

**A third (2026-09-16, the Develop tool's verb)**: `run()` is called in the SAME tick as the activation, so a verb that needs the active media itself must not read it in `run`'s closure — it asks (a pending flag) and an effect answers after the render. Trips' verbs never read it, which is why the trap stayed hidden — `develop-roll.md`.

**And the trap INSIDE that pattern (2026-09-20, Trips' «Situer cette photo»)**: the effect is keyed on the pending flag and resets it, so its own cleanup fires one render later — a `cancelled` flag set there cancels the very read it just started, and the sheet waits for ever. Guard a read with a sequence number in a ref, not with the effect's teardown; the reasoning and the measurement are in `roadtrip.md`.

## A remote ref is re-FETCHED, never cached (2026-09-06)

**Decision, taken with the maintainer.** The library is `File`s in memory and a reload empties it. A folder file survives that (the document keeps a directory handle, one permission click re-reads it); a file fetched from a Winnow does not, so every restart used to mean finding the day on the calendar and ticking it again. `shared/sources/winnow/resolve-media.ts` answers it from the DOCUMENT instead: since phase 0 a `SavedMediaRef` carries `assetId = "<host>/<id>"`, so `refetchMedia` asks the instance for that row and runs it back through `materialize`.

**Why not a byte cache.** It was offered and declined: a cache of fetched proxies would be the first place this suite persists media (against `local-first.md`), needs a budget, an eviction policy and pruning, and buys nothing the ref does not already say. The maintainer's own counter-proposal — *"not persist the file but search in the winnow library"* — is this, and his worry that it would cost the mixed library was unfounded: nothing about the pool changes, so folder media and instance media go on coexisting exactly as before.

**How to apply**:
- **Only a CONNECTED source, and never at boot.** `resolvableSource` returns null for a host absent from `winnow/store.ts`. A stored id must not become a reason to call a server the user never allowed; the request happens when a piece is opened, and the panel says which instance it is talking to.
- **Null is "gone"; a throw is "the instance had something to say".** A 404 on the detail route means the asset was purged and the caller reports that; a 401 must reach the UI as "sign in there" with the link, or a fixable problem reads as a lost picture.
- **Match a `WinnowError` on its KIND, never on a kind plus a status** (2026-09-06). `asset()` recognised a purged row as `kind: 'protocol' && status === 404`, which was true the day it was written; the persistence branch then gave 404 its own kind (`notfound`) and the two landed on `main` from different pull requests. Nothing conflicted textually, both branches were green alone, and `main` was red with a missing asset rethrowing as a broken instance. **How to apply**: adding a kind to `request()` re-homes every 404/412 already being caught somewhere — grep the status number across `src/` in the same commit, and let the kind carry the meaning so a later split cannot silently change it.
- **Claim the slide BEFORE the await** (`restoredFor.current = slideKey`), then release it when the files land so the ordinary restore picks them up on the next pass. Without the claim a second render fetches the same bytes again; without the release the picture arrives and nothing activates it.
- `addFiles` is read through a ref inside the effect, never listed as a dependency: it is a fresh callback on some renders and re-running the restore would re-download.
- `client.asset(id)` and `client.assetsByIds(ids)` exist for this. `assetsByIds` sends Winnow's `ids` filter (its `intList`: comma-separated) and falls back to the detail route for an id the collapsed list did not return — a RAW's half of a pair, say. **Verified against Winnow's `src/lib/filter.ts` and `src/app/api/assets/[id]/route.ts`**, which answers `{ asset }`, not a bare row.
- One reading of `"<host>/<id>"` in the codebase: `finals.ts`'s `splitAssetId`, reused here rather than copied.

## The document sync machine is ONE hook, and a tool only describes its documents (2026-09-15)

**Decision (D2 of `docs/develop-tool.md`).** The shell-side machine that keeps an open document's mirror and its instance in step — dirty on edit, push on idle / tab hidden / unmount / "Save now", reduce the LIVE record after the request, resume on open, the pill's four verbs — was copied line for line into `StudioTool` and `RoadTripTool`. It is now `shared/sources/use-document-sync.tsx`, and the resume decision (304 · clean replace · dirty conflict · failure, a protocol error on a clean mirror staying quiet) is the pure `afterPull` in `doc-sync.ts`, tested. A tool passes a `DocumentSyncDriver` (record store, `putDoc`, `deleteDoc` with what belongs to the document — a trip's thumbnails —, `push`, `pull`) and says what replacing or deleting the open document does (`onReplace`: the Studio REMOUNTS its editor with a new generation, Trips sets the document). **Why**: the Develop tool's roll is the third consumer, and a third copy is where copying stops being cheaper. **How to apply**: two tool shapes are supported and must stay so — a tool whose editor saves itself (the Studio) just calls `edited(doc)`; a tool with its own debounced local write (Trips) passes it as `beforeFlush` (so a push never carries a document older than the screen) and clears it in `onDiscardPending` (take theirs, keep local, delete). Staleness is checked against the document the machine is WORKING FOR (`activeId`, set by `resume`/`adopt`, cleared by `clear`), not the one on screen: the Studio resumes BEFORE it sets the document open. Behaviour is unchanged, including one quirk kept on purpose: Trips resumes only when the open trip CHANGES, so going to the gallery and back to the same trip does not re-ask the instance. Verified against a stub bucket (scratchpad node server, CORS with credentials) in the Browser pane: Trips — resume 304, edit → PUT after the idle with `If-Match`, a server bump replacing a clean mirror on reopen, a conflict from an edit racing a bump, the two-step Take theirs, Keep mine re-PUT over their etag, a deleted row → `gone` → Keep here as local; Studio — resume 304, the editor's autosave pushed, a bump replacing the mirror on reopen and the remounted editor pushing it back clean.

**The gallery half followed the same day (D2b).** `shared/sources/document-gallery.ts` (pure: `sourceLabel`, `documentSourcesFor(kind)`, `groupDocuments`, tested) and `use-document-gallery.ts` (the local list beside every instance's, the busy map, the notice, and the verbs that cross a source: `createOn` writes THERE first and keeps nothing here if refused, `remove` deletes there with the revision held and is refused while unreachable, `moveTo`, `mirrorRemote`). A gallery passes a `DocumentGalleryDriver` with its `kind` and `noun` — the sentences are the same for every kind, only the noun changes. **What stays in a tool**: anything that is not crossing a source — Trips' cover (which hands the OPEN trip back to the shell's save machine), the Studio's template duplicate, imports and the New modals. **The kind now filters the sources**: `documentSourcesFor(kind)` and every `remoteFor(id, kind)` in the gallery ask `bucketHolds`, so a gallery never offers or lists a kind the instance's bucket does not keep; for trips and projects this is the old behaviour, since every bucket keeps them. ## Undo is a stack of whole DOCUMENTS, watched at the tool's one change funnel (2026-09-15)

**Decision.** `shared/history/` is the suite's one undo engine: `history.ts` (pure, tested — past · present · future, `record`/`undo`/`redo`/`seal`), `undo-keys.ts` (who owns ⌘Z), `use-history.tsx` (the React half, returning the buttons as `control` the way `useDocumentSync` returns `pill`) and `UndoRedo.tsx`. A step is a **snapshot of the whole document**, not an operation with an inverse. **Why**: every editor already funnels its edits through one call (Trips' `handleChange`, Develop's, the Studio's autosave slice), the documents are plain JSON held immutably — so a snapshot costs a pointer, not a copy — and nothing has to describe how to invert itself, which is the half of an undo engine that rots. A field added to a document tomorrow is undoable the day it is added.

**The hook WATCHES, it does not intercept.** `useHistory({ value, onRestore })` records every value that arrives through the tool's existing funnel, so no call site changed — the only shape that could cover editors with hundreds of them. What makes watching work is IDENTITY: restoring hands the tool the very object the history holds, so when it comes back down the hook sees its own state rather than an edit. A tool whose document is a SLICE assembled from several `useState` values cannot preserve identity (it rebuilds the slice) and passes `isSame: shallowSame` instead — one level deep, which is exactly right because every member of such a slice is itself held immutably.

**How to apply.**
- **Merging is what makes it usable**: a slider fires a change per pixel, so two edits become one step when they arrive within `COALESCE_MS` (700 ms — longer than two frames of a drag, shorter than the pause before the next different thing, and just under the 800 ms save debounce, so one saved document is one undo step) under the same `label`. Pass a label that says what the edit was ABOUT (`post:<id>`, `trip`), or a gesture merges with the different thing done right after it.
- A present is **sealed** — nothing may merge into it — when a document opens and after every undo or redo, or the first edit after an undo would swallow the state it just came back to.
- `subject` (the document id) starts the history again: another document has another past. `reset(value)` is for a document REPLACED under the tool (the sync pill's take-theirs / keep-local), which must never be undoable back onto the server's copy.
- **An editor that seeds itself ASYNCHRONOUSLY passes `ready`**, false until it has: what arrives while a document is still finishing its own arrival becomes the beginning, not a step. The Studio restores its saved grade by fetching every built-in cube again, so without it a graded project opened on an undo that stripped the grade. The commit where seeding ends may carry the last of it (React batches), so the transition reseeds too — that is why `ready` is in the effect's deps.
- **Anything a restore hands back must come back BY REFERENCE**, never copied: a hook that rebuilt the array it was given (`useLutStack.revert` did, once) is equal in every value and reads as a fresh edit, which costs the step just taken — the redo branch disappears. That is the failure mode to look for when a redo goes missing right after an undo.
- **A slice is compared `sameSlice`, not `shallowSame`** — one level deeper for a member that is an array or a plain record, and never further. Identity is the right question for state held immutably and the wrong one for a member a HOOK rebuilds while meaning nothing by it: `useLutStack.restore` empties the stack onto a fresh `[]`, and that alone opened a fresh project on an undo. One level is where it stops because an item of an immutably updated collection is a new object exactly when it changed.
- **React does not promise that a promise's state lands in the same commit as a flag set from it** — measured: the looks landed one commit AFTER the `ready` flag they were supposed to close. So an editor that seeds asynchronously wants two flags, the first set after the seeding writes (every one of them is then in the value by the commit that observes it) and the second opening the gate a commit later, from an effect declared AFTER the history's own.
- The buttons are **always both drawn**, disabled when there is nothing to step to: a control that appears once you have edited is one nobody knows is there, and a phone has no ⌘Z at all. They are ONE control (2026-09-16): two bare halves under one border, a hairline element between them (a `border-l` on a half loses to its `border-0` by Tailwind's order), a half with nothing to do greying its glyph rather than fading whole — the pair costs one gap less in a tight bar and reads as the mirrored arc it is.
- What is NOT in a history: anything the document does not hold. A deleted piece comes back without its baked thumbnail (it re-bakes), and an export already written stays written.

## EXIF is WRITTEN two ways, and the copy is the good one (2026-09-20)

**Decision.** A developed picture leaves carrying the original's metadata, and
`shared/exif/` gained the writing half for it: `exif-block.ts` moves the
original JPEG's own `APP1` block across without interpreting it, and
`exif-build.ts` constructs one from an `ExifData` where no block can be moved.

**Why.** A canvas encodes PIXELS — the JPEG it hands over has no GPS, no body,
no capture time — and the maintainer looks his photographs up by exactly those
(2026-09-20: *"j'ai besoin de conserver l'exif… mais vraiment au maximum"*).
The copy is preferred because it keeps what no struct models, the MAKER NOTES
above all; the build is the fallback, and it is bounded by what `ExifData`
holds, which Winnow's own row is bounded by too (`exif-from-row.ts` carries no
make, model or lens on purpose).

**How to apply.**

- Three tags are corrected on a copied block, and only three: the ORIENTATION
  to 1 (a delivered picture is already the way up it was looked at, and a
  viewer honouring the original's tag turns it twice), the pixel dimensions to
  the delivered ones, and the THUMBNAIL cut loose by zeroing IFD0's next-IFD
  pointer — the original's thumbnail shows the picture before the development,
  and a file that previews as its own undeveloped self reads as broken.
- A copied block cannot come from a DNG or an ARW: their TIFF stream IS the
  file, so those rebuild. A segment also caps a block at 65527 bytes, which a
  copy can exceed; `withExifBlock` throws rather than write a file no reader
  parses, and the caller falls back to the build.
- `relativeAltitude` (DJI's height above take-off) is deliberately NOT written:
  it is an XMP property, not an EXIF tag, and an invented EXIF home for it puts
  a number where no reader looks. An XMP packet is its own job.
- `parseExif` takes `ArrayBufferLike` since, so a `Uint8Array`'s `.buffer` goes
  in without a cast and the writer is read back by the reader in one line.
