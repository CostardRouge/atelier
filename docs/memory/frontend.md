# Frontend — layout, styling, MapLibre, fonts

Read before touching UI, layout, the design tokens, or any MapLibre pane.

## "Studio Papier" is the design system, expressed as Tailwind v4 tokens (2026-08-20)

**Decision.** `src/index.css` declares the palette and typography in an `@theme` block — warm paper surfaces (never pure white), ink text, **one** desaturated vermilion accent (`--color-accent: #d9442a`), a near-black `--color-frame` behind video, plus `Space Grotesk` (sans), `Instrument Serif` (serif) and `JetBrains Mono` (numerals), paper radii/shadows and an `--ease-paper` curve. Everything else is Tailwind utilities in the components. **Why**: one accent and one surface family is what makes the suite read as a single studio rather than nine tools. **How to apply**: use the tokens; do not introduce a second accent colour or a raw hex in a component. Numeric readouts use the mono face.

**There is ONE button, one icon button and one segmented control (2026-09-13).** `shared/ui/Button` (`primary` · `default` · `ghost` · `danger`, sizes `sm` 28px · `md` 34px · `lg` 40px, `rounded-control` = 11px, Winnow's recipe with Atelier's vermilion on hover), `IconButton` (square, `label` REQUIRED — it becomes the accessible name and the tooltip) and `Segmented` (a recessed well with the chosen option raised on a paper tile, `aria-pressed` buttons, the one look for "chosen"). `buttonClass()` is exported for a `<label>` or `<a>` that must look like a button. `PageBar`'s back pill IS a `Button`, and `barPill` is now that `md` geometry with no skin, so a screen's own pill stays one band with it. `Segmented` takes `columns` (2026-09-13) for a choice wider than one row — Trips' eight formats sit on a 4-column well — so a chip grid is never hand-rolled beside it. **How to apply**: never write a new `pill`/`btn`/`chip` constant — reach for these; a control that needs a fifth variant is a design question, not a class string. Legacy constants still exist in the tools not yet migrated (`panels/ui.ts`, `StagesPanel`, `SourcesScreen`, `WinnowBrowser`, `DayPanel`…); retire them screen by screen as the audit's plan reaches each one.

**Icons are SVGs from `shared/ui/icons.tsx`, never Unicode glyphs (2026-09-13).** One 24-grid, stroke 1.7, `currentColor`, `1em` — the same drawings Winnow ships, kept in the repo (no icon package: no dependency, no request). `Icons.play`/`pause` replaced the `❚❚`/`▶` string copied into seven players; `Icons.settings`, `back`, `export`, `check`, `down`/`chevronRight` replaced the bar and fold glyphs. **How to apply**: a control's glyph comes from `Icons`; a glyph that is CONTENT (the `→` between two places, the `◆` marker, a `▶` kind chip on a thumbnail) stays text. Add a missing icon to the module rather than typing a character — a glyph is drawn by whichever font the platform substitutes. **An icon must read ALONE (2026-09-16).** `settings` was a circle with eight rays — fine beside the word, a SUN (brightness, in a grading suite) once the Trips piece bar dropped the word; it is a toothed cog now. Judge a new glyph with its label covered.

**An EMPTY library starts as the rail (2026-09-13).** **The rail is 64px wide and reaches under the shell's 16px gutter (`-ml-4 w-16`), with no top padding and `md` (34px) icon buttons**: the maintainer saw its icons off-centre and lower than the back pill — they were centred in a 48px column that started AFTER the gutter (26px from the page edge, 10px from the rule) and sat under 12px of padding. Centre a rail between the page edge and its rule, and put its first control on the bar's line. With no asset and no instance connected, `App.tsx` forces the docked library to its 48px rail whatever the size's stored preference: the column was a drop zone, one sentence and "0 selected" for a fifth of the screen. The rail carries an add control (`Icons.plus`, primary while empty) so the way in never waits for the panel; expanding the empty rail is one click (`peeked`) and writes the size's preference, and the first file to arrive lets that preference apply again — so on a desktop the panel opens by itself. The tablet rule (rail by default under 1180px) is untouched.

**The rail's add control is `OverflowMenu`, not a bare `IconButton` (2026-09-19).** It used to call `pickFiles()` alone — "add a folder" existed only as a text link in the expanded panel, so the rail's one visible gesture was never the one the maintainer reached for most on this project. `OverflowMenu` gained two props for exactly this case: `icon` (default `Icons.more`) and `variant` (default `ghost`), both ignored once the worded `trigger` is set, plus `disabled` — so the SAME menu component now covers a card's ⋯, a screen's worded verb (`trigger`), and a rail's own icon-only button, instead of a fourth bespoke trigger. The rail's menu opens `align="start"` (never the default `"end"`): the rail sits at the page's left edge, and an end-aligned menu would extend left, off-screen. **How to apply**: a control that must offer more than one gesture from a narrow rail is this pattern, not a second icon stacked under the first — two similar glyphs are harder to tell apart than one glyph plus written-out menu items.

**A menu is drawn in a PORTAL at fixed coordinates, never `absolute` inside the thing it belongs to (2026-09-21, reported on the Develop gallery: "parfois il passe en dessous ou au-dessus de la cellule que je survole").** A card is `position: relative`, so every card in a grid is a positioned element with `z-index: auto` and they paint in TREE order: a menu inside card 1 is painted with card 1 and the card AFTER it paints over the menu, whatever `z-index` the menu carries — raising the menu cannot win, only raising the whole card could, and the card below would then be the one on top. The page's own scroll container (`pageScroll`, `overflow-auto`) clips the same menu on the bottom row. `OverflowMenu` therefore renders through `createPortal(…, document.body)` at `position: fixed`, placed by `shared/ui/menu-anchor.ts` (DOM-free, tested) from the trigger's rect and the menu's measured size: `side`/`align` became a PREFERENCE — it flips above when the bottom cannot hold it, slides back in from either edge, and keeps `MIN_ROOM` and scrolls when nothing fits. `z-[70]`, above every modal (`z-50`) and the raised library sheet (`z-[60]`), because a menu opened from a sheet must not be swallowed by it. Three things the portal costs, all of them in the component already: the outside-`pointerdown` close tests the trigger's box **and** the menu's, which are now in two places in the document; the menu re-places on `resize` and on `scroll` **with `capture`**, since a scroll in an ancestor does not bubble to the window; and it is measured with `scrollHeight` so a re-place cannot chase its own `maxHeight`. **How to apply**: any popover anchored to a control that lives inside a list, a card or a scroller goes through `OverflowMenu`, or through `menuAnchor` in the same shape — never a fresh `absolute` + `z-index`. The masthead's `ToolSwitcher` is the second consumer of `menuAnchor` (2026-09-21): hung `absolute left-0` from a trigger ~100px into the bar, its 22rem menu ran past the right edge of a 390px phone and cut the second column of instruments off — a `max-w-[calc(100vw-…)]` caps a width, it does not move a left edge. An anchored menu slides back inside the viewport and caps its height, so a landscape phone scrolls it. Verified in headless Chromium at 1280×800, 900×560 and 390×844: `elementFromPoint` inside the menu is the menu at the top of a grid, at its last row and on a phone; it stays 6px under its trigger through a scroll, and Escape, an outside press and picking an item all still work through the portal.

**Nothing MOVES under the pointer (2026-09-21, the maintainer's ruling).** A card's hover said `hover:-translate-y-1` (`hover:-translate-y-[3px]` on the home doors, `hover:-translate-y-px` on three legacy buttons): *"ça le fait monter ou descendre … ce n'est pas du tout une approche UX que j'apprécie"*. A hover may change the SHADOW and the BORDER — both are wanted, and both say "this is live" without the pointer chasing a target that slid — and nothing else; Trips' own card was already this shape and is the reference (`transition-[box-shadow,border-color] … hover:shadow-paper`). The Develop and Studio cards, the home doors, the telemetry and EXIF cards and the three transcode/retry buttons now match it, `transform` gone from each `transition-[…]` with it. **How to apply**: a new hover state is colour, shadow or border; a translate, a scale or a rotate on hover is a regression, and one on a card under a portalled menu was also the stacking context nobody asked for.

**Tailwind trap: two utilities of one property are resolved by Tailwind's order, not the class list's (2026-09-13).** `IconButton` appended `px-0` after `Button`'s `px-2.5` and lost: the padding stayed, the 28px button had 8px of content and the glyph shrank to 6px wide (measured). `buttonClass` therefore keeps padding SEPARATE from height (`{ square: true }` omits it) rather than overriding it. **How to apply**: never "override" a utility by appending another value of the same property — split the recipe so the conflicting one is not emitted.

**A date is entered through `shared/ui/DateField` (and `DateRangeField`), never a bare `<input type="date">` (2026-09-13).** The native input STAYS — invisible, full-size, on top — so the keyboard, the screen reader and a phone's wheel keep it; what is seen is the suite's own dress (the date as `formatIsoDate` writes it, mono, a calendar glyph, the control radius). `showPicker()` is asked for on click where the browser has it. Eight native fields across the trip screens broke the paper with the platform's format and font; `DayPicker` is a different thing (a day stepper over a density strip) and was never one of them.

**Trap: a dialog rendered inside a clickable card bubbles its clicks into that card (2026-09-13).** React events bubble through the component tree, so `ConfirmDialog` mounted inside a gallery card whose own click OPENS the document turned "Delete" into delete-then-open — and the opened Studio editor saved the project straight back, so deleting looked done and came back on reload. `ConfirmDialog` now stops click propagation at its root, and a clickable card ignores clicks from anything interactive inside it (`closest('button, select, input, a, [role="menu"], [role="alertdialog"]')`). **How to apply**: any overlay (menu, dialog, popover) mounted inside a clickable container stops its own clicks; verify a delete by RELOADING, never by reading the list the click just updated.

**Trap: a file or folder picker opens only inside the click's transient activation, and Chrome grants about FIVE SECONDS of it (2026-09-20, the maintainer's "export the roll does nothing").** `showDirectoryPicker` — and `showSaveFilePicker`, `showOpenFilePicker` — throw `SecurityError: Must be handling a user gesture` once the activation has expired (measured in headless Chromium: honoured at the click, refused 6 s later, `navigator.userActivation.isActive` false). Every await between the click and the picker eats into the window, so a picker asked for AFTER a render opens for one quick picture and never for a roll, a deck or a clip — and a caller that reads every rejection as "dismissed" then writes nothing and says nothing. `shared/sources/deliver-files.ts` is the shape to copy: `pickDeliveryTarget()` FIRST, from the click, then the render, then `deliverFilesTo(target, …)`; the Studio's own "Folder…" button is the same rule in another dress. A dismissal (`AbortError`) is the only rejection to swallow; a `SecurityError` is said. **How to apply**: never put an `await` of unknown length between the gesture and a picker, and never catch a picker's rejection without looking at its name.

**Every side panel speaks ONE grammar: folding sections of label-and-control rows (2026-09-13, the maintainer's ask against the audit's mock).** `shared/ui/Inspector.tsx`: `InspectorSection` (title, optional badge, prose behind an ⓘ, a chevron, the whole header band folding it, the fold remembered per id under `atelier.inspector.<id>`, a rule between sections), `FieldRow` (label in a 5.75rem column, the control at the right, a hint sentence under the control), and the three controls a row most often holds — `RangeField` (value beside the track, never in the label), `SelectField` (a native select in the suite's dress), `ToggleField` (a switch) — plus `Readout`. **How to apply**: a new panel control is a `FieldRow` inside a section, a mode picker is a `SelectField` whose option text carries the real line (or why not) with the chosen line repeated as the hint, and a standing paragraph is the section's `info`. The rules between inspector sections are wanted — they part blocks of settings in one column — even where the maintainer removed rules between page regions. `ModeChoice` (the card of modes) was retired for it.

**A section folds from its WHOLE header band, and a docked inspector is a rounded box (2026-09-14, the maintainer's ask).** He kept hunting for the 28px chevron, so a click on the title, the badge, the empty stretch or the chevron folds. The band cannot be one `<button>` (the ⓘ and `actions` are buttons inside it), so the header div listens and folds only for a click on itself or on a child marked `data-fold`; everything else (an action, the ⓘ, the note it unfolds, a portalled menu) is ignored by that whitelist — never switch it to a blacklist of interactive tags, the ⓘ's note is plain text. The title stays the one real button (`aria-expanded`), and the chevron is an `aria-hidden` span. Both editors' docked inspectors wear the same frame — `border border-line rounded-paper bg-surface p-3` around the `Segmented` strip and the sections — while the piece editor's PageBar (Overview · Trip · Export) and name stay OUTSIDE it, above, as he asked. **How to apply**: a new foldable header marks its non-interactive parts `data-fold` rather than adding a second click handler; a new docked inspector takes that frame.

**Light · dark · system: the theme is a stored PREFERENCE and a stamped RESULT (2026-09-13).** `shared/ui/theme.ts` (pure, tested) resolves `ThemePref` (`system` follows the OS live) to `data-theme="light|dark"` on `<html>`; `index.html` runs the same arithmetic inline before paint (no flash of paper for a dark reader) and rewrites `theme-color`; `use-theme.ts` keeps it in step and `app/ThemeToggle.tsx` cycles system → light → dark from the masthead (monitor · sun · moon; three states, not Winnow's two, because a chosen theme must be able to hand control back to the OS). The dark tokens are Winnow's night palette (`#16130e` paper, warm off-white ink, the accent lifted), declared BEFORE the darkroom block so a grading screen is neutral grey under either theme. **How to apply**: a colour that looks wrong in the dark theme is a hex that should have been a token — `HEATMAP_LEVELS[0]` became `var(--color-paper-2)` for exactly that (bare paper is near-black at night, and a hex drew every untold day as a bright tile). Key: `atelier.theme`, absent = system.

**The DARKROOM: a grading screen sits on neutral grey, the rest stays paper (2026-09-13, the maintainer's ruling).** Warm paper beside the picture biases colour judgement (the eye adapts to the cream and reads the frame colder), so the Studio editor and the piece editor call `useSurface('darkroom')` (`shared/ui/use-surface.ts`, mounts counted) which stamps `data-surface="darkroom"` on `<html>`; `index.css` redefines the SAME tokens under it — hue-less greys, the accent unchanged, `accent-wash` translucent, the state trios lifted for a dark ground, no paper glow (`--color-paper-glow` is a token now) and no grain, `color-scheme: dark` for native controls. Galleries, overview and home keep Studio Papier: the identity steps back only where the picture is judged. **How to apply**: never hand-tint a component for the darkroom — if something looks wrong there, it is a raw colour that should have been a token (the lint rule catches new ones; the few `rgba(251,248,241,…)` chips predate it).

**`surface` vs `paper-2` is a weak edge in the dark theme and the darkroom — do not rely on that gap alone to show "chosen" (2026-09-14, reported: the piece editor's Segmented tabs were unreadable at night).** In light mode `Segmented`'s selected tile read fine off `bg-surface` + a black-rgba shadow over `bg-paper-2`; at night `surface`/`paper-2` sit only ~2-3 hex steps apart AND the shadow (pure black rgba) is invisible on an already-dark ground, so the raised tile vanished. Fixed by giving the chosen segment a real edge, `border-line-strong` (transparent when unselected, no layout shift) — `line-strong` keeps enough lightness contrast against `paper-2` in every theme, same recipe `Button`'s `default` variant already used. **How to apply**: a "selected/active" state built only from a `surface`-vs-`paper-2` background swap (± a shadow) needs checking in the dark theme and the darkroom, not just light — prefer pairing it with a `line-strong` border, which is what stays legible everywhere.

**The home is a DOOR per editor over a list, not equal cards (2026-09-13, the maintainer's ruling; rev. 2026-09-21).** Each door SHOWS the document this browser touched last and OPENS that editor's gallery — the Studio `listProjects()[0]` with its baked thumbnail, Trips `listTrips()[0]` as a 60-cell strip, Develop `listRolls()[0]` as its first thumbnails, each over `#${tool.path}`; the other pages are a compact list under "Instruments", the word the tool menu uses. **The door used to open that document itself** ("each with its resume point", agreed in the audit's third pass, 2026-09-13) and the maintainer took it back on 2026-09-21: *"je préfère que ça ouvre vraiment la galerie et ensuite moi je choisis le projet"*. The reason, worth keeping because it generalises: a "last document" destination is right only when you came back for the same thing, and wrong silently the rest of the time — it loads a project, its media and its folder permission for you to leave again. Showing the document and opening the choice keeps the half that was useful. The verb is therefore **Open** at every state (never "Resume"), a `last` that is information and never a destination; resuming is one click from a gallery that already sorts newest-first and marks the open document. **How to apply**: nothing on the home page navigates to a document — a second, explicitly worded "Resume" link inside a door was offered at the same time and declined; a card with two targets is what the gallery cards' own rule avoids. A door is looked up by tool id (`DOORS` in `Home.tsx`, `PlainDoor` for an editor without one), never a branch; the row is one column, then three from 900px, because two columns strand the third door alone. `Tool.subtitle` is the instruments' one-line caption there.

**Waiting, emptiness and a yes/no question each have ONE shape (2026-09-13).** `shared/ui/LoadingState` (+ `Spinner`), `EmptyState` (framed: serif title · one sentence · the Button that fills it; `compact`: the sentence alone, for a rail) and `ConfirmDialog` (the title IS the question, `danger` paints the yes and keeps Enter from firing it, focus lands on the safe answer). The galleries' delete went from an inline "Delete · Keep" pair to the dialog, because the verb is moving into an overflow menu where nothing can unfold. **How to apply**: a new "Loading…" line, dashed box or two-step confirm is a regression — use these; a row's inline confirm (`DayPanel`) may stay inline where the verb has room.

**The type scale is NAMED, and a raw hex is a lint error (2026-09-13).** Text sizes are Tailwind's named steps plus `text-2xs` (0.66rem, the mono eyebrow labels) and `text-3xs` (0.58rem, a caption under a thumbnail); state colours are the `danger` / `ok` / `warn` / `info` trios (ink, `-wash`, `-line`, plus `warn-bright` for a pulsing dot) declared beside the accent. `eslint.config.js` refuses `text-[…rem|px]` and any `-[#hex]` utility with `no-restricted-syntax`, so the 43 hand-picked sizes and 47 raw hexes the audit counted cannot come back. **How to apply**: pick the nearest named step; if a size genuinely has no step, add one to `@theme` with its `--line-height`, never an arbitrary value. Migration mapping used, for the record: ≤0.61rem→3xs · ≤0.71→2xs · ≤0.81→xs · ≤0.93→sm · ≤1.07→base · ≤1.22→lg · ≤1.37→xl · ≤1.6→2xl · else 3xl.

## The home-screen icon is a PNG set, and an SVG favicon is not one (2026-09-10)

**Reported**: the icon was right on the home screen for Winnow and wrong for Atelier, on Chrome for iOS. **Cause**: Atelier declared one thing, `<link rel="icon" type="image/svg+xml">`. iOS builds a home-screen icon from `apple-touch-icon` **only** — a PNG, square, opaque — and ignores `rel="icon"` whatever its type; with no such link it screenshots the page instead. Chrome for iOS is WebKit, so it reads exactly what Safari reads: the browser makes no difference, the missing tag does. Winnow shipped the full set from the start, which is the whole of the difference.

**The set, and it is the same in every repo of the portfolio** (`COMMON-PROJECT-SPEC.md` in `second-brain` carries it as the cross-repo contract): three SVG sources in `public/icons/` — `icon.svg` (rounded tile), `icon-apple.svg` (**full-bleed**, no corner radius of its own) and `icon-maskable.svg` (full-bleed, inverted, art inside the safe zone) — rasterised by `scripts/gen-icons.mjs` into seven **committed** PNGs: 192/512 any, 192/512 maskable, `apple-touch-icon.png` at 180, and 16/32 favicons. A static host cannot rasterise on request, so the output is tracked; the SVG alone is not what ships to a phone.

**Traps, each one measured here:**
- **Transparency is black on iOS.** A touch icon with rounded corners of its own comes back framed in a dark vignette under Apple's mask. Hence the full-bleed Apple source and the one `flatten()` in the generator — the other outputs keep their alpha, where it is wanted.
- **Vite rewrites `/…` hrefs in `index.html` with the base path** (verified in `dist/` at `BASE_PATH=/atelier/`, `rel="manifest"` included), so absolute paths there are correct and survive both the custom domain and a `/atelier/` preview.
- **It does not rewrite anything inside `public/manifest.webmanifest`** — that file is copied verbatim. Its `icons[].src`, `start_url` and `scope` are therefore **relative** (`icons/icon-192.png`, `./`), which resolves against the manifest's own URL and is right under either base. An absolute `/icons/…` there 404s on any base but `/`.
- The manifest is the **Android/Chrome half** and carries no weight on iOS. It is not what fixed this, so do not let a manifest question (its MIME type on Pages, say) hold up the touch icon.

**`display: "standalone"`, and the status bar is what bought it (2026-09-10).** It shipped as `browser` that morning, because Atelier's projects and trips are in this browser's IndexedDB and a home-screen launch can be given a storage container of its own — then the maintainer reported the status bar staying **system white** over the paper and asked for the colour, having weighed that cost and taken it. **The colour was never the missing part**: `theme-color` was declared in `index.html` and as the manifest's `theme_color`, survives the build (checked in `dist/`) and was deployed — a screenshot of his phone measures `#ffffff` in the bar and the paper gradient exactly right one pixel below, so the chrome was refusing a colour it had. A browser tab tints only if it feels like it (iOS has a per-device *Allow Website Tinting*); an installed app is told. So the lever is the launch, not the value: `display: standalone` plus **`apple-mobile-web-app-capable`** and **`apple-mobile-web-app-status-bar-style: default`**, which is the iOS half — iOS reads no manifest for this. `default` is the LIGHT style (dark glyphs over the theme colour); `black-translucent` would put white glyphs on cream and slide the page under the bar. `viewport-fit=cover` is deliberately NOT set: without it iOS keeps the web view inside the safe area and paints the inset itself, which is exactly the wanted result and leaves every existing layout alone.

**The cost is real and must be said out loud when it bites**: on iOS a home-screen app has its own storage, so a trip made in Safari is not in it. The ways across are an export/import (`.roadtrip.json`, `.atelier.json`) or keeping the document on a Winnow. Android shares one origin between the installed app and the browser, so nothing is lost there.

**How to apply**: change the mark in the three sources, then `npm i --no-save sharp` (it must never enter `package.json` — CI would pay for a native install on every job) and `node scripts/gen-icons.mjs`, and commit the PNGs in the same commit. The paper `theme-color` and `apple-mobile-web-app-title` sit beside the links in `index.html`; there is one theme (`color-scheme: light`), so one `theme-color`.

## A fixed edge takes no gutter (2026-09-10)

**Reported from a phone, once the document was locked and the masthead and the section bar became fixed by construction**: a stripe of paper between the masthead's border and the content, with the first card cut across. Measured at 390×844: header `0→48`, the tool's SCROLL CONTAINER `56→779`, the bar `787→844` — `<main>` was paying an 8px vertical gutter, so the scroller began 8px inside the chrome and clipped its content against a gap.

**The rule.** A gutter between a fixed edge and a scroll container is not spacing, it is paper the content gets clipped against: the content scrolls to the SCROLLER's edge, never to the screen's, so whatever sits between the two is permanently visible and permanently cut. Breathing room therefore belongs **inside** the scroller, where it scrolls away with the first row — `pt-3` on the two galleries' own sections, not on `<main>`. The sides keep their gutter (`px-2`): nothing is clipped horizontally, and a card touching the screen edge is a different fault.

**What is still owed at the bottom**: the bar pays `env(safe-area-inset-bottom)`, and since 2026-09-10 a compact tool screen always has one, so `<main>` owes nothing.

**The same rule read from the other end: a scroller owes air at its END (2026-09-11).** `<main>` paying a gutter is the stripe above; the scroller paying nothing is the complaint that followed — *"in the bottom of the pages we lack of padding"* — because the scroller's bottom edge IS the bar's top, so the last card in a column landed against it with nothing between. A `gap-4` between cards does not put anything after the last one. **`shared/ui/page-scroll.ts` is now the one class the three tool SCREENS scroll in** (the trip overview and the two galleries), `pb-4` included and unconditional: above a phone the frame's own `pb-3` sits OUTSIDE the box, so the last card was landing on the frame's edge there too. They had already written those five classes by hand and already drifted — two paid `pt-3` at compact and the third did not. The TOP deliberately stays out of it: `PageBar` clears the masthead itself, and a screen without one adds its own. **And at its SIDES (2026-09-13)**: a scroll box clips both axes, so the selected day's 2px outline (offset 1) on a short trip's strip was cut off against the scroller's flush left edge. `pageScroll` now carries `-mx-1 px-1` — 4px of air inside, borrowed from the frame's `px-4`, so nothing moves. Anything drawn OUTSIDE an element's box (outline, ring, a corner badge) must fit in that 4px or bring its own inset.

**Verified** at 390×844 with a list long enough to scroll: the scroller runs `48→787`, flush with both, and scrolled content reaches the masthead's border with no stripe.

## The shell wears THREE layouts, and names them once (2026-09-10)

**Decision, the maintainer's, taken off an interactive artifact showing all three widths side by side.** How much room the shell has is decided in ONE place — `shared/ui/layout-mode.ts`, DOM-free and tested — and published by the shell through `use-layout-mode.tsx` the way a tool publishes its media scope, inverted: `compact` (< 820px, a phone: the stage owns the screen, the tool's sections sit in a bottom bar, the panels are sheets over it), `medium` (820–1179: the library still docked at the left but collapsed to its rail, so a tool keeps the width its own layout needs), `expanded` (≥ 1180: the docked full library · stage · inspector, unchanged). **Why a published name rather than a utility**: the rule was spread by hand across dozens of literal `max-[820px]:` utilities in fourteen files, each re-deciding what small meant, and none of them able to say what the shell should DRAW at that width.

**820 keeps exactly its old meaning, so adoption is additive** — every utility already measured at 390, 744, 834 and 1280 stays correct, and only the upper boundary (1180) is new. `modeForWidth` is bottom-exclusive where `max-[820px]:` is inclusive, so the two disagree at exactly 820px and nowhere else; that pixel is the price of not re-tuning verified work, and is deliberate.

**This is NOT the query a tool's own layout splits on.** The container-query rule stands (`studio.md`, and «A stage that must fill the height» below): the Library rail eats 288px no viewport query can see, so a tool's internal columns stay on `@container`. A `LayoutMode` answers a different question — which chrome the SHELL wears, and therefore whether a tool draws its own tabs or hands its sections to the shell's bar. A tool reads the mode for that decision alone.

**What `compact` actually draws (2026-09-10).** The shell keeps its **fixed `h-dvh` at every width** — it used to give it up under 820px (`h-auto min-h-dvh`) so the page could scroll, and that is precisely what turned the suite into a stack (library card first, editor third, a 240px stage on an 844px screen) *and* what made every height above a stage indefinite. ## The Library's day is a stepper over a density strip, never a date field (2026-09-08, rev. 2026-09-09)

**Decision.** The Winnow tab picks its day with a **stepper** — `‹ Tue 8 Sep 2026 ›` in the mono face, a reading line under it (`● today · nothing here`, `● 24 days ago · 19 files`) — and the value opens the month as a **density strip**: one bar per day, height normalised to that month's own peak (`shared/sources/winnow/day-density.ts`, pure and tested), a month header whose arrows stop at the instance's `bounds`. **Why**: the verb in that rail is *browse the days around a shoot*, so stepping is the common move; and the question a picker has to answer at 288px is *which days have footage on them*, which a grid of empty squares cannot. `/api/assets/calendar` answers a span with a count per day **plus a library-wide `bounds`** — confirmed in Winnow's own route, which computes bounds ignoring the window — so the shape is read, never estimated. A month/year select was considered and refused: it lands you in a month you would then walk blind.

**Two readings, one click apart.** The strip and a mini **calendar** (fixed-height cells, never `aspect-square`; counts drawn in the cell) are both bodies of the same panel, toggled by a glyph at the end of the month header and remembered in `localStorage` (`atelier.library.month-view`). ## Waiting never looks like an answer (2026-09-09)

**Reported, and it cost the maintainer real time**: walking the day picker's months, an unanswered month drew as thirty empty bars — indistinguishable from a month holding nothing — so he moved past months that turned out to be full, and learnt to sit and wait rather than read the control. The tile grid had the same shape: `rows === null` drew nothing at all.

**How to apply.** Any pane that waits on an instance draws a **busy state that cannot be mistaken for a result**: the day picker's month body keeps its days but at a uniform height, dimmed, pulsing and inert (`aria-busy`, `pointer-events-none`, `motion-reduce:animate-none`); `WinnowScopeGrid` draws eight skeleton tiles in its own grid; the reading line's dot pulses while its span is out. ## A control row wraps; the shell clips — nothing scrolls the page sideways (2026-08-22)

**Trap, measured.** The studio's transport was one flex row of `flex-none` chips (play, clock, trim rail, duration, loop, shutter, preview speed, A/B). Each feature added one more, and on a 390 px phone the last one landed at x=437: the whole **document** gained a horizontal scrollbar and the interface drifted into the margin. Nothing was clipped, so nothing looked broken — it just scrolled sideways.

**The shape to keep.** The row is **two groups** inside a `flex-wrap` container: the *rail* (play, timecode, trim, duration) with `grow shrink basis-[15rem] min-w-0`, and the *tools*, itself `flex-wrap max-w-full`. Flex breaks lines before it shrinks, so the tools drop to a line of their own instead of pushing the last chip off the edge — and if even they cannot share one line, they stack. **How to apply**: a new transport control goes in the tools group and costs nothing; a new *row* of controls anywhere follows the same two-group shape.

**The net, and where it actually works.** The tool shell (`src/app/App.tsx`) clips on desktop but switched to `overflow-visible` under 820 px, which is what let the overflow reach the document. It is now `overflow-x-clip` + `overflow-y-visible` there: sideways it clips, vertically the page still scrolls normally (verified: a 2 000 px child no longer moves `window.scrollX`, a 2 000 px-tall one still scrolls). `clip`, not `hidden` — it establishes no scroll container, so sticky positioning inside the page keeps working, and `position: fixed` modals still cover the viewport (verified at 390 and 1400). **Do not** put this on `html`: Chromium computes it there but does not propagate it to the viewport, so the page scrolls anyway — measured, and the reason the rule sits on the shell.

## MapLibre's own CSS can collapse its container (2026-08-20)

**Trap.** MapLibre adds `.maplibregl-map` to its container, and that stylesheet — loaded *after* Tailwind — sets `position: relative`, overriding an `absolute inset-0` container and dropping it to `height: 0`. The symptom is a black map with the overlays still visible. **Remedy**: give the map container a real height as a flex child (`flex-1 min-h-0`), never rely on absolute positioning, and call `map.resize()` once the style loads as insurance against a 0-size measurement during the async (dynamic-import) mount.

## MapLibre is dynamically imported, JS *and* CSS (2026-08-20)

**Decision.** `use-flight-map.ts` and `use-composer-map.ts` import MapLibre lazily. **Why**: it is a heavy dependency and only two tools use it; static import would put it in the main bundle for everyone. **How to apply**: keep the import inside the hook, and keep the "map failed to load" state — the caller shows a fallback instead of a broken pane. The live-position marker uses inline styles so it never depends on the CSS scanner picking up dynamically-built class names.

## Canvas text needs fonts explicitly loaded (2026-08-20)

**Trap.** `fillText`/`measureText` only render and measure correctly with faces the document has actually loaded; the brand fonts arrive asynchronously, so an overlay drawn too early measures against a fallback and exports mis-sized text. **Remedy**: `overlay/fonts.ts` calls `document.fonts.load(...)` for each used face and awaits `document.fonts.ready` before the first measured draw and before export. System fonts (Arial/Georgia/Courier) need no loading. Any new canvas text path must go through the same helper.

## The file picker must listen to `cancel`, not guess (2026-08-20)

**Trap.** The old "did the user cancel?" heuristic (focus + timeout) raced the `change` event: when the page was busy — a video playing in LUT Studio — the timeout fired first and a real selection was silently discarded. **Remedy**: `shared/sources/file-sources.ts` uses the native `cancel` event (Chrome 113+, Firefox, Safari 16.4+), so a successful pick always resolves through `change` no matter how busy the page is. The transient `<input>` is attached to the document but kept out of layout so events fire reliably across browsers.

## Keyboard shortcuts live in the shared hook, and yield to the focused element (2026-08-21)

**Decision.** Space plays/pauses, and the binding sits in `shared/media/use-video-transport.ts` (opt out with `spaceToggles: false`), so Studio, Grade, Compare, Composer and the legacy Overlay all get it from the one transport instead of five copies. It listens on `window`, not on the stage: in most tools the element that actually plays is a 1px off-screen `<video>` feeding a canvas, so there is nothing meaningful to focus. **Why the guard matters**: space is also the browser's activation key for buttons and a character in every field, so `transport-keys.ts` (pure, tested) decides whether the focused element has the stronger claim — fields, contenteditable, `BUTTON`/`SUMMARY`/`VIDEO`/`AUDIO`, and the ARIA widget roles — and when it does the handler returns *without* `preventDefault`, or the play button would stop working the moment it has focus. **How to apply**: a new global key goes through the same predicate, and any new one must also skip `e.repeat` (a held key would toggle forever) and modified presses. Tools whose `<video controls>` is the visible player (Telemetry, Flight Map) deliberately keep the browser's native space handling — Telemetry shows several cards at once, so a global key would have no obvious target.

**Trap.** The listener is mounted once (deps `[spaceToggles]`) and calls `togglePlay` through a ref refreshed on every render. Re-wiring it on `resetKey` like the media listeners looked equivalent and is not: Compare's `togglePlay` closes over `aIsVideo`/`bIsVideo` state, and a stale closure would toggle the wrong pair after a swap.

## ⌘Z is the third window-bound key, and the one that may repeat (2026-09-15, rev. 2026-09-16)

**Decision.** `shared/history/undo-keys.ts` is the third key-ownership module beside `transport-keys.ts` (space) and `dialog-keys.ts` (Enter, Escape), bound on `window` by `use-history.tsx`. It yields to ONE thing only, and narrowly — a place where TEXT is being typed, where ⌘Z is the browser's own undo of the letters and taking it would throw a half-typed name away to step the whole document back instead. A focused BUTTON keeps nothing here (a button undoes nothing of its own), which is the same narrow/wide split the trim keys taught: `targetOwnsSpace` for a toggle, `targetOwnsTyping` for everything else.

**Trap (2026-09-16, the maintainer's "undo redo dont work in develop").** It is narrower than `targetOwnsTyping`, which answers for a TAG: an `<input>` is an input to the letter shortcuts, but a `type="range"` holds no text and has no undo of its own to protect — and every number in the suite is a `RangeField`, an `<input type="range">` that a drag leaves FOCUSED. Standing down for it swallowed every ⌘Z from the first edit onwards, worst in the Develop tool where a slider is most of the tool. So `KeyTarget` carries the input's own `inputType` (filled by `describeKeyTarget`, ignored by space and the letter keys) and `undo-keys.ts` asks its own question: contenteditable and `<textarea>` yes, `<select>` no, `<input>` only when its type is not one of the textless ones (range, checkbox, radio, colour, file, the button types). **An unknown type keeps the field's claim** — guessing wrong that way costs a step, the other way it eats a half-typed word.

**How to apply.** Both accelerators are read on every platform rather than sniffing for a Mac — ⌘Z / ⇧⌘Z and Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z — since a browser on either can be driven by the other's keyboard; exactly one of ⌘/Ctrl must be held and Alt never. It `preventDefault`s when it acts, or the browser's own undo fires as well on whatever field it last touched. **A held key repeats here, deliberately**, against the rule the space key set: space is a toggle, where a repeat flips the transport forever, while holding undo to walk back a stack is what every editor does. The accelerator is shown in the button's `title` only, never drawn beside it.

## Escape and Enter are one hook, and Enter yields to the focused element (2026-09-08)

**Decision.** Every modal binds its two keys through `shared/ui/use-dialog-keys.ts` (over the pure `dialog-keys.ts`, tested), never a hand-written `window` listener: Escape dismisses the sheet, **Enter runs its primary action** — Save, Create trip, Apply, Add to library, and in `TripSettingsModal`, whose fields autosave on every keystroke, closing it. **Why**: nine modals each carried the same Escape effect and none acted on Enter, so filling a form ended with a reach for the mouse — typing a date and pressing Enter did nothing. A per-field `onKeyDown` was the old answer and is now wrong: it fired only in the one input that had it, and left beside the hook it submits **twice**. Remove it when you adopt the hook.

**How to apply.** Pass `onConfirm: null` — never a no-op — whenever the CTA would be disabled (`canSubmit`, `picked.length`, a ticked diff) or a question is already on screen waiting for its own answer (`ProjectSettingsModal`'s "Replace the settings / Keep mine"); read the very condition the button carries, so the two can never disagree. `dialog-keys.ts` decides who owns the press, the twin of `transport-keys.ts` for space: a textarea, a button, a link, an `<input type=file|checkbox|…>`, a contenteditable and the ARIA widget roles keep Enter, while a text, date or `<select>` field yields it — which is exactly the browser's own form behaviour. A field that handles Enter itself calls `preventDefault` (`PlaceSearchField` looks a place up), and the hook stands down on `defaultPrevented`; a nested control that must keep Enter therefore has to say so on the event, not hope.

**Verified** in the dev server: Enter from the New-trip date field created the trip, Enter with an empty name (disabled CTA) did nothing, Enter in the From field opened the place-search consent instead of submitting, and Escape still closed the sheet.

## Library thumbnails always letterbox in a fixed box; the kind chip is a third text line (2026-08-22, rev. same day)

**Decision.** `AssetSidebar.tsx`'s `AssetRow` thumbnail is a **fixed 80×56 box for every row, unconditionally** — never resized per asset. The `<img>` is always `object-contain` (never `object-cover`), so a landscape/square clip fills the box width-first same as before, and a portrait clip pillarboxes with black bars left/right inside that same box, exactly mirroring how the tools' own video players letterbox a mismatched aspect ratio. **Why fixed, not variable-width** (rejected 2026-08-22 same day): an earlier version shrank the box width for portrait media so it would visually "stand up" — technically fine, but it made every row's thumbnail a different size, so titles no longer started at the same x and the list read as disordered. The maintainer explicitly wants one uniform thumbnail footprint with the orientation cue coming from the *letterboxing*, not the box shape — the same compromise the video player already makes.

The kind chip (`video+srt`, `video`, `photo`, …) is back to its original full-word pill (`kindLabel()`/`chipClass()`), but as a **third line in the text column** (`flex flex-col`: title, facts, chip — `self-start` so the pill doesn't stretch) instead of beside the name or on the thumbnail. **Why not on the thumbnail** (also rejected 2026-08-22): the frame already carries up to two scrims (cadence top-left, fps bottom-left) and a third corner badge reads as cramped/overlapping, especially once the thumbnail was still variable-width. Three text lines fit inside the existing 56px thumbnail height without growing the row.

**Trap, measured in this environment's headless Chromium (Chromium 141, software rendering, `--headless=new`).** The thumbnail wrapper was `grid place-items-center`; changing the `<img>` to `object-fit: contain` with `width:100%; height:100%` silently stopped letterboxing — the image filled the box edge-to-edge regardless of its real aspect ratio, confirmed with a plain PNG (not just an SVG data URI, ruling out a data-URI/intrinsic-size issue) and reproduced with `viewBox` present. The identical percentage-sized `<img>`/`object-contain` combo inside a **flex** parent (`display:flex; align-items:center; justify-content:center`) or a plain block parent rendered correctly every time. **Remedy**: the wrapper is `flex items-center justify-center`, not `grid place-items-center` — swapped here and worth defaulting to for any future `object-fit` content on a centred replaced element, since flex reproduced correctly across every variant tried and grid did not, in this environment, regardless of whether `place-items` was set. Not confirmed whether this is a genuine cross-browser Blink bug or an artifact of this sandbox's software rasterizer — treat it as "flex is the proven-safe choice for object-fit centering here," not as a general indictment of CSS Grid.

**Verified** by screenshotting the compiled Tailwind output (`dist/assets/*.css`) against a static harness of landscape/portrait/square/photo rows with real (generated) PNGs in headless Chromium — this is what caught the grid/object-fit trap above; an SVG-only harness had masked it behind a different, coincidental failure mode.

## Tools own full height; only the inner list scrolls (2026-08-20)

**Decision.** The shell gives each tool a full-height frame and the tool's own gallery scrolls inside it (`349ea08`). **Why**: a page-level scroll fought the stage/preview layouts. **How to apply**: a new tool that needs a scrolling list scrolls it internally rather than growing the page.

## A modal is a full-screen sheet under 820px, and shows ONE pane at a time (2026-09-02)

**Trap, seen on an iPad.** `WinnowBrowser` is a fixed-height card (`h-[min(90vh,52rem)]`, `overflow-hidden`) holding a two-column grid that switched to `grid-cols-1` under 820px. Stacking put two panes in a height that never grew: the pictures pane landed *on top of* the calendar, clipped, and its "Choose a day on the left." sat across the grid. **The shape to keep**: below 820px the modal is the whole screen (`max-w-none h-dvh rounded-none border-0`, overlay `p-0`, `pb-[max(1rem,env(safe-area-inset-bottom))]` so the actions clear the home indicator) and only one pane is rendered — the picker until something is chosen, then the results with a back control (`hidden max-[820px]:inline-flex`). A drill-down, not a stack; the header, the filters and the action row stay pinned around it, and only the middle scrolls.

**A viewport query IS right for a modal** — the container-query rule (`studio.md`, `roadtrip.md`) exists because the Library sidebar eats 288px a tool cannot see; a `position: fixed` overlay spans the viewport, so `max-[820px]:` measures exactly what the sheet gets. Use `dvh`, never `vh`: on iOS Safari `vh` is the *large* viewport, so a `max-h-[90vh]` card can hang behind the toolbar with its Apply button under it.

**`hidden` loses to a base class carrying `inline-flex`.** Tailwind orders `display` utilities in its own layer, not by the order written in `className`, so `` `${pill} hidden max-[820px]:inline-flex` `` rendered the control at every width (measured at 834px). A conditionally-hidden button spells its own classes out rather than borrowing a shared pill. **Not just `display`**: `w-40 … max-[820px]:w-full` on the LUT gallery's search field measured 197px wide on a 390px viewport (`LutGalleryModal`, 2026-09-18) — same layer-ordering trap, on `width`. The fix that holds for any property: give the responsive-only element its OWN row/className rather than layering a base utility and a `max-[…]:` override of the same property on one element.

**Touch sizing, applied at the same breakpoint.** Controls go up a size and any `<select>` or `<input>` reaches **16px** — below that, iOS zooms the page on focus and never zooms back. The 16px is for the PHONE only: a field that wears it at every width looks oversized beside its own `text-xs` buttons (the maintainer's report on the preset-name field, 2026-09-16) — write `text-xs max-[820px]:text-base`. **Since 2026-09-22 that rule is written ONCE, in `index.css`**: an unlayered `@media (max-width: 820px) and (pointer: coarse)` rule gives every text `input`, `select` and `textarea` `font-size: max(1rem, 1em)`, because the sheets that forgot the per-field spelling (the Library's filter, a leg's name, a place, the deck's speed select) zoomed the phone one by one. A field already at 16px or more is left alone; the one thing it can do wrong is shrink a field larger than its parent's size to 16px, which no phone field is. **And a verb revealed on hover is SHOWN on a touch screen** (`pointer-coarse:`, Tailwind's own variant): the element list's × and the filmstrip's × were `opacity-0 group-hover:opacity-100` — on a phone that is no way to delete an element and no way to take a picture off the roll (the filmstrip's was even `max-[820px]:hidden`), and on a touch tablet above 820px an invisible control that still answers a tap. On a coarse pointer they are visible and a size larger. That is also why two native date fields no longer share a 390px row (`NewTripModal`), and why the filter selects wrap two-per-line on a phone (`basis-[10rem]`) instead of one being squeezed against the tabs. Calendar cells drop `aspect-square` when the calendar owns the full width (100px-tall squares on an iPad) for a `min-h-[3.5rem]` band.

**Long action rows follow the two-group shape** documented above for the transport: `[choice + hint]` with `grow shrink basis-[20rem]`, then `[cancel + go]` with `ml-auto`, so the actions never get stranded alone on a line while the hint keeps the one above. Any modal deep enough to scroll pins that row (`sticky bottom-0 -mx-6 px-6 pb-6 bg-surface`, container `px-6 pt-6`) — `ProjectSettingsModal` already did; `NewProjectModal` and `NewTripModal` now do too.

**A modal opened from INSIDE the shell's library sheet needs `z-[60]`** (2026-09-20). Every overlay in the suite is `z-50` — `MediaLightbox`, every tool modal, `BottomSheet`'s panel — so within that level the DOM order decides, and the shell renders after the tool: on a phone the library sheet sat over the sheet a verb had just opened and swallowed its primary button. Only one modal needs this today (Trips' «Situer cette photo», `roadtrip.md`), because every other `MediaAction` navigates away instead of opening a sheet over the one it was pressed from. **How to apply**: raise the sheet, do not try to close the library from a tool — the sheet belongs to the shell and the seam is one-way.

**Verified** in headless Chromium at 390×844, 744×1133, 834×1112 and 1280×900 against a throwaway harness that mounted the modal with `window.fetch` stubbed for the Winnow endpoints (no instance needed, thumbnails deliberately failing); `scrollWidth - clientWidth` was 0 at every width. Rebuild that harness rather than eyeballing this file — it is the only way to see the modal without a connected Winnow.

## A `1fr` grid track cannot be trusted to carry `aspect-ratio` (rev. 2026-09-07)

**Struck twice.** `WinnowBrowser`'s calendar cells already dropped `aspect-square` below 820px (`max-[820px]:aspect-auto max-[820px]:min-h-[3.5rem]`, entry above) because a `minmax(…,1fr)` track's width can turn indefinite once the grid's own container is inside a narrow or stacked context, and a browser resolves `aspect-ratio` against that indefinite size however it likes — observed as the tile collapsing to a thin band instead of a square. The Road Trip piece editor's day strip (added later, in the 22rem side panel — narrow on every width that matters; retired 2026-09-20, `roadtrip.md`) used the same `aspect-square` and hit the same collapse, because the lesson lived only in the file that had already paid for it. **How to apply**: a thumbnail tile in an `auto-fill`/`minmax` grid takes a **fixed pixel height** (`h-[74px]`, `h-[90px]` — whatever the design calls for), never `aspect-square`/`aspect-[…]`, matching `WinnowBrowser`'s own `Thumb` component (`h-[90px] max-[820px]:h-[120px] object-cover`). `aspect-ratio` on a grid-track-sized box is only safe once the grid's own tracks are a definite, non-`1fr` size — which a tile grid meant to fill available width never is.

## An `auto` grid row is a SHARE of a height that turns definite (2026-09-12)

**The third strike of the family above, same tiles.** The Road Trip piece editor's day strip (retired 2026-09-20, `roadtrip.md`; the rule outlived it) drew a hundred pictures as 6px slices of themselves on a phone: the tiles still carried their `h-[74px]`, but the `<button>` around them is `overflow-hidden`, so what the reader saw was a letterboxed sliver of each. The height on the picture was never the guarantee it looked like — the ROW is what decides a tile's box, and a grid with `auto` rows divides its own height among them the moment that height becomes definite (measured in Chromium: 40 tiles in a `height: 208px` grid gave 15px rows while the `<img>` stayed 74px). A `max-height` is enough for that in WebKit, and a flex parent shrinking the grid is enough everywhere — a scrolling strip meets both.

**How to apply**: a tile grid that scrolls pins its rows in pixels (`auto-rows-[74px]`, `max-[820px]:auto-rows-[104px]`) and the tile fills the row (`w-full h-full`); add `shrink-0` so a short sheet scrolls the strip instead of squeezing it. Then the only way the grid can answer "too many pictures" is to scroll, which is what it is for. A grid with no definite height of its own (`WinnowScopeGrid` in the library column) is not exposed and was left alone. **Verified** in headless Chromium at 390×844 against a throwaway page mounting the real `BottomSheet` chain — rebuild it rather than eyeballing; iOS Safari, where it was reported, could not be run here.

## `max-h-full` measures nothing in a `flex-1 min-h-0` chain (2026-09-07)

**The bug**: `WinnowLightbox`'s picture came out cropped and its clip drew square. The media sat in a `grid place-items-center h-full overflow-hidden` box whose parent was a `flex-1 min-h-0` row, and carried `max-w-full max-h-full`. A percentage height needs a **definite** height on the containing block; a flex item sized by `flex-1` inside `min-h-0` has none until layout is done, so `h-full` fell back to content height and `max-h-100%` capped nothing — the picture drew at its natural size and the `overflow-hidden` cut it.

**How to apply**: to fill a flex line's cross size, stretch the box (`items-stretch` on the row + `self-stretch` on the item, arrows `self-center`), never `h-full`. Then let the box be the frame and CONTAIN the media in it — `absolute inset-0 w-full h-full object-contain` — rather than asking the media to measure itself against an ancestor. `object-contain` is also what gives a `<video>` its aspect ratio: an unfitted `<video>` takes its own default box, which is where the 1:1 clip came from. Twin of the `aspect-ratio` entry above: both are a box asking an indefinite ancestor for a size.

## A tool screen is an APP: the DOCUMENT is locked, not just the frame (2026-09-10)

**Reported on a phone**: the masthead slid off the top, the section bar lifted off the bottom and paper showed under the frame — *"the layout header and footer must be fixed, we must have a mobile app feel, no scroll outside of the ui"*. The frame was already `h-dvh` and clipping, and in a fixed-size browser that IS the end of it: measured at 390×844, `documentElement.scrollHeight === clientHeight` on every tool screen, before any change. **The overflow is not in the app's boxes, it is the document's**: on iOS the initial containing block is the LARGE viewport (toolbars retracted) while `dvh` is the current one, so `<html>` stays about a toolbar taller than the frame inside it, and that difference is what a finger drags. No amount of `overflow-hidden` on a child can reach it.

**Decision**: the shell tells the document which of its two lives it is in — `App.tsx` sets `data-shell="fixed" | "flow"` on `<html>` from whether a tool is mounted — and `index.css` locks the fixed one: `height` (see the entry below — `--app-h`, and it was `100dvh` until the unit proved unreliable), `overflow: hidden` and `overscroll-behavior: none` on **the root element and body both**. The root is the load-bearing one (overflow on `body` alone propagates back to the viewport); the explicit height is what trims iOS's larger ICB; `overscroll-behavior` is the rubber band and pull-to-refresh, because a page that cannot scroll must not bounce either or it still reads as a web page. Home and `#/sources` get `flow` and keep the ordinary page scroll they are written for. **How to apply**: a new full-height screen belongs to a tool route, or it must set its own lock — and never reach for `position: fixed` on the header and the bar, which is the fix this made unnecessary.

**`viewport-fit=cover` is set, and it is what makes `env(safe-area-inset-*)` mean anything** — without it every inset is 0 and the safe-area padding the shell already pays (`pt-[env(…)]` on the compact frame, `pb-[max(0.5rem,env(…))]` on the section rail) is dead code. Two edges nobody owned are paid now: `body` takes the left/right insets, since a landscape notch belongs to no component in particular, and Home's top padding is `max(its clamp, env(safe-area-inset-top))`. **No `maximum-scale`, no `user-scalable=no`** — pinch-zoom stays, and a form that must not zoom the page under it is still answered by 16px controls.

**Verified in headless Chromium** at 390×844 and 1280×900: the document is unscrollable on all three tool screens and scrollable on Home and `#/sources`, the flag follows an in-app hash navigation both ways, a wheel over the trip overview moves its own list by 310px with `documentElement.scrollTop` at 0 and the masthead still at y=0, and both bottom sheets still reach the bottom edge exactly. **What cannot be checked here is the thing that caused it** — a real iOS toolbar — so the iPhone is where this is confirmed.

## And `dvh` itself can be stale, so the app MEASURES its height (2026-09-12)

**Reported from Chrome on iOS, and only after a reload**: a band of paper under the bottom bar. Read off the screenshot at 3× on a 430pt phone, which is what identified it: the section bar is exactly its 57px, it ends **59.3 CSS px above the browser's toolbar**, and that band is uniform across the whole width — no chrome icons in it, so it is the page's own paper and the app's box is a retracted toolbar SHORTER than the screen it was given.

**The fault is the unit, not a box.** The browser keeps its toolbars retracted across a refresh, the page is laid out against the shorter viewport they were expanded for, and `100dvh` — "the current viewport", the right idea — is never recomputed, precisely because the entry above locks the document: a scroll is what would ask the question again, and there is none. The bug is therefore permanent for that page load and invisible to every other browser.

**So the height is read.** `shared/ui/app-height.ts` (pure, tested) reconciles the two viewports a browser exposes; `use-app-height.ts` publishes the answer as `--app-h` on `<html>`, and every box meaning *the whole screen* is sized in it instead of `100dvh` — the document lock, the tool frame, `DockedPanel`/`BottomSheet`'s fractions, and the four `max-[820px]:` full-screen sheets. `100dvh` stays as the variable's own fallback: the first paint, and anything mounted outside the shell.

The rule is **the larger of `window.innerHeight` and `visualViewport.height`, and neither while the page is pinched**, and each half earns its place. The visual viewport is the only reading that grows when the chrome retracts without the layout being told — the bug itself. The layout viewport is the only one the software keyboard does not move, and resizing the app to the strip above a keyboard would reflow the editor under the fingers typing in it. A zoom (in *or* out) freezes the measurement rather than shrinking the layout around the gesture. It is re-read on `resize`, `orientationchange`, `pageshow`, `visibilitychange`, the visual viewport's own `resize`, and `load` — the moments a phone hands back a different screen, several of which are not resizes.

**A drag reads the same number** (`readAppHeight()`): both sheets turned a finger's travel into a fraction of `window.innerHeight` while their CSS sized them in `dvh` — the same disagreement one level down, and it goes away by construction now.

**Verified in headless Chromium** at 390×844 driving the dev server: `--app-h` equals `innerHeight`, root, frame and the bar's bottom all land on it, the document overflows by 0, and Home still scrolls 3080px as `flow`. The failure is reproducible by hand and worth reusing — force `--app-h: 744px` and the bar sits 100px above the bottom, exactly the screenshot; one resize event puts it back flush. **What no headless browser can produce is a real iOS toolbar.** If a gap ever survives this, the remaining possibility is that BOTH readings are stale at load and only a later moment would catch it — a timer, or the first touch.

Both keep an `sr-only` live region with the full sentence, so nothing is lost to a screen reader. **`useIsCompact()` gating the word was removed 2026-09-13**: a desktop toolbar packed as tight as the Trip piece editor's (`< Overview` · `TRIP` · the pill · `Export`) wrapped on "Saved" too, not only under 820px — so the word now shows only for `pillNeedsAction`, at every width. **How to apply**: a new status in a `PageBar` is a dot plus an optional word, and the word surviving at all is what a waiting-on-the-author state buys, never screen width.

## A header row of pill buttons: wrap it, and collapse the status into it (rev. 2026-09-10)

**The bug, reproduced**: the Road Trip piece editor's header (`PostEditor.tsx`) packed a fixed-height "← Overview" pill, a variable-width sync-status pill (`SyncPill`, shared with the Studio) and an "Export" button onto one `flex items-center gap-3` row with no `flex-wrap`. Once the sync pill's text ("saved to winnow.steeve.website · just now") left too little room, the fixed-height buttons had nowhere to put their own text but a second line — which a `h-[1.9rem]` box does not grow for, so the overflow line spilled outside the button and over the title beneath it. **`TripOverview`'s own header already gets this right** (`flex items-center gap-3 flex-wrap`): under pressure, an *item* (the whole pill) drops to its own line, instead of the *text inside one* wrapping. **How to apply**: any header row mixing a fixed-height pill with a variable-width one needs `flex-wrap` on the row and `shrink-0 whitespace-nowrap` on the fixed ones — copy `TripOverview`'s pattern rather than composing a new row by hand. The same fix retired a duplicate "Export" button that only repeated the Export tab's own — a header action row is navigation and status, never a second trigger for a tab's own button.

**A status of uncontrolled length does not get a row — it gets a pill and a popover (2026-09-10, the maintainer's ask: "the status bar is taking too much space, especially on mobile a whole line is dedicated where it could just be on the line above").** The first answer had been to give the sentence a full-width row of its own beneath the navigation, because sharing the row made the three fixed-height pills wrap one per line in a ragged stack. That bought legibility with a tenth of a phone screen spent on "saved · just now", so it is **superseded**: `SyncPill` is now the SAME `h-[1.9rem]` lozenge as the buttons beside it — a coloured dot and one word (`pillLabel`, pure and tested) — and the sentence with its verbs lives in a popover on click, and on hover where `pointerType === 'mouse'`. Nothing in it can wrap, so the ragged stack cannot come back and the row is one row again.

**On a phone even the word goes, unless the state is waiting on the author.** `pillNeedsAction` (unauthenticated · forbidden · conflict · gone) is what keeps "Conflict" and "Sign in" spelled out at every width: a decision nobody is asked to make does not get made, while `synced`/`dirty`/`saving`/`offline` resolve themselves and a 30px dot is enough. Measured at 390×844: with the dot alone the piece editor's header is one line; the four action states take a second, which is the trade being made deliberately. The full sentence is announced either way — it sits in an `sr-only` `role="status"` live region, because a pill is a summary and a live region has to carry the whole state.

**A popover hanging off a pill mid-row needs a CLAMP, not a choice of two corners.** Anchoring it left or right by which half of the screen the pill sits in put its left edge at −87px on a 390px screen: the 20rem panel is wider than the room either side of a pill in the middle of a row. Measure the trigger at open time and slide the panel back inside (`Math.min(Math.max(rect.left, EDGE), innerWidth - width - EDGE) - rect.left`, applied as `style.left` on the wrapper). Two more things the hover half needs: the gap above the panel is **padding on the wrapper**, never a margin on the panel, or the pointer crosses a strip over neither element and the panel drops on the way to its own buttons; and the trigger carries **no `title`**, or the browser's tooltip covers the panel repeating its sentence.

**A pill that can grow needs a radius, not `rounded-full`** — the lesson that paid for the old auto-height pill, and still binding on anything that wraps. `rounded-full` resolves to half the *grown* height and draws a fat lozenge, so a box that may wrap takes half the ONE-line height instead (`rounded-[0.95rem]` against a `1.3rem` line), or the app's own `rounded-paper`.

**A `rounded-full` container that can wrap its contents to two rows is the same shape mistake one level up**: the piece editor's six-tab bar (`p-1 rounded-full border … bg-surface`) wraps to two rows in its 22rem column, and a pill stretched over two rows of buttons reads as a mis-shapen blob, not a toolbar. The individual tab buttons stay `rounded-full`; the wrapping *container* takes the app's own soft-rectangle radius (`rounded-paper`, 14px) instead — a `rounded-full` wrapper is only correct when its content is guaranteed to stay one row.

## A stage that must fill the height: measure the box, never trust a replaced element (2026-09-06)

**Measured on Road Trip's piece editor** (maintainer ask: "the preview must take the whole page height"). Three things each silently capped the picture short of the column. (1) **A canvas never displays past its bitmap**: `max-h-full` on a 720px-tall canvas stops at 720 CSS px however tall the box is — a replaced element's intrinsic size is its ceiling. (2) **CSS `aspect-ratio` cannot transfer a max-constraint back onto a definite axis**: `h-full` + `max-w-full` + `aspect-ratio` clamps the width but leaves the height, so a width-limited frame distorts or letterboxes. (3) **A container query never matches the `@container` element itself**, only an ancestor — `@min-[860px]:grid` on the section that IS the container silently never applied, and the layout stayed stacked at every width. **How to apply**: put the queried layout on a CHILD of the container; size the picture's box in JS from the wrapper's rect (largest aspect-fit, `ResizeObserver`), so the element box stays exactly the picture (hit-testing maps through it); and let the bitmap follow the displayed size × `devicePixelRatio` between `PREVIEW_LONG_EDGE` and `MAX_PREVIEW_LONG_EDGE`, or a bigger preview is a blurry upscale. In the stacked layout the wrapper's height must come from CSS (`min(62vh, 100cqw / aspect)` — `cqw` is the editor's container) because the box inside no longer has content height of its own; and a `min-h-0` on the stage column must stay wide-only, or flex-shrink squeezes it to nothing inside the fixed-height shell when the editor is stacked at a mid width.

## A media preview never view-zooms; a day-sized zone does (2026-09-08, rev. 2026-09-10)

**Decision, and it reverses the first half of this entry.** A view zoom over a MEDIA PREVIEW is out, in both editor stages, on the maintainer's call: the pill was wanted for Road Trip's day heatmap and its stage ruler, and over a preview it fought the gestures the picture itself answers — a trackpad pinch had to be taken away from the badge stage's own framing zoom to feed it. **A preview fits the room it is given, and that is all**: the Studio centres its canvas under `max-w-full max-h-full` (a canvas is a replaced element, so that is the whole arithmetic), Road Trip measures the largest aspect-fitting box in its wrapper. Do not put a `StageZoomControl` over a picture again; looking closer at ONE picture is the lightbox's job (entry below).

**The exception, named rather than left to be re-derived (2026-09-22): a surface whose ONLY gesture is looking.** The look gallery's scene (`LookScene.tsx`) carries `usePictureZoom` and the ± pill over the photograph, and that does not reopen the decision above: what the pill cost on the two editor stages was the picture's own FRAMING gestures, and a scene has none — it is an inspection surface, like the lightbox and the develop viewport, which both drive it already. The test for the next one is that question, never the surface's size: *does this picture answer a gesture of its own?* If it does, the pill takes it away. The scene's ceiling is `usePictureZoom`'s new `ceiling` option at the lightbox's 8×, not a develop's 4000 %: what is on screen there is a 720p raster (`SCENE_PIXELS`), and magnifying a preview pixel says nothing about a look. It keeps the develop sheet's wipe grammar too — at the fit a press anywhere places the divider, zoomed only the `[data-wipe-handle]` strip does — through the same `claim`/`onTakeover` pair, because a second grammar for the same two gestures is how they stop being learnable.

**The primitive stays, for the zones it was really for** (rev. 2026-09-22: the zones stopped zooming on 2026-09-13 for the loupe, so `use-stage-zoom.ts` had no consumer and was DELETED; `stage-zoom.ts` survives for `ZoomControls`, `zoomLabel`, `STAGE_ZOOM_STEP`, `wheelZooms` and the scroll-anchoring arithmetic `zoom-anchor.test.ts` still guards, in case a scrolling zone zooms again): `shared/ui/stage-zoom.ts` + `StageZoomControl.tsx`, with the pill driving the lightbox and the Develop stages. The scale is applied as **layout size** — a zone multiplies its own unit — never a CSS `transform`: a transformed element still measures unscaled, so the scroll box would not know it had anything to scroll. Panning is then native scrolling, and every pointer handler keeps working untouched, because the zones map pointers through `getBoundingClientRect()`.

**Range: 25% to 1600%**, a quarter of the fit up to sixteen times it, in ×1.25 steps that land exactly on 100% when they cross it. The zone's own floor is what really stops a zoom-out (the ruler will not draw a day under 6px, the grid a cell under 4).

**Gestures.** ⌘/ctrl-wheel (which is what a trackpad pinch sends) and a two-finger touch pinch are the view zoom. What a BARE wheel does is per zone (`WheelZoom`, `wheelZooms`): both trip-overview zones pass `wheel: 'any'`, because nothing else there wants the wheel — but a shift-wheel and a sideways trackpad swipe (the dominant axis decides) stay the browser's horizontal scroll, which is how a zoomed track is panned. `modifier` is what a zone with its own use for the wheel would pass, and no zone does today: that was the editor stages, and the arrangement is exactly what failed — the badge stage had to hand ⌘/ctrl over to the view zoom, so a trackpad pinch stopped framing the picture. **A pinch means the same thing as the wheel on the same surface, or one of the two is wrong.** A pinch also makes a zone stand down while it runs (`pinching`), or the first finger drags a leg across the ruler under the gesture.

**Zoom-at-the-pointer has FOUR traps, every one of them found the same way: read the fraction of the content under a fixed point, zoom, read it again (2026-09-08).** Do that before believing any of this works — three of the four shipped green.

1. **A wheel spins out several events before React renders once.** The correction is measured from the scale the box is still LAID OUT at — the first of the batch — not from the one the last event started from; keeping the later `prev` walked the day from 65% of the ruler to 24% in three notches. So `pending.prev` is only written when nothing is pending.
2. **The scroll it is measured from must be the one the box had at gesture time**, kept in `pending` beside `prev`. Reading `el.scrollLeft` back in the layout effect is right while the content GROWS and lies when it shrinks: the browser has already clamped the scroll into the smaller content, so a zoom-out that overshot the floor projected from a position never asked for and jumped to the start of the track.
3. **The multiplier is how much the content actually grew, not the ratio of the two scales** (`growthRatio`, `scrollAfterZoom`'s `grew`). A zone with a pixel floor or whole-pixel rounding is not linear in the scale — the ruler's frozen 6px track is the extreme: it did not move at all while every notch pulled the scroll by a quarter.
4. **Content that does not scale must be subtracted first**: the day grid's weekday rail keeps its width at every zoom, so `scrollAfterZoom` takes a `fixed` prefix and anchors past it, or the day slides by the rail's width times the zoom.

**And below the fit point no correction exists at all**: while the content is narrower than its box the browser pins the scroll to 0, so nothing can hold a point under the pointer. Hence `zoomFloor` + `minScaleToFill`: a zone declares its content width at a scale (`contentWidth`) and the zoom stops going out where that stops filling the box — capped at 1, so 100% and the reset button are always reachable. Where a zone still fits at 100% (a short trip's grid on a wide screen) it is CENTRED (`w-fit min-w-full flex justify-center`) so it grows about the middle rather than rightward from the left edge; the buttons anchor on the box's centre, so they hold exactly there. The regression guard is `src/shared/roadtrip/zoom-anchor.test.ts`: a simulated scroll box, clamped the way a browser clamps one, swept both directions over each zone's real width function.

**Three tolls a scroll box charges, all three invisible until something is zoomed past the viewport.** (1) **A scroll container's intrinsic width is zero** — it advertises no content width, so any ancestor sized by its content collapses. (2) **The content is a flex item and will be squeezed**: a 949px box inside a 486px viewport shrinks back to 486 unless it is `shrink-0`. (3) **`min-w-full` alone leaves the left half unreachable**: the centring wrapper's width is still 100% of the viewport, so a centred overflow spills both ways and the scroll extent only counts the right. It needs `w-fit h-fit min-w-full min-h-full` — fit-content around the picture, never smaller than the viewport, which centres while it fits and starts at the corner once it does not. All three were learned on the editor stages and paid there; they are the price of the scroll box, which is why a preview that no longer zooms is no longer one.

**A measured box must never be sized by the picture it holds (2026-09-09, rev. 2026-09-10).** Anything that reads a box and then fits a picture into it — `useStageZoom` did, `BadgeStage` still does — is measuring its own output the moment that box takes its size from its content, and every gesture or repaint feeds the next. Measured in Chromium at 390×844 when the shell still went `h-auto` on a phone: one pinch out collapsed the canvas to 1×1 and the measured viewport oscillated 201 → 4 → 1 → 201 px, while zooming in grew the stage 240 → 1920 px tall and pushed the inspector 1 700 px down the page. **The rule survives the zoom's removal**: Road Trip's piece column keeps its `w-full` (`PostEditor`) so the badge's own measured box cannot decide it, and a stage whose ancestors are NOT definite states its own height from the media's aspect and the screen (`h-[min(62vh,calc(100cqw/var(--aspect)))]`). The Studio needs neither — the compact shell keeps `h-dvh` at every width, so its stage is plain `flex-1 min-h-0`; do not re-add a height restatement there. No unit test can see any of this: check it in a browser at 390, 900 and 1280, reading the box twice a second apart, and a correct one does not move.

## A drag surface inside a scroll box claims only the axis it writes (2026-09-09)

**Rule, learned on Road Trip's stage ruler and binding anywhere a draggable thing sits in something that scrolls.** `touch-none` is the reflex for a pointer-drag surface — it is what stops the browser stealing the gesture — and it is a trap the moment that surface lives in a scroll box, because a finger has no other way in. The ruler's scrub surface covered the whole track and set `touch-none`, so a track wider than the phone by construction could not be scrolled AT ALL on touch: every swipe meant to read the rest of the trip was read as a scrub instead. The split that works, verified with `Input.dispatchTouchEvent` in headless Chromium:

- **A surface that is only pointed at claims nothing.** Picking a value is a `click` — a tap on touch, one gesture, no capture — and the browser is left free to pan. A press-and-travel gesture for choosing a value is what forces the `touch-none`, so the two decisions are the same decision.
- **A surface that is dragged claims its own axis and no more**: `touch-pan-y` on a thing dragged sideways. The browser then leaves horizontal movement to the pointer handlers while a finger travelling UP it still scrolls the page — `touch-none` had made the whole band a place the page could not be scrolled through.
- **An ORDINARY scroll box declares no `touch-action` at all** (2026-09-10). This whole rule is about a surface that WRITES a drag; a plain `overflow-x-auto` strip — Road Trip's counts on a phone — is not one, and the browser already does both axes on it. Adding `touch-pan-x` there buys no horizontal scrolling and costs the vertical swipe that scrolls the page under it. Reach for `touch-action` only when pointer handlers are taking a gesture away from the browser.
- **A flex child that scrolls also becomes crushable** (2026-09-10). An `overflow` other than `visible` sets the item's AUTOMATIC MINIMUM SIZE to zero, on the cross axis too — so the moment that counts strip could scroll sideways, the column above squeezed it from 47px to 18px with the numbers sheared off at the waist. `flex-none` (or an explicit basis) is part of making a flex item scroll, not tidiness. Same family as the `min-h-0` rules above, running the other way: there the automatic minimum stops a child shrinking; here `overflow` removes it and nothing does.
- **The scroll box gets `overscroll-x-contain`**, or a track sitting on its first day hands the next swipe to the browser, which reads it as *Back*.
- **A drag over things that are CLICKED is decided, never claimed at pointerdown** (2026-09-14, the Trips loupe's body over its day cells): a mouse drags past a slop, a finger only after a still hold (a travelling finger is a scroll), the ending click is swallowed in the capture phase, and once held a finger's travel is kept from the browser by `preventDefault` on a NON-PASSIVE `touchmove` — `touch-action` cannot help, it is fixed before the hold is known. `shared/ui/press-intent.ts` holds the thresholds.
- **`touch-pan-y` alone loses the gesture one frame in — a surface that PANS sideways must TAKE it** (2026-09-16, reported from the maintainer's phone on the stage ruler: "the event only works on the first instant"). `pan-y` leaves the vertical axis to the page, so the small vertical component every real swipe has starts the page scrolling, and the browser then CANCELS the pointer: the pan moves once and dies. Measured here with `Input.dispatchTouchEvent`: from the second `touchmove` on, `cancelable` is already `false` — the browser had taken the gesture. The cure is the loupe's, one rule above, generalised: decide the direction on the first travel past the slop (dominant axis wins, `swipeIntent`), then hold the gesture with `preventDefault` on a non-passive `touchmove` for as long as it lasts. `touch-pan-y` stays on the surface — it is what keeps a vertical swipe the page's — but it is the FALLBACK, never the mechanism. `shared/ui/fling.ts` (pure, tested) + `shared/ui/use-fling-pan.ts` do this, with the throw a phone expects after the lift (velocity blended over the last samples, `0.93` per 16ms, nothing under 0.08 px/ms, none at all from a cancelled gesture, from a finger that had stopped ≥80ms before lifting, or under `prefers-reduced-motion`) and a `false` from the caller stopping the glide at a real edge. A gesture surface reaches for it rather than reading `pointermove` by hand.
- **Bind native listeners from the REF callback, never from an effect beside it** (2026-09-16, and it cost an hour of "the element is right, the listeners are there, nothing answers"). A hook that attached in a `ref` callback and detached in a `useEffect` cleanup works in production and is DEAD in dev: StrictMode runs the simulated remount, the cleanup pulls every listener off the node, and React never calls the ref again because the node did not change. A ref callback is called with `null` on the real unmount, so attach and detach both belong there and the pairing cannot come apart.

**What it costs, and it is the right trade.** `useStageZoom`'s two-finger pinch and native panning are mutually exclusive: once the browser owns a gesture it cancels the pointers, so on a zone that lets it pan the pinch is best-effort and `StageZoomControl`'s +/− is the way in that always answers — which is now the case on both zones that zoom. No CI gate can see any of this — `touch-action` is a string in a class list and the failure is a gesture that does nothing — so check it with real touch events, not with a mouse.

## The browser's OWN pinch is what "the pinch does nothing" means on a phone (2026-09-16)

**Reported**: in the Develop tool on the maintainer's phone, *"les pinch, les
zoom, le panning, tous ces événements ne fonctionnent pas forcément bien"*.
Three faults of three different shapes, and only the first is invisible from a
desktop.

**The trap.** `touch-action: none` takes away every gesture the PAGE owns —
scrolling, panning, double-tap zoom — and cannot reach the one the browser
chrome owns: WebKit zooming the visual viewport. So on iOS a two-finger pinch
over a picture magnifies the whole app, and the pointer events that were
feeding the surface's own pinch are CANCELLED mid-gesture. There is nothing in
the pointer code to find, because the pointers stop arriving. (`app-height.ts`
already freezes its measurement under a pinch, which is how we know this
happens here rather than in theory.) `shared/ui/native-gestures.ts`'s
`blockNativeZoom(el)` refuses WebKit's `gesturestart`/`gesturechange`/
`gestureend` — non-passive, or `preventDefault` is ignored — and that is the
only handle on it. **How to apply**: any surface that answers a pinch itself
calls it on its own element, and NEVER on the document: the reading pages must
keep the browser's pinch, it is how someone enlarges text. It is a no-op
outside WebKit, which is correct — `touch-action: none` suffices there. Since
2026-09-22 it is bound by the one gesture machine (`use-zoom-gestures.ts`) on
every element it reads — the develop viewport, the lightbox's deck, the crop
stage and Trips' badge stage — so a surface that adopts the machine cannot
forget it.

**A listener on the CANVAS is a listener a pinch can miss.** The crop stage's
picture is letterboxed inside a wider box — 147px of canvas in a 374px stage at
390px wide — and two fingers pinching something small land either side of it,
outside the canvas, inside the stage. The gestures belong on the box the
picture is centred IN, with `touch-none`, never on the picture.

**A finger of a pinch is a finger even when it lands on a control, and a pinch
that ends is not over.** Two bookkeeping rules that read as "the pinch is
unreliable": a press over a button was returning before the touch was counted,
so a pinch begun on the "hold for before" pill never became one and the count
stayed one short for the rest of the gesture — count the finger, then let the
control keep its press; and lifting one finger of a pinch left the other inert
until it was lifted and put back, where it should take the pan over, which
zoomed in is most of the gesture.

**Where a pinch is best-effort, the pill is not optional.** `StageZoomControl`
is drawn at every width in the Develop tool, phone included — the lightbox
hides it under 820px on the argument that the pinch is the gesture there, and
that argument only holds while the pinch cannot be taken away. On the crop tab
it drives the FRAMING's scale (what is kept) rather than the view's (how
closely it is being looked at), through the same `ZoomControls` interface.

## Two uses, one hand: the zoom grammar (2026-09-22)

**The maintainer's distinction, and it is the axis of the whole thing.** The same gestures — the wheel, a trackpad pinch (a ⌘/ctrl-wheel), two fingers, one pointer dragging — serve TWO uses that must stay two: **Looking** (a view zoom that writes nothing: the Develop viewport in both hosts, the crop stage, the lightbox, the look scene — a `transform` over the preview, gone at the fit) and **Placing** (a FRAMING that writes the document: Trips' badge stage, the picture moved and enlarged inside its frame and cropped against its edges, per cell on a collage; no view zoom there, the 2026-09-10 decision above stands). Same hand, same code, two targets. The design record is the artifact *Grammaire des gestes* (https://claude.ai/artifact/TXiBfu1pqVd5NRrs2dov9g): the rule, the map of surfaces, a live demo of the anchor.

**Decision: ONE reading of the hand**, `shared/ui/zoom-gestures.ts` (pure, tested) + `use-zoom-gestures.ts` (the DOM half: native non-passive listeners bound and unbound in ONE effect, `blockNativeZoom` on the element, capture phase on request, an `enabled` switch so a stage with nothing to zoom leaves the wheel to the page). Before it, four surfaces each read the hand: four pinch machines, four copies of `exp(-deltaY / 400)` (now `wheelZoomFactor`, the one curve), Trips anchoring nowhere and the crop where the pinch BEGAN. The machine has no opinion on what it moves: a `ZoomTarget` answers `scaleAt(point)`, `zoomTo(scale, anchor)`, `panBy(dx, dy, at)`, and may take, read or refuse a single pointer (`drag`: `'pan'`, a handler, or null). What every surface then shares: ⌘/ctrl-wheel and a bare vertical wheel zoom about the pointer (`wheel: 'any'`; `'modifier'` leaves a bare wheel to the page, `'none'` leaves the whole wheel to the surface — the lightbox keeps its own sweep/momentum path); a sideways wheel pans; two fingers pan by their LIVE centre first and then zoom by the ratio from the starting spread (never compounded per frame); the second finger takes over whatever the first was doing (`onTakeover`, `onPinch`); the finger left after a pinch takes the pan over; a finger over a control counts for the pinch and never drags. The keys of a Looking surface are `zoom-keys.ts`: `Z` toggles fit ↔ zoomed, the arrows pan a ZOOMED view (Shift a stride), nothing in a text field or under a modifier; the lightbox keeps paging at the fit; the workbench maps `Z` through `roll-editor.ts` and gives its arrows to the roll; a Placing surface gives its arrows to the selected element. Ceilings stay per surface on purpose (lightbox ×8, develop 4000 %, crop ×8, framing ×8): the gesture is uniform, the limit says what the surface is for. Not taken: double-tap to zoom (the crop's double-click is "zone maximale"), a ± pill everywhere.

**How to apply.** A new surface that zooms or moves a picture calls `useZoomGestures` on the BOX the picture is centred in and writes a `ZoomTarget`; it never reads `wheel` or a second finger itself. Its arithmetic is `pan-zoom.ts`'s `zoomAbout` for a view (`crop-view.ts` shows the mapping for a stage that draws through a canvas) or `framing.ts`'s `zoomFramingAbout` for a framing — built on `unframePoint` → `framePoint` → `panBy`, so it is exact at any rotation, mirror and fit and never opens a gap.

**Three traps the migration found, each measured with the fraction-under-a-point probe** (recipe in `testing.md`, «The anchor probe»):
- **A value clamped only when it is DRAWN drifts under a still pointer.** The crop stored whatever the gesture produced and clamped at paint time; the stored origin and the drawn one disagreed the moment a pan hit its limit, and the next notch anchored from an origin not on screen (0.118 → 0.129 → 0.094 at a corner). Clamp at the WRITE (`useCropZone.setView` through `clampCropView` against the box the stage reports) so what is stored is what is drawn.
- **A document lags the hand.** A pinch pans then zooms in the same event, and a wheel burst lands several notches before React renders once; a target that re-reads the document's framing for each write overwrites the write before it (a pinch's drift was lost). `BadgeStage` keeps the framing THIS hand last wrote, for 300 ms, and reads that first — the crop's `currentRef` is the same rule for a zone.
- **`{ ...e }` on a KeyboardEvent copies none of its getters** (`key`, `shiftKey` are on the prototype): a record must be spelled out field by field (`describeZoomKey`). The first cut of `Z` did nothing and nothing said why.

**Expected, not a bug:** on the letterbox axis no pan exists until the picture exceeds the box, so the FIRST notch from the fit cannot hold that axis — the same rule as «below the fit point no correction exists» above, on every Looking surface, and on a Placing surface wherever the cover leaves no slack.

## Looking at ONE picture is the other zoom, and it is a transform (2026-09-08, rev. 2026-09-09)

**Decision.** ONE sheet shows a media large, wherever it lives: `shared/ui/MediaLightbox.tsx` over `shared/ui/pan-zoom.ts` + `use-media-viewer.ts` — a second primitive beside the zones', deliberately not the same one, and since 2026-09-10 the ONLY way to look closer at a picture. It knows nothing of sources; a caller hands it `LightboxItem`s (title, facts, kind, `src`, a `still` for the neighbour slots, the natural size, an `unavailable` reason, and whether the URLs need the cookie) plus the footer, which is the only thing the two callers do differently: `WinnowLightbox` brings the picture across, the Library sidebar puts it to work in the tool. A pool asset reaches it through object URLs the sidebar pins for a ±2 window around the open one (`shared/lib/use-object-urls.ts`) — `createObjectURL` reads nothing but pins the handle, so a library of thousands must not hold thousands. A RAW that arrived without its JPEG twin says so instead of handing the browser bytes it cannot decode. A zooming zone scales its LAYOUT so the browser's scroll box does the panning; a viewer's deck has to follow a finger *past its own edges*, which no scroll box does. So everything here is a `transform` and every limit is arithmetic we own (`panLimit`, `clampView`, `zoomAbout`, `rubberBand`, `swipeCommit` — all DOM-free, tested in `pan-zoom.test.ts`). Range is **fit to 8×**, in ×1.5 steps: fit is the floor because a viewer showing less than the whole picture shows nothing. `StageZoomControl` drives both, over a `ZoomControls` interface `StageZoom` now extends, with a `hint` prop for the gesture the surface really offers.

**The pager floats IN the frame, not beside it (2026-09-09).** Previous/next were a column each side of the deck, so the black frame stopped two buttons and a gap short of the sheet's own padding and sat out of line with the title above and the footer below. They are now `absolute` inside the frame, wearing the translucent-paper pill style (it reads over a white sky as well as over the frame's black) — the media box then runs edge to edge with the header and footer content, which is what the maintainer asked for, and covering a sliver of the picture is the cheaper price. **Two rules for that placement**: they are siblings of the viewport element and never children of it — that element answers every pointer event itself, in the capture phase, so a button inside it would be a drag; and a single media draws **no** pager at all, a dead control over a picture being noise the header's `1 / 1` already covers. Under 820px there is still none: the swipe is the gesture there.

**What each gesture means, and why the two surfaces disagree.** ⌘/ctrl-wheel and a two-finger pinch zoom, as everywhere. But a **bare vertical wheel zooms here too** — the stages leave it to the page, and a viewer has nothing else to do with it while a mouse has no other way to zoom. A **bare horizontal wheel** (a two-finger trackpad swipe) pages the deck, and pans instead once the picture is zoomed and has somewhere to go. A **drag pans when zoomed and swipes when not**: at the fitted size there is nothing to pan, so the same gesture is free to mean the other thing, decided once after 6px of slop. Two fingers pinch AND pan by their centre, which is why the viewport is `touch-none`.

**The exposure line is a second fact line, and both sources fill it** through one pure formatter (`shared/exif/exif-summary.ts`): body · lens · focal length · ƒ · shutter · ISO, each part absent when the picture does not say it — the line never writes `—` and never guesses. A local file is read for it when the sheet opens (`readEffectiveExif`, the head only; a CLIP is not read at all, since an MP4 has no EXIF and only what its source vouched for is worth having). An instance fills it from its own columns: Winnow's `/api/assets` returns `a.*`, so `lens` was already on the wire and only missing from `WinnowAssetRow`. The camera's name and the lens stay OUT of `exifFromRow` — they are display labels, not cue values — and are added where they are read.

**The three things that are not obvious:**

- **A wheel gesture has no end event, and macOS keeps streaming momentum for a second after the fingers lift** (rev. 2026-09-13). Waiting for 140ms of quiet before committing left the header on the old media all that time while the deck showed the new one — read by the maintainer as "the details are loading". A sweep now pages the moment it crosses `sweepCommit` (a quarter of the slot, capped at 160px), and the momentum after it is SWALLOWED until quiet, unless a delta climbs back up or reverses (`sweepRestarts`: fingers landing again), which pages again. Both pure, in `pan-zoom.ts`.
- **The deck pages on a timer, never on `transitionend`.** The offset is sometimes already at its target, and that fires nothing — the deck would hang mid-slide. One `DECK_SETTLE_MS` timer slides the deck a whole slot, and only THEN moves the index and drops the offset in the same commit: the neighbour is already where the middle slot is, so the swap shows no seam. A gesture arriving while it is in flight lands it first (`land`).
- **Key the slots by row id, not by slot** — React then carries the neighbour's already-loaded picture into the middle and the page shows no reload. With exactly two media both neighbours ARE the same row, so the key has to fall back to the slot; with one, there is a single slot.

**The wheel is heard on the frame's wrapper, and the node under the pointer is never removed (2026-09-13).** Symptom: arrows always paged, a trackpad sweep sometimes did nothing until the cursor MOVED. Two causes. (1) A wheel event goes to the element under the pointer, and the pager buttons are siblings of the viewport, not children — a sweep started with the pointer resting on the arrow just clicked reached no listener; `surfaceRef` (the `relative flex-1` wrapper) now takes the wheel. (2) Chrome latches a whole wheel sequence, momentum included, to the node it started on; once that node leaves the DOM its events propagate nowhere until a mouse move resets the latch. The clip's `<video>` used to unmount when it left the middle slot — it is under the pointer at that instant — so it is now mounted in every slot of a video item, given `src` and `controls` only in the middle, and `pause()` + `load()` when it leaves (removing `src` alone keeps the download going). A two-media deck keys its previous slot `id:prev` and the others by bare id, so whichever media was under the pointer keeps its element across a page. **How to apply**: in any surface driven by wheel, never unmount or re-key the element a sweep may have started on.

**The header names where the deck is GOING (`viewer.heading`), not where it has landed**, so the title and facts change with the picture instead of 280ms after it; the index itself still moves only on landing, or the slot swap would show a seam. A second arrow press while a page slides lands the first (`pageBy`), so no press is lost. The exposure line keeps its height across the whole deck whenever any item has one (a line appearing per page resized the frame under the finger), a local photo whose head is still being read says `reading exposure…` in that place (`LightboxItem.cameraPending`), and the Library reads the open photo and its two neighbours so the line is usually there before the page lands.

**The zoom pill is in the HEADER, left of Close, hidden under 820px (2026-09-13)** — in the frame's bottom-right corner it sat on a clip's native control bar (volume, fullscreen, ⋮). Under 820px the pinch is the gesture, as the swipe is for the pager. Close beside it wears the pill's height (34px, `h-[2.125rem]`, Button `md`'s too): a 22px chip next to a 34px pill read as a mistake — controls sharing a row share a height.

**Pan limits are measured off the PICTURE (`containedSize`), never off the box**, or a letterboxed panorama pans into its own bars. Winnow's row and the library's `MediaMeta` both already carry `width`/`height`, so the limits are right before a byte arrives; the media reports its own through `onMeasured` otherwise.

**Looking at a picture and putting it to work are two verbs, so they are two buttons.** A library row's 80×56 cover opens the sheet (a `⤢` on hover, nothing at rest) and its text column stays the activate target — a button inside a button is not markup, and the cover was inside one. Same rule as the Winnow tab's tiles, where a click already previewed rather than fetched.

**A clip keeps the bottom 56px to itself** — a heuristic strip for the native control bar, since the browser does not expose it — and above that a clip swipes like a picture. Everywhere, a tap still reaches the controls because nothing is `preventDefault`ed before the drag slop. **Not built, and cheap to add later**: a swipe that continues out of a zoomed picture once it hits an edge (iOS does it; it needs a per-axis "how far past the edge did this push" state machine).

**Nothing waits, and nothing is ever greyed out.** Two answers to "why does it feel stuck while it loads", neither of which blocks a hand: (1) a slot draws the cheap **still under the full rendition**, so a page never opens on black and simply sharpens — and the full one is mounted in EVERY slot, not just the middle, because rendering the neighbours is what preloads them (three requests instead of one, which is the point; a clip is the exception, only the middle slot mounts a `<video>`); (2) a 2px indeterminate bar (`--animate-deck-load`) along the top of the frame while the middle slot is not yet sharp, with `aria-busy` on the frame. And a gesture arriving DURING a page no longer waits for it: it lands that page at once (`land`) and starts from there, which was the only place the deck genuinely refused a swipe. A clip reports ready on `loadedmetadata`, never `loadeddata` — with `preload="metadata"` a browser may hold the first frame back until play, and a bar that never stops is worse than no bar.

**A media opens on the instance in its own tab** — the secondary action beside "Add to library". It points at the PROXY's own URL, because Winnow has no page per asset (checked in its repo: `/library`, `/sift`, `/search`, no `/assets/[id]`, and its viewer takes no deep link) and its `/download` route sends `Content-Disposition: attachment`, which saves a file rather than showing one.

**The develop sheet is the second surface that looks closer at one picture (2026-09-15, the maintainer: *"in the develop modal … mouse zoom/pinch, trackpad, touchpad gestures"*).** It does not contradict «a media preview never view-zooms»: the sheet is where a picture is INSPECTED, like the lightbox, not an editor stage whose own framing gestures a zoom would fight. Four decisions. (1) **Its own hook, `use-picture-zoom.ts`, on the same arithmetic** — `use-media-viewer.ts` pages a deck in every handler (swipe, sweep, momentum, `land`), and teaching it an "off" switch would put the wheel-latching fixes above at risk for a surface with nothing to page; the pinch and wheel semantics are copied, so the two surfaces answer a hand the same way. (2) ~~The ceiling is one preview pixel per device pixel~~ — **revised 2026-09-19, the maintainer: *"we need to be able to zoom much more maybe like 4000% like Lightroom right, and choose between smooth or pixelated zoom"*. The develop ceiling is `INSPECT_MAX_ZOOM` = 40× (4000 %, Lightroom's own), and 1:1 becomes a LANDMARK rather than a limit** (`onePixelZoom`, beside the untouched `pixelCeiling` the lightbox still uses at 8×). The old argument — past 1:1 nothing is added, so stop there — was right about the pixels and wrong about the use: a photographer magnifies past 1:1 to judge an edge, a speck or a stroke's own falloff, and refusing is refusing the gesture, not protecting the truth. What protects the truth instead is SAYING it: past `PictureZoom.magnifying` a pill offers **smooth ↔ pixels** (`use-pixel-view.ts`, `image-rendering: pixelated`, a `localStorage` preference and never a document, like the LUT interpolation mode), so a magnified preview pixel can be drawn as a pixel rather than as a gradient nothing photographed. Below 1:1 the pill is absent and the CSS is left alone — there the browser is DOWNSCALING, where `pixelated` is simply worse. Re-decoding at full size on zoom stays declined (the 194 MB buffers that killed an iPhone tab), so what 4000 % magnifies is still the stage's budgeted preview; the honest next step for real detail is P11's 1:1 loupe over a full-resolution decode (`docs/photo-editor.md`), not a higher ceiling. `pan-zoom.ts` functions still take the ceiling as an optional last argument. (3) **Fitted, a drag anywhere places the divider as before; zoomed, a drag pans and the divider carries a HANDLE that wipes at any zoom** (his pick over "pan only" and "modifier to pan"). The divider moved from a canvas stroke to a DOM line + handle positioned through `pictureRect`, so it stays a hairline at 2.5×; the wipe fraction goes through `pictureFraction`, which also fixed an old drift over a letterboxed picture (it used to be a share of the WRAPPER). The handle is held inside the frame when the line is panned out of view, and at rest (nothing moved yet) it sits on the picture's right edge — an affordance the plain drag never had. (4) **A finger does not wipe until it travels 6px or lifts as a tap**, and a second finger never starts a wipe: the first finger of a pinch otherwise threw the divider to wherever it landed. The native pinch listener fires before React's delegated one, so the sheet counts its own fingers rather than trusting `onTakeover` to have run first. Verified in the Browser pane on a 4000×3000 JPEG: wheel to 267% (= 3326 / (622 × 2)), a slider change keeps the view, a mouse drag pans without touching the wipe, the handle wipes while zoomed, a synthetic pinch fitted leaves the divider, a tap places it, and at 390 wide the pill is gone. Not checked from the Studio's Grade tab (same component, same props). **Its Close wears the pill's 34px, always** (the lightbox's rule, missed on the first build and reported by the maintainer the same day): any header that gains the zoom pill gains the height with it — a 22px chip beside it reads as a mistake.

**Testing gestures in a throttled browser will lie to you.** A background tab clamps `setTimeout` to ~1s, so synthetic `pointermove`s land a second apart and every velocity reads ~0.02 px/ms: the distance path pages, the flick path never does, and nothing is wrong. Check the event `timeStamp` deltas before believing a velocity bug.

## 2026-09-14 — `accent-color` disables Chromium's dark-mode repaint of a range track

`<input type="range">` renders with a UA-default light-grey runnable track under `color-scheme: dark` too, once the element also carries `accent-color` (the whole suite's sliders do, for the vermilion thumb) — verified live by comparing an `accent-color`-free range (correctly dark under `color-scheme:dark`) against one with it (stays pale under every `color-scheme` value). It is why the darkroom's `color-scheme: dark` (`index.css`) never reached `RangeField`'s Zoom/Rotation sliders, the AssetSidebar's Library rows (`bg-white`, unrelated hardcoded hex) and the badge-time slider all had the same white-under-dark symptom. **How to apply**: never rely on `color-scheme` to theme a range input that also sets `accent-color` — paint `::-webkit-slider-runnable-track`/`::-moz-range-track` from a token instead (`index.css`, one rule for every range in the app). Any new raw white (`bg-white`, `#fff`) found the same way this one was — a hardcoded value never covered by dark-theme/darkroom token overrides — is the same bug class, not a one-off.

`RangeField` additionally reports the value as an accent fill, which took a second pass: a hard-stop gradient placed at a raw `fraction * 100%` does not land on the thumb, because the native thumb's own travel is inset by half its width at each end — the two stops disagreed worst at a low or high value, drawn as a solid circle sitting past a visible vertical seam. Fixed by giving `.range-fill`'s thumb a FIXED, known size (14px, `-webkit-appearance:none`/`-moz-appearance:none` on both track and thumb) so the gradient stop can be computed at the thumb's own centre with `calc((100% - 14px) * var(--range-fraction) + 7px)` instead of guessing the UA's own thumb width. **How to apply**: never place a range's fill stop at a plain percentage of the track box once the thumb is anything but a mathematical point — fix the thumb's size first, then the calc.

**Artifact trap**: the maintainer views artifacts in a ~600px panel. Mockups scaled with container units shrank to unreadable text there, and `cqw` on an element that is ITS OWN container resolves against the ancestor (or the viewport), not itself. Draw a mockup at a fixed real width inside an `overflow-x: auto` box, with an opt-in fit-to-width `zoom`.

## 2026-09-14 — Two shapes drawn close together can "merge" visually with correct stacking; z-index only settles who wins on shared pixels

Reported: on a phone, the trip overview's LOUPE frame (`LoupeBrush.tsx`, drawn over `DayHeatmap`'s grid) looked cut wherever the OPEN day's own selection square sat, which is routinely inside the loupe's edge column (opening/dragging the loupe centres or ends it on the open day). First guess, matching the report's own wording, was a stacking bug — a transformed cell (`hover:scale-125`) can be promoted ahead of a `z-index:auto` sibling regardless of DOM order — so the loupe's root got an explicit `z-10`. **That changed nothing**, confirmed live with `getBoundingClientRect()` in headless Chromium: the frame's 1px border and the selection ring's 3px halo (2px outline + 1px offset) sat only ~2px apart, close enough to visually fuse at a phone's pixel density. z-index decides paint order only for pixels the two elements actually SHARE — two adjacent-but-separate shapes with no shared pixels don't have an order to settle, and a thin 1px line was never going to visually "win" against a several-px-wide shape drawn right beside it. Fixed by widening the real gap instead (`docs/memory/roadtrip.md` has the numbers: the frame's `OUTSET`, the ring's `outlineOffset`, the scroll box's padding). The `z-10` stayed — a defensible default for an overlay meant to sit above interactive cells — but it was not the fix. **How to apply**: before reaching for z-index on a "cut" or "broken" edge, measure the actual boxes (`getBoundingClientRect`, or a tight zoomed screenshot) — if they do not overlap, the fix is spacing, not stacking.

**The maintainer's ask (2026-09-21)**, out of the RAW work but deliberately
suite-wide: a hairline on a MEDIA's edge — a fill when the length is known, a
sweep when it is not — as the passive surface, plus something naming the
operation with a Cancel *"si l'utilisateur veut faire autre chose"*. That last
clause is the argument against a modal and for the `SyncPill` family: a modal
forbids the very thing the cancel is for. The design, the five phases and the
five open questions are `docs/progress-feedback.md`; the honest-value rule
applies to a bar as much as to a badge — a percentage nobody measured is a
fabrication, so an unknown length SWEEPS, and a Cancel is drawn only where the
work can really stop. **Built the same day, T1 → T5** — the registry, the
pill, the edge and every wiring decision are `tasks.md`; the one rule for a
panel's own bar is there too: beside the verb it stays, repeating the pill it
goes.

**A toolbar never INSERTS a control (2026-09-22).** The Develop stage bar drew
its `smooth ↔ pixels` pill only past 1:1, so crossing that zoom pushed every
verb after it sideways — and a second press of `+` landed on the pill that had
just appeared under the pointer. The rule: a control whose existence depends on
state belongs inside something of FIXED width — a menu hanging off a label that
is already there — never in the flow between two buttons a hand is aiming at.
`OverflowMenu` gained `trigger.bare` for it (`className` is then the whole
recipe, so none of `Button`'s font, height, padding or `shrink-0` fights the
caller's), and `StageZoomControl` takes optional `items` that turn its
percentage into that menu. The same prop is what lets a file NAME carry a menu
(`develop-roll.md`, B2).
