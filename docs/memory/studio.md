# Studio — the unified editor and the merge plan

Read before touching `src/tools/studio/`, `src/shared/overlay/`, anything about project persistence, title styles, or before retiring one of the legacy tool pages.

## The suite is converging into one Studio (2026-08-20)

**Decision.** The maintainer wants the separate tools merged into a single editing studio: import from the drone's card, view, grade (LUT), place styled telemetry/text overlays by drag-and-drop, compare, and export — without switching pages. Agreed phases: **0** consolidate `shared/` (done, PR #29) · **1** the `/studio` route with viewer + overlay + grade + export (this phase) · **2** projects (gallery, persistence, reconciliation) · **3** title styles (cascade + glow) · **4** absorb the remaining tools as panels and retire their routes · **5** photo export + HUD kit (SD-card import dropped — see below). **Why**: juggling between pages to produce one piece of content. **How to apply**: the transition is *soft* — legacy routes stay until their studio equivalent exists (phase 4); new capability goes into the studio (or the shared engine), not into the legacy pages. Scopes and Cull were explicitly retired (maintainer decision, 2026-08-20), not to be re-proposed.

## Routes and the end state (2026-08-20)

**Decision.** Phase 2 introduces a project gallery under `/studio/home` (create / open / delete, an After-Effects-style creation modal) while `/studio` edits the open project (`/studio/:projectId` when the router grows params — today's hash router is exact-match only, ~20 lines to extend). At the end of the transition the gallery becomes the app's home page. **How to apply**: don't build navigation that fights this; the studio opens on *projects*, not on a file picker.

## Project model: portable template + bound instance (2026-08-20)

**Decision.** A project document splits in two. *Portable* (the template): style theme, overlay elements and positions, LUT, export format/gabarit, map settings. *Bound* (the instance): the media-directory **handle**, the media list (name + size + mtime), the active clip. Media bytes are **never** copied into storage. Directory handles are structured-cloneable → stored in IndexedDB; on open, one permission click re-resolves media by filename; manual re-pointing is the fallback (Chromium-only feature — Firefox/Safari get the manual path, say so in the UI). Reconciliation classifies media found / changed / missing and never blocks opening. "Save as template" = portable half alone; "open with other media" = keep portable, rebind. **Storage**: IndexedDB for documents, handles, baked thumbnails (galleries can't decode media that isn't reconciled yet — bake thumbnail + duration + size at save time); `localStorage` for UI prefs only; request `navigator.storage.persist()`.

## The missing-media banner is not always a problem (2026-08-22)

**Decision.** "Missing" media is a routine outcome, not an error: the maintainer reworks his folders after export (moving satisfying takes, deleting rejected rushes), and a project reopened against that folder will legitimately never see those files again. The banner (`StudioEditor.tsx`) now says so and offers two ways out: `onRepoint` (point to a different/updated folder — unchanged) and a new `onForgetMissing` (`StudioTool.tsx`) that prunes the matched-by-name missing `SavedMediaRef`s out of `media.files` and persists the trimmed doc — so a deliberately-gone file stops being flagged on every future open. It recomputes the `Reconciliation` locally from the existing `items` (no re-list of the folder, no permission prompt). **Visual weight follows the actual risk**: missing-only uses a neutral tone (`noticeMuted` — paper/line/ink-soft, no accent colour), while a `changed` count (same name, different size/mtime — could silently alter the export) keeps the warning-accent `notice` style. **How to apply**: don't reintroduce a single alarmed style for both cases; "missing" alone must read as informational, "changed" as worth attention. `media.trims` is deliberately left untouched by the forget action — it's keyed by asset id and harmless to keep, and lets a trim survive if the same-named file is ever re-added.

## The project file: the portable half on disk (2026-08-21)

**Decision.** A project's settings export to `<project>.atelier.json` and import back (`shared/projects/project-file.ts`, pure, 14 tests). The file IS the portable half — nothing new to keep in sync: `settings`, `elements`, `guides`, `lutStack` (custom `.cube` text inlined, so a shared grade lands identically), `outputTransform`, `theme`, `exportPrefs`. Never the bound half (dir handle, media list, thumbnail) nor the document `id`: a project file is a template you can mail, not a backup of a folder.

**Where it lives, and why there.** Export + "import into this project" sit in the **Project settings modal** under an *Import / export* section; the gallery gets its own "Import a project file" that creates a **new** project. The maintainer first suggested a download icon in the project bar — rejected together: the bar's chips are already balanced, and a lone ↓ next to an editor whose Export tab renders video reads as "download the video". Importing has two meanings and both are offered: into the open project (destructive → inline two-step confirm, the deck-reset pattern, never a second modal) or as a new project (the "someone sent me a preset" case).

**Conventions to keep.** The download is composed from the LIVE editor state plus the modal's *draft* values, not from `docRef` — otherwise an unapplied draft or the 800 ms autosave debounce ships a stale file. Import writes straight into the editor's state and lets the autosave persist it; the project's **name** and media are never overwritten by a file. `version` is `PROJECT_DOC_VERSION` and `parseProjectFile` replays `migrateProjectDoc`, so bumping the doc version keeps old files readable for free — but a file from a **newer** version is refused, never half-read. The text comes off a stranger's disk: parsing returns `{ok:false, error}` with a sentence a human can act on and never throws.

**Trap seen in the browser**: the section sits at the bottom of a `max-h-[90vh] overflow-auto` dialog, so the confirmation appeared below the fold and read as "nothing happened" — it now `scrollIntoView({block:'nearest'})`s on appearance. Anything added below it needs the same care.

## Creation-modal parameters (2026-08-21)

**Decision.** Aspect before resolution (9:16 / 1:1 / 4:5 / 16:9 presets named by destination), background colour **plus** media fit (cover/contain/stretch — the real decision), initial style theme, "start from template", optional media folder, units + label language, safe-zone margins. Explicitly **out**: bitrate/codec/LUT/destination — export-time decisions. **Frame rate left this list** (2026-08-21): it is a per-*variant* delivery choice, sitting in the export matrix beside aspect and resolution, not a project setting — one project legitimately ships a 60 fps master and a 30 fps social cut, and a project-level cadence would have to be overridden by every row anyway. The arithmetic and its traps are in `media-pipeline.md`. All parameters editable later; a *resolution* change is a pure homothety (element positions are normalized, sizes are short-side fractions), an *aspect* change is a recomposition and must go through a small confirmation step, never silently.

## Safe zones turn with the frame (2026-08-22)

**Decision.** A safe-zone preset is authored for one orientation (portrait for Reels/TikTok/Shorts, landscape for YouTube), so over a frame of the opposite orientation the upright template used to shrink to a band across the middle — the maintainer's "elle s'affiche complètement au milieu de la landscape". The template now takes a **quarter-turn** so it spans the frame: `safeZoneOrientation: 'auto' | 'upright' | 'rotated'` on `GuidesState`, `'auto'` turning it only when the two orientations disagree, plus a **Rotate** toggle in `GuidesControl` that pins the other value. **Why**: he reads the guide to judge *what a crop would cover* before choosing an export — a template spanning the frame answers that; a band in the middle does not. It is the **guide** that turns; media rotation and cropping are separate features he has not asked for.

**Rejected, do not re-propose.** I first argued rotation was semantically wrong (Instagram's chrome never rotates) and offered instead a *fit/letterbox* mode — the frame inscribed in the platform's screen, deadzones reprojected — and binding the guides to an export variant. Both were declined: he is not claiming the rotated layout is a screenshot of Instagram, he is using it as a reading grid. The lesson generalises: the anti-fabrication rule (palette, battery, heading) is about **values presented as measured**, not about editor chrome the author positions himself.

**Conventions to keep.** `resolveSafeZone(guides, frameAspect)` is the single entry point — `draw-guides.ts` calls it, nothing else recombines `findSafeZone` with a rotation. The turn is **clockwise** (`rotateSafeZone`: `x' = 1-y-h, y' = x, w' = h, h' = w`), i.e. the phone tipped onto its right side: the portrait top bar lands on the right edge, the action column along the bottom. Labels are never rotated — they name what covers the area and must stay readable. `orientationOf` carries a ±2 % dead band so a square frame or template never triggers `'auto'`. Picking another preset resets the mode to `'auto'`: a rotation pinned for a portrait template means nothing under the landscape one. `GuidesControl` takes `frameAspect` so its toggle shows what `'auto'` actually resolves to; without it the toggle reads upright, which is what `'auto'` draws when the orientation is unknown.

**Migration.** ProjectDoc v9 lands existing projects on `'auto'`, deliberately breaking the usual "a reopened project must look exactly as it was closed" rule — that rule guards **rendered output** (v6's output transform, v7's frame rate), and guides never reach a pixel of an export. Landing them on `'upright'` would have hidden the feature from every project that predates it.

## Title styles: a three-level cascade (2026-08-20)

**Decision.** Named preset ("Or ciné", "Pixel CRT", "Rouge plein cadre") → project theme (preset + tweaks) → per-element **partial** overrides (store only the overridden property; show a per-property "back to theme" control). The theme carries *appearance only* (font, weight, italic, case, colour, glow, letter-spacing, legibility, grain) — never geometry (position, anchor, bound field, text); size is a theme *multiplier* over the element's own size. The film-glow ("bave") is one 0–100 theme slider driving four layers proportionally (softened core ~0.3–0.8px blur, tight bright halo 1–3px, wide warm-drifting bleed 10–30px at 5–15% opacity, animated grain), with an advanced per-layer disclosure. **Why**: the maintainer's reference imagery is optical-era title cards (halation); the slider spans muted (gold serif card) to fluo (CRT pixel cards). **How to apply**: extending `LegibilityStyle` needs `measureOverlays`' margin widened for anything painting outside the text box, and the mode is switched on in three draw sites (text, arrow, compass) — see `shared/overlay/draw-overlays.ts`.

## SD-card import is abandoned (2026-08-21)

**Decision.** The planned "drone card import" (recognise DCIM trees, auto-pair from the card) is **dropped** — do not re-propose it. **Why**: the maintainer reworks his folders before editing (combining, pruning, sometimes copying locally for speed), so a card-shaped importer would fight his workflow; pointing the existing folder picker at whatever directory he prepared is strictly better. **How to apply**: invest in the folder picker and reconciliation instead; treat "where the media lives" as the user's business.

## The grade is a stack, baked not chained (2026-08-21)

**Decision.** The studio's Grade tab holds an ordered stack of LUT layers (add, remove, ↑/↓ reorder, per-layer intensity 0–3, per-layer enable switch — the maintainer's "quick disable for testing"). `shared/lut/lut-stack.ts` (pure, 15 tests) resolves it: `composeLutStack` walks a lattice and pushes each point through every enabled layer (trilinear `sampleLut` + intensity mix), **baking one `CubeLut`** — it does NOT chain N GPU passes. **Why**: the renderer, the preview, the frame grab and both export paths keep taking exactly one LUT and never learn stacking exists; one shader pass regardless of stack depth. **How to apply**: the composed cube adopts the LARGEST input size (capped 64) to limit resampling error, and a single full-strength layer is returned as-is so the common case pays nothing. Baking is memoised on the layer list — never bake in a render body. Layer *order matters* and is user-visible; reordering is ↑/↓ buttons by explicit request (drag-and-drop is fiddly in a 340px column). `useLutStack` is studio-only; the legacy pages keep the single-look `useLutSelection` and must not grow features. ProjectDoc v4 persists `lutStack` (custom `.cube`s as text); the v3→v4 migration turns the old single look into a one-layer stack so old projects grade identically.

## Adding an overlay element is a palette (2026-08-21)

**Decision.** The Overlay tab adds through `shared/overlay/ElementPalette.tsx`: a foldable grid, **three cells per row**, grouped Flight / Camera / Time / Shapes (`palette-groups.ts`, pure, with a test asserting every `TelemetryFieldKey` is reachable exactly once — add a field to the model and the test fails until the palette offers it). Each cell previews **what it will really add**: the live value at the playhead resolved through the project theme, on a dark `#141210` stage. The dropdown + `+ Field` pair is gone (the maintainer: picking a field blind, then pressing a second button, was "agaçant"); arrow and corners are ordinary cells. **Conventions to keep**: a field with no value shows its label ALONE — never a fabricated "87 m", which would lie about the footage; already-placed components are marked (dot, or a count) but never disabled, duplicating is legitimate; the fold state is **owned by the caller**, because the inspector unmounts its tabs and a palette re-collapsing on every trip to Style is maddening (it starts open only on an empty deck). Cell names strip the dropdown's parentheticals ("Clock (HH:MM:SS)" → "Clock") and the stage fades at both edges rather than chopping a long readout mid-glyph.

**"Add deck" became a reset.** It silently replaced the whole deck. Now: an empty frame gets a plain offer ("Start from the default deck"), a populated one gets "Reset deck" behind an inline two-step confirm — same pattern as the gallery card's delete, no modal.

**DOM previews are shared.** `shared/overlay/style-preview.ts` turns a `ResolvedStyle` (or a `TitleStyle` plus its derived layers) into CSS: font stack, and the four canvas glow layers collapsed into a two-stop `text-shadow` in **em** (so one helper serves any preview size) plus a `drop-shadow` variant for SVG glyphs. The Style tab's preset cards and the palette both go through it — do not hand-roll a third approximation. It is an approximation on purpose; `draw-overlays.ts` remains the truth.

**`ElementList` no longer owns adding.** Its add row is opt-in via `addControls` — the studio omits it, the legacy overlay page passes it and stays untouched (that page dies in phase 4; don't polish it, don't duplicate the list either).

## Slow motion and time-lapse: one measured number (2026-08-21)

**The cause, so no future session re-diagnoses it.** A conformed clip (120 fps laid down at 30) makes one second of flight last four seconds of file. Everything in `motion.ts` is a distance over a time, so the ground speed read a quarter of the truth — the maintainer's "30 km/h affiché 3". A hyperlapse is the same bug with the sign flipped.

**The model.** `timeScale` = **capture seconds per second of media** (1 real time, 0.25 = 4× slow, 10 = 10× lapse), measured in `telemetry/time-scale.ts` and passed to `attachMotion(cues, timeScale)`. It divides the rates **and** stretches the look-back window (`WINDOW_S`/`MIN_DT_S` are capture seconds; one file-second of a 4× clip holds a quarter of the GPS updates the estimate needs). Rule that decides every future case: **physics in capture seconds, aesthetics in timeline seconds** — the heading smoothing's `tau`/`hold` and the glow's grain stay on the file's clock, because the author tunes them by eye.

**What must NOT be corrected.** Not the playhead: on a conformed clip the cues are already aligned with the picture, so remapping the lookup would desync the overlay. Not the heading — an azimuth is a ratio of distances and survives any conform. Not the clock/date badges: they read the capture timestamp, so they tick slowly on a ralenti, and that is the truth about the footage.

**How it is measured, and why that shape.** Theil–Sen (median slope over *all* anchor pairs, each spanning ≥ ¼ of the clip) of capture timestamp against `cue.start`, ~128 anchors spread by time. Three traps, all measured against synthetic clips before the code settled: (1) the whole-baseline ratio has no defence against one cue written before the aircraft's clock was set; (2) the median of *neighbouring* ratios breaks on firmware that writes whole seconds — neighbours 0.3 s apart read 0 or 1 s, and it called an ordinary clip a 3× lapse; (3) **dropping the pairs where the clock did not tick biases every estimate upward**, because only the pairs that rounded *up* survive — a five-second clip came out at 1.04, i.e. a time-lapse. Zero-tick pairs therefore vote. And when the clock's resolution exceeds a tenth of the capture time it must divide, the answer is thrown away (`MAX_QUANTISATION`): error tracks that ratio closely (0.1 → ~0 %, 0.2 → ~5 %, 0.4 → ~17 %), and "not measurable" is a real answer where a 17 %-wrong cadence is not. The full matrix — {ms, whole-second} × {DiffTime, none} × cadences from 60× lapse to 8× slow — is exact or refused, never wrong. `DiffTime` (now parsed; it sits outside the `[ ]` brackets, which is why it was silently dropped for so long) is the fallback only: one firmware-written number with no baseline, and a firmware that conformed it too would hide the ralenti. The result snaps to an exact ratio of standard rates when within 2 %, and `snapRate` picks the **nearest** candidate — 29.97 and 30 are 0.1 % apart, so first-match rounded exact 30 fps footage to NTSC.

**Four guards, each bought with a measured failure — do not remove one without reproducing its case.** (1) A real subtitle file is a valid `.srt`: SDH captions carry `[MUSIC PLAYING]`, so the parser's format sniff accepts them and their cue spacing would have the library announce a film as "0.40 fps" — a cue list with no frame numbers and no fields is not a flight log. (2) The clock's resolution is read from a **dense burst of consecutive cues**, never from the spread-out anchors: those are seconds apart, so their smallest gap measures how far apart we sampled and would refuse a good short clip. (3) A clock silent across more than 40 % of the clip is stalled, not slow, and is refused — quantisation never reaches that, because a coarse clock's silent runs are bounded by the resolution the previous guard already caps. (4) `attachMotion` caps the look-back window at **half the clip**: 8× slow motion on an eight-second file would otherwise stretch a one-second window past the whole thing and turn every reading into "the average since frame 0".

**Two more, from the adversarial review of the first version.** (5) `DiffTime` is **whole milliseconds**, and the rates slow motion uses fall badly inside one: 120 fps is 8.333 ms written `8ms`, 240 fps is 4.167 ms written `4ms`. Dividing by the written value reads 125 and 250 fps — rates no camera shoots — 4 % out, twice the snap tolerance, so nothing downstream rescues it. Invert instead: *which standard rate, rounded the way firmware rounds, writes this millisecond?* No match means silence. Any test helper for this path must write whole milliseconds; an exact `1/fps` float hides the whole problem (the first version's did). (6) `formatCadence` returns null unless a capture rate was actually measured: `60 fps` on its own **states** that the clip was shot at the rate it plays, which is exactly what an unmeasurable log cannot support — a surface with only a playback rate must say so in words ("plays at 30 fps · shooting cadence not measurable").

**Two integration rules.** The manual override carries the `clipId` it was typed for — a project steps between the clips of its working set, and a cadence typed for a slow-motion clip must not quadruple the speeds of the ordinary one beside it (auto mode is per-clip for free, manual would not have been). And `use-overlay-stage`'s mark-dirty effect must list `params.cues`: correcting the cadence hands down a re-derived cue list with the same clip on screen, and without a repaint the canvas keeps the old speeds while the inspector shows the new ones — and the autosaved thumbnail bakes the stale frame.

**The container can never answer this.** A conformed file honestly declares the rate it *plays* at; the rate it was shot at is written nowhere in the mp4. Only the telemetry knows — hence a clip with no `.srt` gets an honest "unknown" plus the manual override, never a guess. And `parseSrt` applies the measurement **by default**, so the map, composer and legacy panels are right without knowing the concept exists; the studio parses at scale 1 and applies `ProjectSettings.timeScale` (`auto` | `manual`, ProjectDoc v8) itself. The v8 migration is the one that deliberately changes what an old project shows: pinning it to `manual: 1` would preserve a wrong measurement as if it had been a choice.

## A settings modal explains itself without paying for it in height (2026-08-22)

**Decision.** The studio's modals justify their controls in prose — why a cadence must be corrected, why the capture time is a shift and not a timezone — and on a phone that prose pushed the controls, and Apply itself, below the fold (measured at 390×844: 1064 px of content in a 760 px card, Apply unreachable without scrolling). The prose is **folded behind an ⓘ next to the legend** (`tools/studio/SectionLegend.tsx`), not deleted and not moved to a doc: it is one tap away, next to the word it explains. Same modal now: 714 px, no scrolling at all. **How to apply**: a section whose control needs no explanation passes no children and gets no ⓘ — an icon that reveals nothing is worse than no icon. The `NewProjectModal` was measured too and already fits (608 px), so it keeps its one-line hints; adopt the component there only if it grows.

**What the fold cost, and how it was paid.** With the prose hidden, "Capture time" no longer said it was a *shift* — the label became "Capture-time shift". Folding an explanation means the visible label has to carry what the reader needs to not misuse the control.

**Sticky-footer trap, measured.** `position: sticky; bottom: 0` inside a scrolling card anchors to the **padding box**, so a card with `p-6` leaves a 25 px strip under the pinned bar where scrolled content shows through, and a negative bottom margin does not move it (it changes flow, not the sticky offset). The fix is to take the bottom padding off the card (`px-6 pt-6`) and let the bar own that edge (`-mx-6 px-6 pb-6`).

## Two speeds, and they must never be confused (2026-08-21)

**Decision.** *Playback speed* is a **viewing** choice — `video.playbackRate` on the transport, session state, no document field, and nothing derived follows it (the readouts key off `currentTime`, which is media time whatever rate it advances at). *Delivered speed* is a **per-variant export** choice that really re-times the file, and it sits in the export matrix beside aspect / resolution / frame rate, where a per-variant delivery decision belongs. Both offer the factor that undoes the clip's own conform (`real (4×)` on the transport, "4× speed — real time" in the variant menu), which is the whole reason the cadence measurement exists.

**The arithmetic is one line, on purpose.** The source span is divided by the speed *before* it meets the existing `1/fps` grid (`planFrameIndices`), so cadence and speed compose instead of fighting: 2× at the source rate drops every other frame, 0.5× repeats each one, 2× at 30 fps from 60 fps keeps a quarter. No interpolation, ever — the same rule the frame-rate control already followed.

**A re-timed variant ships silent, and that is a decision, not an omission.** Audio is copied bit-for-bit and never re-encoded (see `media-pipeline.md`); a copied track against a re-timed picture is a desync, which is worse than no track. The muxer must not even *declare* an audio track in that case — an empty track is worse than none — and the UI says it before the export runs. Both export paths do this: the seek fallback too, because the studio falls back there for undecodable HEVC and a variant that quietly ignored its speed would ship a normal clip under a `-2x` name.

**Burned-in telemetry does not change under a re-time**: every output frame still draws the cue of the source frame it shows, so a sped-up clip reports how fast the aircraft really flew. That falls out of deriving motion in capture seconds (above) — don't "fix" it.

**Trap for whoever tests this in CI or a container**: the headless Chromium in this project's cloud sessions has **no H.264 encoder** (`VideoEncoder.isConfigSupported` says false for every `avc1.*`; VP8/VP9 only), and `MediaRecorder`'s `video/mp4` writes VP9 in an MP4, which the export pipeline rejects for want of an `avcC`. So no export can be driven end to end there — verify the retime through `frame-rate.test.ts` and the UI, and run the encode on a real machine.

## The heading is course over ground, and it has holes (2026-08-21)

**The cause, so no future session re-diagnoses it.** The `.srt` carries no compass and no yaw. `motion.ts` reconstructs the heading as the azimuth between GPS fixes ~1 s apart, and **suppresses it** below `MIN_MOVE_M = 1` metre of horizontal travel — hovering, creeping, or **yawing on the spot** (nose turns, ground track doesn't) all produce nothing. Do **not** lower that floor to "fix" the gaps: it trades a gap for a weathervane driven by GPS noise.

**The remedy.** `telemetry/heading-smooth.ts` (pure, 8 tests) averages a window of readings and reports `{heading, age, confidence}`. Two rules it must keep: (1) it is a pure function of `(cues, time)`, **never an accumulator over rendered frames** — preview and export do not render at the same cadence, and a frame-fed filter would make the burn-in disagree with the screen; (2) the average is **circular** (unit vectors), because averaging 350° and 10° arithmetically points due South. The same window bridges short gaps for free.

**Gap behaviour is the author's choice** (`headingGap` on the element): `dim` (default) holds the last bearing and fades it over `headingHoldSeconds`, `hold` keeps it plain then drops, `hide` is the old abrupt no-data state. Both the arrow and the tape share `headingSmoothing` / `headingGap` / `headingHoldSeconds`. `DrawOptions.cues` carries the cue list into the renderer — without it (a caller that passes only the cue at the playhead) the instruments fall back to the raw reading, so nothing regresses.

## The opening second is measured forward, not left blank (2026-08-22)

**The complaint.** Every motion instrument (speed, vertical speed, heading readout, arrow, tape) opens on `—` and only comes alive after the first second — and the maintainer's cuts are short, so that hole *is* the beginning of the video posted to social. Cause: `motion.ts` differences each cue against one ~1 s older, so the first cues have no past (no speed below `MIN_DT_S`, no heading until `MIN_MOVE_M` of travel accumulates).

**Decision.** The data is not missing, only ahead. `attachMotion` now also attaches `Cue.lead` — the *same* window measured **forward** — to the cues of the opening window only, and `motionAt(cue, early)` merges `derived.x ?? lead.x`. Per-element opt-out `earlyValues` (default **on**, so no document migration and old projects gain it) reaches the renderer, the field formatter and `smoothHeading`; the inspector shows it as "Value from the start" on the two heading instruments and on the three derived readouts.

**The lines that keep this honest**, and that a future change must not cross: it is a *measurement of the coming second*, never an extrapolation — a hovering start still shows nothing, which keeps the palette's anti-fabrication rule intact; `lead` never covers a value the look-back could measure (merge is per field, `derived` wins); and it stops at the opening window — mid-clip gaps belong to `headingGap` (`dim`/`hold`/`hide`), because carrying a bearing *backwards* into a gap would announce a turn before it happens. `lead` is a separate field rather than a patched `derived` precisely so both readings stay available and the opt-out is a read-time decision, not a re-parse.

**How to apply**: read motion through `motionAt`, never `cue.derived?.x` — every call site (overlay, panels, map, composer HUD) was converted. `smoothHeading` reads the field inline instead, on purpose: it walks up to a 12 s window per rendered frame and an object per cue would be a needless allocation.

## The glow's grain must be masked by the glow, not by a box (2026-08-21)

**The bug the maintainer saw**: a visible rectangle around every glowing readout, worse the higher the glow — "comme s'il y avait un carré autour". Cause: the fourth halation layer painted the noise tile through `ctx.rect(); ctx.clip()` at uniform alpha with `overlay` compositing, so the texture stopped dead at a bounding box whose size scales with `bleedRadiusFrac`. **Rule**: nothing in the glow may be bounded by a rectangle — every layer has to carry the halation's own falloff.

**The fix**: compose the grain in a scratch buffer and cut it down with `destination-in` against the same shadowed text the bleed layer paints, so its alpha *is* the glow's falloff. Buffers are module-level and grow-only (`scratches.grain` / `scratches.mask`), because a full-resolution export would otherwise allocate a pair per readout per frame; `MAX_SCRATCH` skips the grain rather than allocating absurdly.

**Canvas trap, measured in Chromium (2026-08-21)**: **a shadow is dropped when the drawing operation runs under a `destination-*` composite mode.** Drawing shadowed text straight into a `destination-in` context left ~2.5k faint pixels where the halation covers ~17k — it silently erased the grain instead of shaping it. Build any such mask in its **own** buffer under `source-over`, then composite it as one image. Applies to every future mask, not just this one.

**The fix regressed preview/export perf — this was the maintainer's next report, "ça ralentit toutes les choses" on Or ciné.** The shape-mask fix above added two more shadow-blurred `fillText` calls per glowing element **per frame** (in `getScratch('mask', …)`), on top of the three already in `drawGlowedText`'s bleed/halo/core layers — `shadowBlur` is the single most expensive Canvas 2D op in this file, and this now ran it 5× per glowing element per `requestAnimationFrame` tick. The mask bitmap does not depend on `timeSeconds`, only on text/font/`bleedRadiusFrac` — only the noise-tile offset (step 2) is time-varying. **Fix (2026-08-22)**: `getMaskFor` in `draw-overlays.ts` caches the rendered mask per element id (`maskCache: Map<elementId, {key, canvas}>`), keyed by a string of `(text, font, letterSpacingEm, bleedRadiusFrac, bx, by)`; the two `fillText` calls only re-run when that key changes (a numeric readout ticking over, a style edit), never on a plain time-driven repaint. `MAX_MASK_CACHE` (256) is the same defensive-clear backstop as `MAX_SCRATCH`. **Ruled out**: the Rec.709→sRGB output-transform work (`media-pipeline.md`) is baked once per slider step via `useDeferredValue`, not per render frame, and no canvas context in the app requests a non-default `colorSpace` — it was not a contributor here.

## Navigating a long deck in a 340px column (2026-08-21)

**Decision.** Four moves, all from the maintainer hunting for controls: (1) the element list folds behind an "Elements · N" header and, open, is **capped at 15rem with its own scroll** — a deck of fifteen readouts used to push the style panel off the bottom; (2) selecting an element scrolls its settings panel into view (`scrollIntoView({block:'nearest'})` on a ref in StudioEditor); (3) `ElementList` keeps the *selected row* in view the same way, because selection often changes from the stage rather than from the list; (4) **picking an element switches the inspector back to the Overlay tab** — the settings only exist there, so a stage click from Style / Grade / Info / Export used to select silently with nothing to show. **How to apply**: route every selection through `selectElement` in StudioEditor (stage `onSelect` and `ElementList`), never `setSelectedElementId` directly, or the tab stays put. The scroll effect is keyed on `[selectedElementId, tab]`, not on the id alone: clicking the already-selected element from another tab changes no id, and without the tab in the deps the panel would never scroll back into view. `block:'nearest'` is deliberate — it does nothing when the target is already visible, so ordinary clicking never jumps the column. New long sections in the inspector should bound their own height rather than relying on the shared scroller.

## The editor splits on a CONTAINER query, not the viewport (2026-08-21)

**Trap, found in the wild.** The stage/inspector split used `min-[900px]:flex-row`, a **viewport** media query — but the editor's real estate is the window minus the 288px Library sidebar and the shell's margins. At a 1000px window the row layout still applied and the fixed 340px inspector left the stage **308px**: the inspector was wider than the picture (the maintainer's "l'overlay remplace la visualisation"). Measured before the fix: 1100→408px, 1000→308px, 900→208px of canvas. It now splits on `@min-[800px]` against the editor's **own** width, and those cases stack instead (538px of canvas).

**Sub-trap**: `container-type: inline-size` implies layout containment, which makes a `position: fixed` descendant resolve against the container instead of the viewport. The `@container` sits on a wrapper around the stage/inspector row only, so the settings modal — a sibling — still covers the viewport. Verified. Any new full-screen overlay must stay outside that wrapper.

## Time fields: format per badge, correction per clip (2026-08-21)

**No timezone picker — deliberately.** DJI's `.srt` records a bare wall-clock reading (`2026-05-30 05:49:34.609`) with no UTC offset and no zone name: it is whatever the aircraft's clock said, and nothing in the file says where on Earth that belongs. Converting between zones needs the source zone, which we do not have; assuming UTC is wrong for most flights. A zone dropdown would look authoritative while producing an arbitrary answer. Do not add one. What is offered instead is a **shift** — hours, **minutes** (the half- and quarter-hour zones are real: India +5:30, Nepal +5:45, Chatham +12:45) and whole **days** (a controller back from a flat battery with the wrong date).

**Where each half lives.** The *format* (12h/24h, meridiem, seconds, milliseconds, date style) is the badge's business and sits on the element as `timeFormat`. The *shift* is the **footage's** and sits in `ProjectSettings.timeShift`, threaded through `DrawOptions.timeShift` to every render path (stage, both exports, the frame grab, and the inspector previews). **Why**: a per-element shift is a footgun — change the clock's, forget the date's, and the overlay contradicts itself. One correction, every time element.

**The arithmetic runs in UTC** (`Date.UTC` / `getUTC*` in `telemetry/time-format.ts`), never through a local `Date`: parsing locally would let the *rendering machine's* zone move the value, so a preview and an export on two computers could disagree. Same input, same string, everywhere.

**Behaviour change to know**: `timestamp` used to echo the SRT line verbatim, milliseconds included; it is now formatted, with milliseconds opt-in (noise on a title card). ProjectDoc v5 adds the zeroed shift.

## The instrument elements: heading tape and battery (2026-08-21)

**Heading tape.** The maintainer's favourite from the HUD mockup, now an overlay kind: a slice of the compass sliding under a fixed sight, ticks fading out at both ends. Geometry is pure in `shared/overlay/heading-tape.ts` (`tapeTicks` / `tapeFadeAlpha` / `angleDelta`, tested) — ticks are emitted on the **absolute** compass scale, not relative to the heading, which is what makes them *slide through* the window instead of being redrawn under it; `angleDelta` is what keeps the ribbon continuous across North. Nearly everything is a knob (`tape*` on `OverlayElement`): width, span, major/minor steps, tick height, edge fade, opacity, sight colour + mark, caption placement, cardinals, baseline rule. **Conventions**: the fade is applied per-tick, never through a canvas alpha mask — a mask needs an offscreen buffer per frame and the export renders full-resolution; only the baseline rule uses a real gradient. With **no heading** the furniture stays and the scale is not drawn: a tape frozen on an invented bearing is exactly the lie the palette rule forbids.

**Battery.** The maintainer suspected it was impossible on his Mini 4 Pro; confirmed — DJI's per-frame `.srt` carries exposure, GPS and altitude, never state of charge (the pack's level lives in the aircraft's flight record). So the gauge reads from a **source**: `'manual'` (an authored percentage, a prop like free text — the default) or `'telemetry'` (probe a cue key; `battery.ts` holds the known spellings and the parser keeps unknown keys, so a firmware that ever emits one works with no code change). With nothing to read it draws the empty cell and a “—”. **Never** ramp a fake level from the clip duration. Do not re-litigate this as "battery is unsupported" — it is supported, honestly.

**Speed units** are `m/s | km/h | mph`, driven by `SPEED_UNITS` in `telemetry/motion.ts` — add one there and every picker follows.

## The export panel reports what a run cost (2026-08-21)

**Decision.** Each variant row shows, after it renders, `✓ 367 KB · 16 s · 0.2× realtime` (`shared/media/export-stats.ts`, pure, 13 tests), and a summary box under the button totals the run. **Why**: the maintainer's stated use is comparing settings — "entre deux variantes, entre deux réglages d'encodage, voir comment ma machine se comporte" — so the figure has to sit **with the setting that produced it** (a grouped ledger under the button was mocked up and rejected for putting them apart). The × realtime ratio is kept deliberately: size and wall clock mean nothing across clips of different lengths, and it is the only one of the three that stays comparable.

**How to apply.** The stats are **session state, never `ProjectDoc`** — they measure this machine today (battery vs mains changes them), not the composition, so they need no document version. They are **dropped the moment they could lie**: changing any of a variant's settings clears that row's figure, and switching clip clears them all — the same anti-fabrication line the palette holds, applied to measurements. Timing wraps the whole variant including `deliver()`, because writing a 400 MB file is part of what the user waited for. One `setInterval` drives the in-flight row's counter for the entire export, not one per row. Formatting reuses `lib/format.ts`'s `formatBytes` (decimal MB, no decimal above 100 — the same figures the Library sidebar shows) rather than a second byte formatter; elapsed time is deliberately **not** `formatDuration`'s `M:SS`, which reads as a position in the clip when the two sit inches apart. Frame grabs are excluded by explicit choice.

## Playback is handed over between clips (2026-08-21)

**Decision.** Stepping through a project's clips no longer stops the transport: `useVideoTransport` takes `resumeAcrossMedia` and plays the new media on its `loadedmetadata` when the previous one was running (the studio opts in; the legacy pages don't, and a tool that swaps media for its own reasons must not start playing on its own). **How to apply**: whether the element was playing is read from a **ref**, not from the `playing` state — the state is already reset when the new media's events arrive. The element is muted and the gesture that started playback already happened, so the `play()` is allowed; its rejection is swallowed rather than surfaced.

## Trimming is per clip, and it is the first brick of editing (2026-08-21)

**Decision.** The transport carries in/out handles (`shared/media/TrimBar.tsx`, geometry in the pure `shared/media/trim.ts`). Rules the maintainer asked for by name: the handles **never cross** (they stop one frame apart); moving a handle past the playhead **pushes** it, live, during the drag; playback **pauses on the out point**, play there **replays from the in point**, and a **↻ toggle** loops the range instead; `I`/`O` cut at the playhead, `Shift+I`/`Shift+O` release a handle. The range is stored **per clip** in `ProjectDoc.media.trims` (bound half, keyed by base name, only for trimmed clips), so switching clips inside a project keeps each one's cut — **that is the point**: he trims several clips of one flight and exports them one by one to assemble later. This does not reopen "one clip per project" below: still one composition, several cuts of it.

**Restoring is guarded by duration, not by name alone.** Each entry carries the duration it was set against; `restoreTrim` refuses it when the media's duration differs by more than 50 ms (same file name, another take) and falls back to the whole clip. A clip that reopens trimmed also opens **on** its in point.

**Dragging previews, and the push works both ways (2026-08-21).** Every drag on the bar seeks: grab a handle and the picture follows *it*, so you cut on the frame you are watching. And the playhead dragged into a handle carries it outwards (`pushBounds`, pure) — the maintainer's complaint was that widening a tight range meant releasing the playhead, finding a handle sitting underneath it and dragging that. Pushing only ever **widens**, so the minimum length can't be violated. The first press of a drag does not push (a click in the greyed-out zone lands on the nearest kept frame instead of silently re-cutting); only carrying on past a handle moves it.

**Three UI traps, all found in the browser.** (1) The trim readout must live on its **own line, always rendered** — putting it in the control row made it appear on the first drag, which resized the flex row and moved the rail under the pointer mid-gesture. (2) A letter shortcut needs a **narrower** guard than the space bar: `targetOwnsSpace` stands down on a focused button or slider, which is right for Space and fatal for `I`/`O` (they would go dead for the rest of the session after any button click). `shared/media/transport-keys.ts` therefore answers both questions — `targetOwnsSpace` for the transport, `targetOwnsTyping` for letters and Delete. (3) The handles and the playhead **coincide constantly** (a fresh clip has both at 0, and every drag parks the playhead on the handle it moved), so stacking them makes one ungrabbable whichever z-order you pick — handles on top turn an intended scrub into a cut, playhead on top makes the in handle of a fresh clip unreachable. The bar is therefore split into two **bands**: handles are grabbed on the rail (top), the playhead by its head (bottom). Any future marker on this bar takes a band, not a z-index.

## One clip per project, for now (2026-08-21)

**Decision.** A studio project is a composition over **one** media (the maintainer's flow: a drone clip, its overlays, its style, its export). Multi-clip editing (timeline, cuts, transitions) is explicitly out of scope; if it ever comes, it is a *list of compositions sharing a theme*, not a rewrite. Don't introduce timeline concepts into the project model.
